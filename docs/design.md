# nod 설계

nod 는 여러 에이전트를 동시에 돌려 일을 처리하고, 사람에게는 결정만 넘기는 오케스트레이터입니다. 사람은 고개만 끄덕이면(nod) 됩니다.

## 불변식

깨지면 안 되는 규칙입니다. 기능을 더할 때마다 이 다섯 가지를 지키는지 먼저 확인합니다.

1. 되돌릴 수 없는 일과 외부로 나가는 일은 사람의 결정 없이 일어나지 않습니다. 프롬프트로 부탁하지 않고 권한 설정으로 막습니다.
2. 모든 상태는 장부(SQLite)에 남습니다. 프로세스가 죽어도 무엇이 어디까지 됐는지 알 수 있습니다.
3. 워커가 끝났다고 보고해도 nod 가 직접 검증하기 전에는 끝난 것이 아닙니다. (M2 부터)
4. 이슈·웹 문서처럼 밖에서 들어온 텍스트는 데이터일 뿐 지시가 아닙니다.
5. 동시에 돌면 안 되는 작업 조합(같은 파일 수정, 같은 포트)은 같이 돌리지 않습니다. 개수 자체는 제한하지 않습니다.

## 구조

```
사람 ─▶ nod CLI ─▶ 장부(~/.nod/nod.db) ◀─ runPool ─▶ runTask ─▶ claude -p (작업마다 작업 폴더 또는 worktree)
```

| 파일 | 하는 일 |
|---|---|
| `src/ledger.ts` | 장부. 작업(tasks)·시도(attempts)·결정(decisions)을 SQLite 에 기록합니다. CLI 와 실행기가 같은 파일을 보므로 둘 사이 통신 서버가 없습니다. 스키마는 `pragma user_version` 으로 버전을 매기고, 마이그레이션은 덧붙이기만 합니다. |
| `src/pool.ts` | 준비된 작업을 빈자리마다 채워 실행합니다. 기본은 무제한이고 `--max` 로만 줄입니다. 작업이 끝날 때마다 준비 목록을 다시 읽어서, 의존이 풀린 작업이 바로 시작됩니다. |
| `src/runner.ts` | 작업 하나를 실행합니다. 에이전트 루프는 직접 만들지 않고 `claude -p` 를 조종합니다. 워커 결과는 파이프가 아니라 파일(`~/.nod/results/<시도>.json`)로 받고 워커 PID 를 장부에 남깁니다. |
| `src/gc.ts` | 오래전에 끝난 작업의 작업 폴더·worktree·Claude 세션 폴더·결과 파일을 지웁니다. |
| `src/cli.ts` | `nod`, `nod <결정> <답>`, `nod drop`, `nod add`, `nod run`, `nod ls`, `nod show`, `nod stats`, `nod gc` |
| `scripts/bench.ts` | 동시 실행 수별 시간·메모리 측정 |

## 장부로 답하는 질문

장부 구조는 아래 질문에서 출발해 정했습니다. 새 컬럼을 더할 때도 어느 질문에 답하는지 먼저 적습니다.

| 누가 | 질문 | 데이터 | 명령 |
|---|---|---|---|
| 사람 | 지금 내가 결정할 게 뭐지? | 열린 결정, 질문, 작업 | `nod` |
| 사람 | 이 작업 지금 어디까지 됐지? | 작업 상태, 시도 수, 비용, 마지막 요약 | `nod ls` |
| 사람 | 이 작업에 무슨 일이 있었지? | 시도 이력(종류·결과·검증·세션 ID·비용), 결정과 답 | `nod show <작업>` |
| nod | PC 가 꺼졌다 켜지면 어디서 이어 가지? | 끝나지 않은 시도, 워커 PID, 결과 파일, 마지막 세션 ID | `nod run` 시작 시 자동 |
| 사람 | 이 방식이 효과가 있나? | 결정 없이 끝난 작업 수, 시도·재시도 수, 결정 대기 시간 중앙값, 비용 | `nod stats` |

결정 대기 시간(결정이 생겨서 사람이 답할 때까지)이 가장 중요한 지표입니다. 여러 에이전트를 돌리면 병목은 사람의 판단으로 옮겨 가기 때문입니다.

## 작업 흐름

```
start ─▶ 워커 결과
          ├─ succeeded ─▶ 검증 명령(--check) 없음 ─▶ 완료
          │               검증 통과 ─▶ 완료
          │               검증 실패 ─▶ 같은 세션에 실패 출력을 주고 retry (최대 2회) ─▶ 그래도 실패면 결정
          ├─ needs_decision ─▶ 결정(question)
          └─ failed ─▶ 결정(failed)
결정 ─▶ nod <결정> <답> ─▶ 다음 run 에서 같은 세션으로 answer
     └▶ nod drop <결정> ─▶ cancelled (워커를 부르지 않음)
실행기가 죽음 ─▶ 다음 run 이 끝나지 않은 시도를 회수:
               워커가 아직 돎 ─▶ 끝날 때까지 기다림 (PID 와 명령줄의 세션 ID 로 확인)
               결과 파일 있음 ─▶ 워커를 다시 부르지 않고 그 결과로 이어감
               둘 다 아님 ─▶ interrupted 로 닫고 같은 세션으로 resume
```

워커는 최소한의 맥락만 받습니다. 작업 지시 한 줄과 짧은 워커 규칙(`WORKER_PROMPT`)뿐이고, 워커끼리는 서로를 모릅니다. 결과는 `--json-schema` 로 `{ outcome, summary }` 형식을 강제해 받습니다.

## 실측으로 정한 것 (2026-10-05, Claude Code 2.1.289, MacBook 32GB·10코어)

**동시 실행.** 같은 작업(파일 하나 쓰기, haiku)을 한꺼번에 돌린 결과입니다.

| 동시 수 | 전체 시간 | 작업 평균 | 최대 메모리 | 성공 | 비용 |
|---|---|---|---|---|---|
| 8 | 11초 | 10초 | 2.3GB | 8/8 | $0.51 |
| 16 | 11초 | 11초 | 4.5GB | 16/16 | $1.01 |
| 32 | 17초 | 15초 | 8.5GB | 32/32 | $2.04 |

- 워커 하나가 약 270MB 를 씁니다. 메모리는 개수에 비례해 늘었습니다.
- 32개에서 작업 평균이 15초로 느려졌습니다. 코어 10개를 나눠 쓰기 때문으로 보입니다(추정).
- 실제 작업은 의존성 설치·테스트·dev 서버가 더해져 훨씬 무겁습니다. 실전 작업으로 다시 재야 합니다.

**worktree 동시 생성.** 한 레포에 `git worktree add` 를 32개 동시에 실행해도 실패가 없었습니다. 그래서 잠금을 두지 않았습니다.

**권한 모드.** `-p`(비대화) 실행에서 측정했습니다.

- `auto`: 파일 쓰기와 셸 명령을 모두 거부했습니다.
- `acceptEdits`: 파일 쓰기는 통과했지만 셸 명령은 거부했습니다. 그래서 기본값을 `acceptEdits` 로 두었습니다.
- `--bare` 는 구독 로그인을 쓸 수 없어서 쓰지 않습니다. 그래서 워커는 사용자 설정(훅·CLAUDE.md)을 물려받습니다.

**셸 명령 정책: 허용 목록이 아니라 샌드박스.** 테스트 실행을 허용하는 순간 워커는 어떤 코드든 실행할 수 있으므로, 명령 목록은 경계가 되지 못합니다. 대신 OS 샌드박스로 "어디에 쓸 수 있고 어디에 접속할 수 있는지"를 막습니다(`DEFAULT_SETTINGS`).

- `sandbox.enabled` + `autoAllowBashIfSandboxed`: 샌드박스 안의 셸 명령은 묻지 않고 실행됩니다.
- 작업 폴더 밖 쓰기(`~/…`)는 `operation not permitted` 로 막혔습니다.
- 네트워크는 기본으로 막히고(프록시가 403), `network.allowedDomains` 에 넣은 곳만 통과했습니다. 기본 허용은 `registry.npmjs.org` 하나입니다.
- `allowUnsandboxedCommands: false` 로 샌드박스를 끄고 다시 시도하는 탈출구를 닫았습니다.
- worktree 에서의 `git commit` 은 레포가 홈 폴더 아래에 있어도 성공했고, 전역 git 작성자 정보도 보였습니다.
- `git -c …` 처럼 설정을 덮어쓰는 명령은 권한 단계에서 거부됐습니다(설정으로 훅을 바꿔 임의 코드를 실행할 수 있기 때문으로 보입니다).
- 사용자 훅(rtk)은 명령을 `rtk …` 로 바꾼 뒤 권한을 검사합니다. 허용 목록 방식이었다면 규칙을 `Bash(rtk wc:*)` 형태로 써야 했습니다. 샌드박스 방식에서는 상관없습니다.

**Bun.spawn 과 PATH.** `env` 를 넘기지 않으면 프로세스 시작 시점의 PATH 로 명령을 찾습니다. 테스트에서 바꾼 PATH 가 무시돼 진짜 claude 가 불렸던 적이 있어, `env: process.env` 를 넘깁니다.

**끝까지 실행한 시나리오** (2026-10-06, 기본 모델, 4개 동시)

| 시나리오 | 흐름 | 결과 |
|---|---|---|
| 검증 실패 | 중단 → resume(검증 실패) → retry(통과), 세 시도 모두 같은 세션 | 통과 |
| 질문 | 질문 → 결정 → "한국어" → answer | `greeting.txt` 한국어 |
| 샌드박스 밖 쓰기 | 샌드박스가 막음 → 우회하지 않고 결정으로 | 홈 폴더 파일 안 생김 |
| git 레포 | worktree 에서 버그 수정·커밋, nod 가 `bun test` 검증 | `nod/4` 에 커밋 |

이 과정에서 두 가지를 고쳤습니다. 실행기가 결과 출력 중에 죽었을 때 resume 은 동작했지만, 그사이 고아 워커가 끝낸 결과는 잃었습니다. 그래서 결과를 파일로 받고 워커 PID 를 남기게 바꿨습니다. 이후 실제 claude 작업 도중 실행기를 `kill -9` 로 죽였더니, 다음 run 이 살아 있던 워커를 6초 기다렸다가 결과를 가져왔고 워커는 다시 불리지 않았습니다(시도 1회, 비용 1회분). 또 "취소"라고 답하면 워커가 "취소했다"며 succeeded 를 돌려줘 성공으로 집계됐습니다. 그래서 워커를 부르지 않고 끝내는 `nod drop` 과 `cancelled` 상태를 추가했습니다.

`nod stats` 의 숫자는 같은 장부를 SQL 로 직접 센 값과 모든 항목이 일치했습니다.

**결과 스키마.** zod 가 만든 JSON Schema 의 `$schema`(draft 2020-12) 키를 Claude Code 가 거부해서, 이 키를 빼고 넘깁니다.

## 계정

nod 는 실행한 셸의 Claude 로그인을 그대로 씁니다. 개인 일은 개인 계정으로 돌리려면 `CLAUDE_CONFIG_DIR=<개인 설정 폴더> nod run` 처럼 실행합니다.

## 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| M1 | 장부, 동시 실행 풀, 작업마다 `claude -p`, 벤치마크 | 완료 |
| M2 | nod 가 직접 하는 검증과 재시도, 샌드박스 권한 정책 | 완료 |
| M3 | 결정 인박스(`nod` / `nod <결정> <답>` / `nod drop`), 같은 세션 이어 하기, 중단 복구(결과 파일·PID 회수), `nod show`·`nod stats`·`nod gc` | 완료 |
| M3.5 | Claude 세션을 앞단으로: `/nod` 스킬, `nod ls --json`, `bun link` | |
| M4 | 목표를 작업 그래프로 나누는 Planner, 경로가 겹치는 작업 분리 | |
| M5 | 트리거(일정·이벤트), 입력 연결부, 알림 | |
| M6 | 실패 회고에서 나온 규칙 변경 제안을 결정으로 올리기 | |

일부러 만들지 않은 것: 웹 대시보드, 자체 에이전트 루프, 여러 PC 연동. CLI 로 부족하다는 게 확인되면 그때 만듭니다.
