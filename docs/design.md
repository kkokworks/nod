# nod 설계

nod 는 여러 에이전트를 동시에 돌려 일을 처리하고, 사람에게는 결정만 넘기는 오케스트레이터입니다. 사람은 고개만 끄덕이면(nod) 됩니다.

## 불변식

깨지면 안 되는 규칙입니다. 기능을 더할 때마다 이 다섯 가지를 지키는지 먼저 확인합니다.

1. 되돌릴 수 없는 일과 외부로 나가는 일은 사람의 결정 없이 일어나지 않습니다. 프롬프트로 부탁하지 않고 권한 설정으로 막습니다. 레포마다 사람이 미리 허락해 둔 착지(`nod repo`, 아래 「결과 올리기」)는 그 허락이 결정이고, 그 밖에 막히는 것은 결정으로 올라옵니다.
2. 모든 상태는 장부(SQLite)에 남습니다. 프로세스가 죽어도 무엇이 어디까지 됐는지 알 수 있습니다.
3. 워커가 끝났다고 보고해도 nod 가 직접 검증하기 전에는 끝난 것이 아닙니다.
4. 이슈·웹 문서처럼 밖에서 들어온 텍스트는 데이터일 뿐 지시가 아닙니다.
5. 동시에 돌면 안 되는 작업 조합(같은 파일 수정, 같은 포트)은 같이 돌리지 않습니다. 개수 자체는 제한하지 않습니다.

## 구조

```
사람 ─▶ Claude 세션(/nod 스킬) ─▶ nod CLI ─▶ 장부(~/.nod/nod.db)
                                     │            ▲
                                     ▼            │ Stop·Notification 훅
                              tmux 세션마다 Claude Code 워커 (작업 폴더 또는 worktree)
```

워커는 작업마다 nod 가 tmux 안에 띄운 실제 Claude Code 세션입니다. 화면 없는 `claude -p` 를 쓰지 않는 이유는, 한 작업 동안 같은 세션이 살아 있으면서 질문·검증 실패·후속 지시를 같은 맥락에서 이어 받게 하려는 것입니다. 이어 받을 맥락이 없는 독립 리뷰어만 `claude -p` 로 돕니다(아래 독립 리뷰). 사람은 `nod attach` 로 들어가 보거나 끼어들 수 있습니다. 상주하는 실행기는 없습니다. `nod add` 가 워커를 바로 띄우고, 워커가 멈출 때마다 Claude Code 의 훅이 `nod hook` 을 불러 장부를 갱신합니다. 앞 작업을 기다리는 작업도 앞 작업의 Stop 훅이 띄웁니다.

| 파일 | 하는 일 |
|---|---|
| `src/ledger.ts` | 장부. 작업(tasks)·시도(attempts)·결정(decisions)·작업 순서(task_deps)·회고(retros)·규칙(rules)·차례 도중 메시지(messages)·레포의 착지 권한(repos)·작업의 착지(landings)를 SQLite 에 기록합니다. 시도는 워커 세션의 한 턴이고, 시도와 메시지에는 그 말을 보낸 작업(`from_task`, 사람이면 비어 있음)이 남습니다. 스키마는 `pragma user_version` 으로 버전을 매기고, 마이그레이션은 덧붙이기만 합니다. |
| `src/tmux.ts` | 워커 터미널. nod 홈마다 tmux 서버(소켓)를 따로 두고, 작업마다 tmux 세션 하나를 둡니다. 띄우기(주어진 환경 변수만, `env -i`), 메시지 보내기(줄바꿈·탭 말고 제어 문자를 지운 붙여넣기 + Enter), 키 보내기, 화면 읽기, 닫기(일부러 끈다는 표지를 남김)를 합니다. |
| `src/worker.ts` | 워커 생명주기. 띄우기, 칸 안에서 Claude Code 를 지켜 다시 띄우기(`keepWorker`), Stop 훅 처리(보고 읽기 → 검증 → 다시 시키거나 결정 열기, 백그라운드 작업이 남았으면 기다리기, `NOD: tell` 을 다른 작업에 보내기), Notification 훅 처리(권한 확인 → 결정), 답·후속 지시를 같은 세션에 보내기, 끝난 세션을 대화 기록에서 다시 열기, 앞 작업이 끝나면 기다리던 작업 띄우기, 계정이 바뀐 워커 다시 띄우기, 칸째 사라진 차례와 너무 오래 기다린 작업을 결정으로. |
| `src/account.ts` | 워커가 쓸 계정(Claude 설정 폴더) 규칙. 기본은 띄우는 셸의 `CLAUDE_CONFIG_DIR`, 그 밖에 파일에서 읽기와 명령 출력(`<홈>/account.json`). |
| `src/triggers.ts` | 트리거. 일정 계산, source 명령의 출력에서 새 항목 고르기, 때가 된 트리거로 작업 넣기(tick), 5분마다 대기 감시와 끝난 작업 정리, OS 스케줄러에 매분 tick 등록·해제. |
| `src/notify.ts` | 결정이 열리거나 작업이 끝나는 등의 일이 생기면 사람이 둔 `<홈>/notify` 를 부릅니다. |
| `src/rules.ts` | 워커가 받는 규칙(장부의 `rules` 중 켜진 것)과, 문제가 있었던 작업의 회고 지시. |
| `src/review.ts` | 독립 리뷰어가 받는 지시. 지시와 그 뒤 사람이 한 말(차례 도중 메시지 포함), 그와 따로 다른 작업의 워커가 보낸 말, 검증 명령, 워커의 보고, 레포면 바뀐 파일 목록과 diff. |
| `src/gc.ts` | 끝난 작업의 세션을 닫고 작업 폴더·worktree 를 지웁니다. 대화 기록은 남겨 resume 으로 되살릴 수 있게 하고, 브랜치를 지우기 전 끝 커밋을 장부에 남깁니다. |
| `src/done.ts` | 끝난 작업을 정리해도 되는지 알려 주는 신호. 그만둠, 같은 할 일을 새 작업이 이어받음, 기본 브랜치에 들어감, 링크한 PR 이 모두 머지·닫힘·내 승인, 끝난 지 7일. 레포 없는 작업은 7일만 보고, 회고 작업은 끝나면 바로 정리합니다. push 안 한 커밋이 있거나, 이 작업 브랜치에서 시작할 작업이 기다리거나, 사람이 세션에 붙어 있으면 정리하지 않습니다. |
| `src/prs.ts` | 링크한 PR 의 상태와 내 마지막 승인·변경 요청을 git 서비스 CLI 로 읽습니다(GitHub 는 `gh`, Gitea·Forgejo 는 `tea api`). 착지를 허락한 레포에서는 nod 의 PR 을 찾고 열고 squash 머지합니다(`serviceOf`). nod 가 git 서비스에 묻는 유일한 곳입니다. |
| `src/land.ts` | 착지. 허락한 레포의 성공한 작업을 fetch·rebase·검증·점검·push·PR·머지로 원격 기본 브랜치에 올리고, 판단이 필요한 일은 그 작업의 워커에게, 사람만 풀 수 있는 일은 결정으로 넘깁니다. |
| `src/todos.ts` | 사람의 할 일과 프로젝트(GTD). 받아 적기, 명료화·정리, 완료, 칸마다 누가 무엇을 바꿨는지의 이력. |
| `src/days.ts` | 할 일의 날짜. 사람이 쓴 날짜 읽기, 반복할 때 다음 날짜 계산. |
| `src/calendar.ts`, `calendar/` | macOS 캘린더 읽기. `calendar/build.sh` 가 EventKit 앱을 nod 홈에 빌드하고, `calendar.ts` 가 그 앱으로 하루치 일정을 읽습니다. 쓰지는 않습니다. |
| `src/trust.ts` | 시스템을 믿어도 되는지의 숫자. 장부에서 읽은 값만 받는 순수 함수와, 하루 첫 세션 알림 한 줄. |
| `src/todo-cli.ts` | `nod in`, `nod todo`(`check` 포함), `nod project`, `nod today` |
| `ui/` | 이 컴퓨터에서만 여는 웹 화면. 작업·결정 화면(`nod.server.ts`)과 할 일 화면(`todos.server.ts`, `todo-fns.ts`)이 같은 장부 연결을 씁니다. |
| `desktop/` | macOS 데스크톱 앱(Tauri). 화면 서버를 창에 띄우는 껍데기와 메뉴·전역 단축키·받아 적기 창(`src-tauri/src/main.rs`, `src/`), 화면 서버를 로그인할 때 띄우는 launchd 설정(`launchd/`). |
| `src/cli.ts` | `nod`, `nod <결정> <답>`, `nod drop`, `nod add`, `nod tell`, `nod resume`, `nod attach`, `nod watch`, `nod ls`, `nod show`, `nod stats`, `nod gc`, `nod trigger add·ls·rm`, `nod rule ls·add·edit·off·on`, `nod repo`, `nod land`, `nod tick`, `nod restart`, `nod account`, `nod hook`, `nod run` |
| `skills/nod/SKILL.md` | Claude 세션을 앞단으로 만드는 스킬입니다. 요청을 작업으로 나눠 넣고, `nod watch` 를 Monitor 로 걸어 결정을 바로 전합니다. 결정은 대신 내리지 않습니다. |

## 장부로 답하는 질문

장부 구조는 아래 질문에서 출발해 정했습니다. 새 컬럼을 더할 때도 어느 질문에 답하는지 먼저 적습니다.

| 누가 | 질문 | 데이터 | 명령 |
|---|---|---|---|
| 사람 | 지금 내가 결정할 게 뭐지? | 열린 결정, 질문, 작업 | `nod` |
| 사람 | 일하는 중에 결정할 게 새로 생겼나? | 새로 열린 결정 | `nod watch` (Claude 세션이 알림으로 받음) |
| 사람 | 이 작업 지금 어디까지 됐지? | 작업 상태, 턴 수, 마지막 보고, 세션이 살아 있는지 | `nod ls` |
| 사람 | 이 작업에 무슨 일이 있었지? | 턴 이력(종류·결과·검증·세션 ID), 결정과 답 | `nod show <작업>` |
| nod | 이 훅은 어느 작업의 것이지? | 시도의 세션 ID | `nod hook` |
| nod | 이 작업은 지금 띄울 수 있나? | 작업 순서, 앞 작업들의 상태 | `nod hook`, `nod add --after` |
| 사람 | 이 작업은 무엇을 기다리지? | 작업 순서 | `nod ls`, `nod show <작업>` |
| 사람 | 세션이 끊긴 작업을 어디서 이어 가지? | 마지막 세션 ID (Claude Code 가 대화 기록을 가짐) | `nod resume <작업>` |
| 사람 | 이 방식이 효과가 있나? | 결정 없이 끝난 작업 수, 턴·재시도 수, 결정 대기 시간 중앙값 | `nod stats` |
| nod | 지금 돌릴 트리거가 있나? | 트리거의 일정, 마지막 실행 시각 | `nod tick` |
| nod | 이 항목은 이미 작업이 됐나? | 트리거가 본 항목과 그 작업 | `nod tick` |
| 사람 | 이 작업은 어디서 왔지? 트리거가 왜 안 돌지? | 작업을 넣은 트리거, 마지막 실행의 오류 | `nod show`, `nod trigger ls` |
| nod | 이 작업을 회고할까? | 재시도 턴, failed·check_failed 결정, 이미 있는 회고 | `nod hook`, `nod drop` |
| 사람 | 이 규칙은 어디서 나왔지? 버린 제안은 뭐였지? | 회고(`retros`): 돌아본 작업, 제안한 규칙, 넣음·버림·제안 없음·할 일로 보냄, 정한 시각 | `nod show r<n>`, `nod ls --all` 의 `r<n>`, `nod rule ls` |
| 사람 | 워커가 받는 규칙은 뭐지? 누가 언제 바꿨지? | 규칙(`rules`): 내용, 만든 회고, 켜짐·꺼짐, 만든·바꾼 시각. 바꾼 이력(`rule_changes`): 누가, 무엇을, 언제 | `nod rule ls`, `nod show r<n>` |
| 사람 | 이 작업의 결과는 어디로 갔지? 아직 안 내보낸 건 뭐지? | 작업의 링크(PR·게시한 리뷰 주소), 링크 전에는 작업 브랜치를 품은 원격 브랜치 | `nod link`, `nod ls`, `nod show <작업>` |
| 사람 | 아직 손볼 작업은 뭐지? | gc 한 시각(`collected_at`) | `nod ls` (gc 한 작업은 `--all` 로만) |
| 루트 세션 | 내가 맡긴 작업은 뭐고, 그 결정은 뭐지? | 작업을 맡긴 Claude 세션(`root_session`) | `nod ls --mine`, `nod watch --mine` |
| 사람 | 이 작업을 맡긴 세션은 어디서 다시 열지? | 루트 세션 ID 전체 | `nod show <작업>`, 웹 화면의 작업 상세 |
| nod | 이 워커는 지금 계정으로 떠 있나? | 워커의 Claude Code 가 뜬 계정(`tasks.account`) | `nod tick`, 모든 nod 명령, `nod show <작업>` |
| nod | 이 워커는 백그라운드 작업을 기다리나? 너무 오래 기다렸나? | 기다린 차례(`attempts.outcome = 'waiting'`)와 그 차례가 끝난 시각 | `nod hook`, `nod tick` |
| 사람·리뷰어 | 이 말은 사람이 했나, 다른 작업의 워커가 보냈나? | 시도·메시지를 보낸 작업(`from_task`) | `nod show <작업>`, 독립 리뷰 |
| nod | 두 작업의 워커가 서로 몇 번 말을 보냈지? | 두 작업 사이의 `from_task` 가 있는 시도·메시지 수 | `nod hook` |
| 사람 | 이 레포에서 nod 가 어디까지 해도 되지? 누가 언제 바꿨지? | 레포의 착지 단계·검증 명령·점검(`repos`), 바꾼 이력(`repo_changes`) | `nod repo <경로>` |
| 사람 | 이 작업의 결과는 어디까지 올라갔지? 무엇을 기다리지? | 작업의 착지(`landings`): 자기 일의 시작, 검증을 통과한 head, push 한 커밋, PR, 머지한 시각, 멈춘 이유, 기다리는 것 | `nod ls`, `nod show <작업>` |
| nod | 이 레포를 지금 다른 프로세스가 올리고 있나? | 레포를 차지한 pid(`repos.lander`) | `nod land`, `nod tick` |
| nod | 이 차례는 착지 일인가? 지금 worktree 를 nod 가 만지고 있나? | 워커에게 착지 일을 넘긴 시각(`landings.handed_at`), worktree 를 쓰는 pid(`landings.busy`) | `nod hook`, `nod tell` |

`succeeded` 는 워커가 자기 몫을 끝냈다는 뜻이지, 결과가 머지됐다는 뜻이 아닙니다. 레포가 착지를 허락하지 않았으면 결과를 내보내는 일은 루트 세션이 nod 밖에서 하므로, nod 는 머지 여부를 직접 확인하지 않고 결과가 간 곳의 주소만 기록합니다(허락한 레포는 아래 「결과 올리기」). 머지를 기준으로 작업을 닫지 않는 이유는 세 가지입니다. 결과가 PR 이 아닌 작업이 있고, 작업과 PR 이 1:1 이 아니며, 코어가 특정 git 서비스에 묶이기 때문입니다. 링크를 달기 전에는 작업 브랜치의 끝 커밋을 품은 원격 브랜치를 git 으로 찾아 보여 줍니다(`pushed`). 다른 세션이 다른 이름으로 push 해도 찾을 수 있고, nod 는 착지할 때 말고는 fetch 하지 않으므로 마지막 fetch 기준입니다. 이 브랜치를 PR 주소로 바꿔 링크하는 일은 스킬이 git 서비스 CLI 로 합니다. 대신 사람이 결과를 다 처리했다고 gc 하면, 그 시각을 남기고 `nod ls` 에서 뺍니다.

처음에는 gc 가 Claude 세션 폴더도 지워서 그 뒤에는 resume 할 수 없었고, 그래서 사람이 리뷰가 끝난 것을 보고 손으로 gc 했습니다. 손으로 하다 보니 끝난 작업이 `nod ls` 에 쌓였습니다(2026-10-22). 지금은 gc 가 대화 기록을 남기고, resume·tell 이 같은 경로에 worktree 를 다시 만들어 그 기록으로 세션을 엽니다. Claude Code 는 작업 폴더 경로로 세션을 찾기 때문입니다. 기록이 남았는지는 nod 가 `projects/` 아래 폴더들에서 세션 ID 로 찾습니다. 폴더 이름은 Claude Code 가 경로로 짓는 내부 규칙이라(2.1.309: 글자·숫자가 아닌 것은 모두 `-`, 200자를 넘으면 해시를 붙임), 따라 지었더니 경로에 `_`·공백·한글이 든 작업의 기록을 못 찾고 첫 지시를 다시 보냈습니다. 브랜치가 지워졌으면 gc 때 남긴 끝 커밋, 원격 브랜치, 원격 기본 브랜치 순으로 다시 만듭니다. 잘못 정리해도 worktree 를 다시 만드는 비용뿐이라, 이름 없이 부른 `nod gc` 와 5분마다 도는 tick 이 완료 신호를 보고 스스로 정리합니다(`src/done.ts`). 신호는 작업마다 다릅니다. 남의 PR 리뷰는 작업을 넣은 뒤 내가 승인했을 때입니다. 앞 차례에 남긴 승인으로 다음 차례 리뷰가 끝나면 안 되기 때문입니다. 내 PR 을 만드는 작업은 PR 이 머지·닫히거나 브랜치 내용이 기본 브랜치에 들어갔을 때입니다. 링크한 PR 이 여럿이면 모두 끝나야 합니다. 그만둔 작업, 같은 할 일을 새 작업이 이어받은 작업, 끝난 지 7일이 지난 작업도 정리합니다. 레포 없는 작업은 폴더의 파일이 곧 결과물이고 되살려도 돌아오지 않으므로, 끝난 지 7일이라는 신호만 봅니다. 회고 작업은 예외로, 결과가 장부(`retros`)에 남으므로 규칙을 넣거나 버리거나 제안이 없거나 할 일로 보냈으면 바로 정리합니다. 장부와 git 으로 알 수 있는 신호를 먼저 보고, PR 상태는 그다음에 git 서비스 CLI 로 읽습니다. 위에서 코어가 git 서비스에 묶이는 것을 피했는데, 이 읽기는(착지의 쓰기도) `src/prs.ts` 한 곳에 두고 CLI 가 없거나 실패하면 그 작업을 정리하지 않고 넘어가는 것으로 타협했습니다. 7일 신호는 PR 상태를 읽기 전에 보므로, PR 을 읽지 못하는 작업도 7일이 지나면 정리됩니다. push 하지 않은 커밋이 있는 작업은 어떤 신호가 와도 정리하지 않습니다. 브랜치는 남지만 작업이 `nod ls` 에서 사라지면 push 할 일을 잊기 때문입니다. 이 작업 뒤에 기다리는 작업이 있어도 정리하지 않습니다. 그 작업이 이 작업의 브랜치에서 시작하는데, 정리하면 브랜치가 지워지기 때문입니다. `nod gc --older-than` 도 같은 이유로 이런 작업을 고르지 않습니다. 사람이 `nod attach` 로 붙어 있는 세션도 건너뜁니다. 사람이 시킨 일은 끝날 때까지 상태가 `succeeded` 로 남아, 정리하면 일하는 도중에 세션이 닫히기 때문입니다. 신호를 읽는 동안이나 앞 작업의 세션이 닫히기를 기다리는 동안 `nod tell` 로 작업이 다시 돌거나 사람이 붙을 수 있으므로, gc 는 작업에 이를 때마다 장부를 다시 읽고 붙어 있는지도 다시 봅니다. 이름을 대거나 `--older-than` 으로 부른 gc 도 같습니다. 세션을 닫고 worktree 를 확인한 뒤 지우기 직전에 장부를 한 번 더 읽고, 지운 다음에는 처음 읽은 그대로(상태·끝난 시각·gc 한 시각)일 때만 한 문장(조건부 UPDATE)으로 gc 한 시각을 찍습니다. 찍은 뒤 브랜치나 빈 폴더를 지우다 실패하면 다시 목록에 올려, 다음 gc 가 마저 합니다. 그사이 `nod tell` 로 다시 돈 작업은 지우지 않고, 지우는 그 순간에 다시 돈 작업도 `nod ls` 에 남고 브랜치도 남습니다. 다만 그 작업의 폴더는 이미 지워집니다. 막으려면 `restore` 가 gc 를 기다려야 합니다. 이름 없는 gc 는 신호를 읽은 때의 작업과 비교하므로, 그사이 다시 돌고 끝난 작업(push 하지 않은 커밋을 남겼을 수 있음)은 다음 판정을 기다립니다. 세션을 닫기 전에 gc 한 시각을 찍어 정리할 몫을 미리 차지하는 안도 있었지만 택하지 않았습니다. gc 가 도중에 끝나면(Ctrl-C, tick 이 죽음 등) 지우지 못한 작업이 `nod ls` 에서 영영 빠지기 때문입니다. 다만 사람이 붙어서 직접 친 턴은 끝날 때까지 장부에 남지 않으므로, 턴 도중에 사람이 나가면 그 턴은 지키지 못합니다. 실패한(error) 작업도 사람이 보도록 남깁니다.

결정 대기 시간(결정이 생겨서 사람이 답할 때까지)이 가장 중요한 지표입니다. 여러 에이전트를 돌리면 병목은 사람의 판단으로 옮겨 가기 때문입니다. 어느 차례도 기다리지 않던 결정, 곧 nod 가 스스로 닫은 결정(워커가 답 없이 이어 감, 차례가 끊김 등)과 끝난 작업에 남은 결정을 사람이 닫은 것은 `answered_at` 을 비워 두고 이 지표에서 뺍니다. `nod show` 에는 `closed: <답>` 으로 보입니다. 이 구분 전에 nod 가 닫아 `answered_at` 이 채워진 결정은 그대로 지표에 남습니다. 대화형 세션은 비용을 알려 주지 않아서, 지금은 비용을 기록하지 않습니다(`claude -p` 시절 시도에만 남아 있음).

## 작업 흐름

```

   ├─ 점검(--gate) 실패 ─▶ 결정(check_failed), 답은 워커에게
   ├─ push·PR·머지가 막힘 ─▶ 결정(land): yes 다시 시도, 그 밖 착지 멈춤 (drop 도 착지만 멈춤)
   └─ 점검 통과 ─▶ push --force-with-lease ─▶ PR (link) ─▶ merge 단계면 squash 머지 ─▶ 다음 sweep 이 gc
```

워커는 최소한의 맥락만 받습니다. 작업 지시와 짧은 워커 규칙(`WORKER_PROMPT`, 레포 작업이면 서브 에이전트 리뷰 규칙과 첫 메시지의 브랜치 시작 커밋까지)뿐이고, 워커끼리는 서로를 모릅니다. 다만 지시에 다른 작업의 번호가 있으면 같은 세션이 맡긴 그 작업에 `NOD: tell` 로 말을 보낼 수 있습니다(아래 「워커끼리 말하기」). 사람이 워커 화면에 직접 입력한 턴도, 백그라운드 서브 에이전트가 끝나 Claude Code 가 저절로 이어 간 턴도 훅이 받아 `followup` 시도로 기록합니다. 이때 워커가 그 앞에서 물었던 결정(question·failed·check_failed·interrupted)은 답 없이 지나갔으므로 `(it went on without an answer)` 로 닫고 알림(`answered`)을 보냅니다. 처음에는 열린 채 남아, 작업이 성공한 뒤에도 질문 네 개가 열려 있었고 웹 화면은 그 작업에 지시를 보내지 못했습니다. `nod tell`·답·resume 이 새 차례를 열 때도 같고, 워커가 나중 차례 끝에 다시 물으면 앞의 것을 닫고 새 것만 남기며, 작업이 성공하면 남은 결정을 종류와 상관없이 모두 닫습니다. 권한·신뢰·규칙 결정은 이 규칙으로 닫지 않습니다. 권한 결정은 그 차례가 끝날 때(칸이 사라진 차례를 메시지가 닫을 때도 `(the turn was cut off)` 로), 규칙 결정은 새 제안이 올 때 닫히고, 작업을 drop 하면 그 작업의 다른 결정도 함께 닫힙니다. 이렇게 nod 가 닫을 때, 작업 상태는 워커가 그 결정을 지나 이어 가는 경우(스스로 이어 간 차례, 칸에서 직접 답한 권한 확인)에만 결정 대기에서 실행 중으로 돌리고, 끝난 작업은 건드리지 않습니다. 이미 끝난 작업(succeeded·cancelled, 결과가 정해진 회고)에 열린 채 남은 결정은 사람이 답하거나 drop 하면 결정만 닫고, 새 차례를 띄우거나 작업 상태를 바꾸지 않습니다. 처음에는 답하면 끝난 워커가 다시 돌았고, drop 하면 성공한 작업이 취소로 바뀌었습니다.

## 작업 순서 (M4)

계획은 루트 세션이 세웁니다. 사용자의 맥락을 가진 쪽이 루트 세션이기 때문입니다. nod 는 그 계획을 지키는 장치만 둡니다.

- **잇기.** `nod add --after 3,4` 로 넣은 작업은 대기(queued)하다가, 앞 작업이 모두 성공하는 순간 마지막으로 성공한 작업의 Stop 훅이 띄웁니다. 두 워커가 동시에 끝나도 한 번만 뜨도록, 띄울 작업을 고르고 running 으로 바꾸는 일을 SQL 문장 하나로 합니다.
- **같은 레포는 이어 쌓기.** 처음에는 "경로가 겹치는 작업을 떼어 놓기"를 계획했습니다. 그런데 워커마다 worktree 가 따로 있어서 실행 중에 파일이 겹칠 일은 없고, 진짜 문제는 나중에 브랜치를 합칠 때의 충돌입니다. 그래서 같은 레포에서 이어지는 작업은 앞 작업의 브랜치에서 worktree 를 만듭니다. 한 레포 안에서는 앞 작업을 하나만 둘 수 있습니다. 두 갈래를 nod 가 합치면 merge commit 이 생기고, 충돌이 나면 어느 쪽을 살릴지 판단해야 하기 때문입니다.
- **브랜치와 worktree 에 이름.** 처음에는 `nod/<작업>` 브랜치와 `<홈>/work/<작업>` 폴더를 썼는데, 번호만으로는 무슨 일인지 알 수 없었습니다. 그래서 레포 작업은 `--branch` 로 이름을 받고, worktree 를 `<홈>/work/<레포 폴더 이름>/<브랜치>` 에 둡니다. 브랜치 이름이 겹치지 않으면 폴더도 겹치지 않습니다. worktree 를 레포 옆에 두는 안도 있었지만, gc 의 「`<홈>/work` 밖은 지우지 않는다」는 안전장치를 풀어야 해서 택하지 않았습니다.
- **gc 의 브랜치 정리.** 브랜치는 원격 브랜치가 그 커밋을 갖고 있을 때 지웁니다. squash 머지 뒤 원격 브랜치를 지우면 커밋을 가진 원격 브랜치가 남지 않으므로, 원격 기본 브랜치가 그 브랜치가 바꾼 파일을 같은 내용으로 갖고 있어도 머지된 것으로 봅니다. 둘 다 아니면 브랜치가 유일한 사본이라 남깁니다. 바꾼 파일 이름은 `git diff -z` 로 받아 패턴이 아닌 이름 그대로(`--literal-pathspecs`) 비교합니다. 처음에는 줄 단위로 받았는데, git 이 ASCII 가 아닌 이름(`기획.md` 등)을 따옴표와 8진수로 내보내 어떤 파일과도 맞지 않았고, 그래서 push 하지 않은 브랜치가 머지된 것으로 보였습니다(2026-10-23). 뜨지 않은 작업은 제 브랜치가 없으므로, 그 이름의 브랜치를 판정하지도 지우지도 않습니다. 사람의 기존 브랜치를 `--branch` 로 준 대기 작업이 앞 작업과 함께 취소되거나, 이미 있는 브랜치라 `worktree add -b` 가 실패한 작업이 그렇습니다. `worktree add -b` 는 됐는데 서브모듈을 채우지 못해 시작에 실패한 작업은 그 자리에서 만든 worktree 와 브랜치(아직 커밋이 없음)를 지웁니다. 남겨 두면 작업 폴더가 장부에 없어서 gc 가 끝내 지우지 못하고, 같은 브랜치 이름으로 다시 시작할 수도 없기 때문입니다.
- **gc 가 worktree 를 지우기 전.** 커밋 안 된 변경은 레포 설정이 status 에서 숨기라고 한 서브모듈(`ignore`)의 것까지 봅니다(`--ignore-submodules=none`). 커밋 안 된 변경이 없어도 worktree 에만 있는 커밋이 있으면 남기고 이유를 보여 줍니다. worktree HEAD 에 작업 브랜치에 없는 커밋이 있을 때(분리된 HEAD 에서 만든 커밋 등)와, 서브모듈의 커밋(HEAD 뿐 아니라 그 서브모듈의 로컬 브랜치·태그·stash 도)이 원격 브랜치에도, 레포의 원래 체크아웃에 있는 그 서브모듈에도 없을 때입니다. 서브모듈은 `.gitmodules` 가 아니라 worktree 의 git 폴더(`modules`)에서 찾으므로, 커밋을 남긴 뒤 worktree 에서 빼낸 서브모듈도 봅니다. `worktree remove --force` 가 worktree 의 서브모듈 복제본(`.git/worktrees/<worktree>/modules/<서브모듈>`)까지 지우므로, 바깥 레포의 브랜치만 push 하면 서브모듈 커밋이 어디에도 남지 않기 때문입니다. 원래 체크아웃도 사본으로 치는 것은, worktree 의 서브모듈이 거기서 복제돼 그쪽 브랜치만 원격 브랜치로 보이기 때문입니다. 그쪽 브랜치가 고정된 커밋보다 뒤에 있는 흔한 경우에도 지울 수 있게 하려는 것입니다.
- **커밋 확인.** 이어 쌓으려면 앞 작업이 커밋을 남겨야 합니다. 그래서 레포 작업은 검증 명령이 통과해도 커밋하지 않은 변경이 있으면 같은 턴으로 돌려보냅니다. `nod gc` 도 커밋만 남기므로 원래 필요한 확인이었습니다.
- **앞 작업의 보고 전달.** 뒤 작업의 첫 메시지에 앞 작업들의 지시와 보고 한 줄을 덧붙입니다. 워커는 첫 메시지 밖의 것을 모르기 때문입니다.
- **앞 작업이 끝나지 못하면.** 사람이 drop 해서 cancelled 가 되면 기다리던 작업도 연쇄로 cancelled 가 됩니다. error 는 `nod resume` 으로 살릴 수 있어서 뒤 작업을 그대로 기다리게 둡니다.

**실측 (2026-10-06, Claude Code 2.1.290, haiku).** 처음 보는 레포에 작업 1(hello.txt 만들기)과 작업 2(`--after 1`, 내용 바꾸기)를 넣었습니다.

|---|---|
| 처음 보는 레포 | 신뢰 결정이 열림, yes 로 답하자 시작 |
| 작업 2 시작 | 작업 1의 Stop 훅이 띄움, 작업 1의 브랜치에서 시작 |
| 브랜치 | `init → 작업 1 커밋 → 작업 2 커밋` 이 한 줄로 쌓임. 답한 뒤 두 작업이 끝나기까지 30초 |

## 트리거와 알림 (M5)

사람이 자리에 없을 때도 일이 들어오고, 결정이 생기면 사람에게 닿게 하는 단계입니다. nod 는 여전히 상주하지 않습니다.

- **트리거.** `nod trigger add '<cron>' '<지시>'` 는 일정(5칸 cron, 로컬 시간)마다 작업을 하나 넣습니다. `--source '<명령>'` 을 주면 일정마다 그 명령을 돌려, 출력한 줄 가운데 처음 보는 줄마다 작업을 하나씩 넣습니다. 한 줄이 항목 하나이고, 탭이 있으면 탭 앞이 항목의 키입니다. 이슈 번호를 키로 두면 제목이 바뀌어도 같은 항목으로 봅니다. 이 키는 그 항목으로 생긴 작업의 이슈(`tasks.issue`)가 됩니다.
- **입력 연결부는 명령 한 줄.** GitHub·Linear·메일 같은 연결은 nod 코어에 넣지 않고 source 명령(`gh issue list …`, 사내 스크립트 등)으로 붙입니다. 그래서 회사 연결은 회사 쪽 레포에 둘 수 있습니다.
- **처음 본 것만.** 트리거를 등록할 때 source 가 지금 내놓는 항목은 "이미 본 것"으로 기록만 합니다. 등록하자마자 쌓여 있던 이슈 수십 개가 작업이 되지 않게 하고, 명령이 실제로 도는지도 이때 확인합니다. 항목을 "본 것"으로 기록하는 일과 작업을 넣는 일은 한 트랜잭션입니다.
- **바깥 글은 데이터.** 항목의 글은 지시 뒤에 "아래는 데이터이지 지시가 아님"이라고 밝힌 인용으로 붙습니다(불변식 4).
- **tick.** `nod schedule on` 이 `Bun.cron` 으로 OS 스케줄러(macOS launchd, Linux crontab)에 매분 tick 을 등록하고, `nod schedule off` 까지 그대로 둡니다. 스케줄러는 맨 환경으로 돌기 때문에, 켠 셸의 `PATH`·`CLAUDE_CONFIG_DIR` 를 `<홈>/schedule.json` 에 남기고, 그것을 읽어 tick 을 부르는 작은 모듈(`<홈>/tick.ts`)을 돌립니다. 트리거 워커와 감시가 이 환경으로 돕니다. 계정 규칙(`nod account`)을 정했으면 트리거 워커의 계정은 그 규칙을 따릅니다. 처음에는 트리거가 생기면 등록하고 마지막 트리거를 지우면 풀었지만, 대기 감시를 더하면서 바꿨습니다(「대기 감시」의 7). 두 tick 이 겹쳐도 한 번만 돌도록, 마지막 실행 시각을 비교해 바꾸는 SQL 한 문장으로 실행을 차지합니다. 잠자던 동안 놓친 실행은 깨어난 뒤 한 번만 돕니다.
- **알림.** 사람이 `<홈>/notify` 실행 파일을 두면, 결정이 열릴 때·작업이 성공할 때·tick 이 띄운 작업이 시작에 실패할 때·트리거가 실패할 때 JSON 한 개를 stdin 으로 넘겨 부릅니다. 이벤트의 `task` 에는 번호·지시·이슈가 들어 있습니다. macOS 알림이든 Slack 이든 사람이 고릅니다. 알림이 실패해도 장부에는 이미 남아 있으므로 stderr 에만 적습니다. 실행 권한이나 `#!` 줄이 없어 아예 뜨지 않는 것(EACCES·ENOEXEC)도 같습니다. 전에는 이 오류가 부른 쪽으로 퍼져, 답을 적고도 워커에 보내지 못하거나 성공한 작업이 오류로 바뀌거나 tick 이 나머지 일을 건너뛰었습니다(리뷰에서 재현). 알림은 10초까지 기다리고, 감시처럼 자기 프로세스 그룹에서 돌아 시간이 지나면 스크립트가 띄운 자식까지 끝냅니다(전에는 스크립트만 끝내서, 남은 자식이 stderr 를 쥐고 있는 동안 기다렸습니다: 10초 제한에 30초). 제때 끝난 스크립트가 백그라운드로 남긴 것(`curl … &`)은 0.5초 뒤 출력을 놓고 기다리지도 끝내지도 않습니다. 놓은 뒤에 출력에 써도 그 프로세스는 죽지 않습니다. Bun 이 SIGPIPE 를 무시로 두고 자식이 그것을 물려받기 때문입니다(실측: nod 가 내려간 뒤 쓴 프로세스도 끝까지 돎). 처음 고친 판은 그것까지 10초를 기다린 뒤 끝내서, 알림마다 훅과 tick 을 붙잡았습니다(리뷰에서 재현).
- **일부러 미룬 것.** source 가 한 번에 새 항목을 많이 내놓아도 항목마다 워커가 뜹니다. 남이 항목을 만들 수 있는 source 라면 상한이나 승인 단계를 붙일 자리입니다.

**실측.** Bun 1.3.14 의 `Bun.cron.parse` 는 `tz` 옵션이나 `TZ` 환경변수와 관계없이 모든 일정을 UTC 로 읽었습니다("0 9 * * *" 의 다음 실행이 한국 시간 18시). 그래서 로컬 시각을 UTC 인 것처럼 넣고 결과를 되돌려 씁니다. 되돌릴 때는 시작 시각이 아니라 결과 시각의 시차를 씁니다. 처음에는 시작 시각의 시차를 써서, 서머타임이 끝나는 날 매일 9시 트리거가 8시와 9시에 두 번 돌았습니다(리뷰에서 `TZ=America/New_York` 로 재현). 지금은 하루 한 번인 일정은 그 시각에 한 번 돕니다. 그날 없는 시각(시계가 2시에서 3시로 건너뛰는 날의 2시 30분)은 시계가 건너뛴 만큼(대부분 한 시간) 뒤에 돕니다. 두 번 오는 한 시간은 한 번만 쳐서, 한 시간마다이거나 더 자주 도는 일정은 그 한 시간 동안 쉽니다(`0 * * * *` 는 두 번째 1시를 건너뜁니다).

끝까지 돌린 시나리오(2026-10-06, macOS, haiku): 파일을 `cat` 하는 source 트리거를 `* * * * *` 로 등록하고 파일에 한 줄을 더했습니다.

|---|---|
| 등록 | launchd 에 `bun.cron.nod-tick-<홈 ID>` 가 올라감. 그때 비어 있던 source 는 "0개를 이미 봄"으로 기록 |
| 실행 | 15:29:55 에 한 줄 추가 → 15:30 tick 이 작업을 넣고 워커를 띄움 → 15:30:17 검증 통과. launchd 에서 띄운 워커도 Claude 로그인을 그대로 씀 |

## 회고와 규칙 (M6)

같은 실패가 되풀이되지 않게, 문제가 있었던 작업에서 규칙을 뽑아 사람이 받아들인 것만 모든 워커에 줍니다.

- **언제 회고하나.** 검증이 워커를 되돌려 보낸 적이 있거나(재시도 턴), 워커가 포기했거나(failed), 재시도를 다 써도 검증이 실패한(check_failed) 작업이 끝날 때입니다. 끝난다는 것은 성공했거나 사람이 drop 한 것입니다. 질문·권한·신뢰는 평범한 결정이라 회고하지 않습니다. 한 작업에 회고는 한 번이고, 회고 작업은 다시 회고하지 않습니다.
- **회고 기록.** 회고는 사람의 할 일이 아니라 nod 가 스스로 돌아본 기록이라, 할 일(`todos`)과 따로 `retros` 테이블에 둡니다(장부 v16). 한 줄에 돌아본 작업(`of_task_id`, 작업마다 하나), 제안한 규칙(`rule`), 결과(`outcome`: 넣음 `added` · 버림 `declined` · 제안 없음 `none` · 제안 전에 그만둠 `dropped` · 규칙 대신 할 일로 보냄 `todo`), 만든 시각과 끝난 시각이 남습니다. 회고를 하는 작업은 할 일을 맡은 작업이 `todo_id` 로 할 일을 가리키듯 `retro_id` 로 회고를 가리키고, `nod ls`·`nod show`·결정 줄에 `t<n>` 자리에 `r<n>` 으로 보입니다. v16 전의 회고는 `tasks.retro_of` 와 규칙 결정에서 옮겨 왔고, `retro_of` 칸은 SQLite 가 외래 키가 걸린 칸을 지우지 못해 쓰지 않은 채 남아 있습니다.
- **회고 워커.** 회고 하나에 작업 하나가 돌고, 빈 폴더에서 같은 모델로 돕니다. 첫 메시지에는 그 작업의 지시·레포·검증 명령·턴(결과, 보고, 검증 출력)·결정과 답, 그리고 워커가 이미 받는 규칙 전부가 데이터로 들어갑니다. nod 가 하는 일 두 가지도 알려 줍니다. 워커가 done 을 보고하면 검증 명령이 워커 샌드박스 밖에서 돌고 이어서 독립 리뷰가 보며, 실패하면 재시도로 돌아간다는 것, 받아들인 규칙은 앞으로 모든 작업의 모든 워커 프롬프트에 붙는다는 것입니다. 원래 작업의 대화나 루트 세션의 맥락은 받지 않습니다. 회고는 먼저 문제가 드러난 턴이나 결정을 짚고, 고칠 곳을 가려 제안을 하나까지 냅니다(아래 「고칠 곳 가르기」).
- **고칠 곳 가르기 (2026-10-25).** 지금의 nod 안에서 워커가 일하는 도중에 달리 판단해야 했던 것이면, 다른 작업에도 쓸 만한 규칙 한 줄을 보고합니다. nod 자체(버그, 워커에게 알려 주지 않는 것)나 작업의 레포·검증 명령(그 실수를 잡을 검사)을 고칠 일이면 규칙을 내지 않습니다. 대신 무엇을 왜 고칠지 `NOD: in` 한 줄로 사람의 받은 일함에 넣고 `none` 을 보고하며, 회고 결과는 `todo` 로 남습니다. 둘 다 아니면 `none` 입니다. 전에는 회고가 낼 수 있는 것이 모든 워커에 붙는 규칙 한 줄뿐이었습니다. 그래서 원인을 nod 쪽으로 맞게 짚은 회고도 워커가 그 원인을 피해 가는 규칙을 냈고, 사람이 버렸습니다. 한 번은 워커가 일하는 사이에 보낸 메시지를 nod 가 기록하지 못한 버그였고, 한 번은 워커가 샌드박스 때문에 돌리지 못한 시험이었는데 그 시험은 샌드박스 밖에서 도는 검증 명령이 이미 돌리고 있었습니다. 앞의 것은 이제 할 일로 가고, 뒤의 것은 검증 명령이 샌드박스 밖에서 돈다는 사실을 알면 규칙을 낼 까닭이 없습니다. 고칠 곳을 문제의 종류로 가르고, 규칙 파일에 한 줄 더하기보다 검사나 환경을 고치라는 생각은 [retro 스킬](https://github.com/appsoftwareltd/mattpocock-skills)에서 왔습니다. 그 스킬은 줄마다 모든 세션에 실리는 지시 파일(AGENTS.md)을 아껴 쓰고, 기계적인 실수는 검사가 잡게 하라고 합니다. nod 의 규칙도 모든 워커의 매 차례에 실리므로 같은 사정입니다. 규칙과 `NOD: in` 을 함께 낸 회고의 할 일은 규칙 결정을 열 때 바로 넣습니다. 전에는 규칙 결정을 열고 바로 돌아가서 할 일이 버려졌습니다.
- **일부러 하지 않은 것 (고칠 곳 가르기).** 리뷰어가 diff 로 잡을 수 있었던 실수를 리뷰 기준으로 따로 두는 길(참고 스킬이 가장 앞세우는 생각)은 택하지 않았습니다. 규칙에 종류 칸을 더해야 하고, 독립 리뷰가 넓어지면 실패할 때마다 재시도를 써서 「서브 에이전트 리뷰」에서 버그 찾기를 독립 리뷰 밖으로 옮긴 결정과 어긋납니다. 회고가 이미 있는 규칙을 끄자고 제안하는 가지치기도 하지 않았습니다. 회고는 작업 하나만 보므로 규칙이 쓸모없어졌는지 알 수 없고, 참고 스킬도 이 부분을 약점으로 꼽습니다. 회고에게 원래 작업의 대화 기록을 주는 것도 하지 않았습니다. 지금까지의 회고는 기록이 모자라서가 아니라 낼 곳이 없어서 빗나갔습니다.
- **결정.** 제안은 결정(rule)이 되고, 사람이 yes 라고 답하면 장부의 `rules` 테이블에 규칙 한 줄이 들어가 그 회고(`retro_id`)와 이어집니다. 그 밖의 답이면 버립니다. 들어가는 문구는 그 결정이 걸린 차례의 보고(`attempts.summary`)이고, 회고의 `rule` 칸도 그 문구로 맞춥니다. 회고에 `nod tell` 로 다시 제안하게 하면 새 결정이 열리면서 앞의 열린 규칙 결정은 `(a newer proposal replaced it)` 로 닫힙니다. 결과(`outcome`)가 정해진 회고에 남은 결정은 yes 든 그 밖의 답이든 결정만 닫고 규칙과 결과는 그대로 두며, 끝난 회고에는 새 차례도 열지 않습니다. 끝난 회고의 차례가 멈춰도(drop 하는 사이 Stop 훅이 돌던 차례, 사람이 칸에 직접 입력한 차례) 훅은 그 차례를 기록만 하고 결과·제안·작업 상태를 바꾸거나 결정을 열지 않습니다. 취소된 작업도 같습니다. 처음에는 훅만 이를 확인하지 않아, 끝난 회고가 결정 대기로 돌아가고 아무도 닫을 수 없는 규칙 결정이 열렸습니다. 다시 제안하는 차례가 도는 동안에는 앞 결정에 yes 를 받지 않고(그 차례의 제안이 대신함), yes 로 회고가 끝나면 그 작업의 다른 열린 결정을 닫습니다. drop 은 결정 닫기와 같은 트랜잭션에서 회고를 끝내, 알림을 기다리는 사이 온 메시지가 끝날 회고에 차례를 열지 않게 합니다. 처음에는 회고의 `rule` 칸 하나를 읽어, 앞 결정에 yes 하면 뒤 제안이 들어가고, 그 뒤 뒤 결정을 drop 하면 회고가 declined·작업이 cancelled 로 덮인 채 규칙은 켜져 있었습니다. 켜진 규칙은 다음에 뜨는 모든 워커의 시스템 프롬프트에서 기본 규칙 뒤에 붙고, 회고 워커의 첫 메시지에도 들어갑니다.
- **규칙은 장부에.** 처음에는 받아들인 규칙을 `<홈>/rules.md` 파일에 한 줄씩 붙이고 사람이 파일을 직접 고치게 했습니다. 그러자 사람이 줄을 고치거나 지워도 장부는 몰랐고, 회고 기록에는 `added` 만 남아 규칙과 그 규칙을 만든 회고가 이어지지 않았으며, 누가 언제 바꿨는지도 남지 않았습니다(불변식 2). 그래서 규칙을 `rules` 테이블(장부 v17)에 둡니다. 한 줄에 규칙, 만든 회고(`retro_id`, 사람이 직접 넣은 규칙이면 비어 있음), 켜짐·꺼짐(`state`), 만든 시각과 바꾼 시각이 남고, 만들고·고치고·끄고·켤 때마다 할 일 이력(`todo_changes`)과 같은 모양으로 누가·무엇을·언제를 `rule_changes` 에 남깁니다. 사람과 루트 세션은 `nod rule ls·add·edit·off·on` 으로 다룹니다. 지우기는 두지 않았습니다. 지우면 규칙이 어느 회고에서 왔는지가 사라지므로 끄는 것으로 대신합니다. `nod show r<n>`(웹 화면의 작업 화면도)은 그 회고가 넣은 규칙의 번호와 지금 상태, 제안과 문구가 달라졌으면 고쳐졌음을 보여 줍니다.
- **파일에서 옮기기.** v17 마이그레이션이 `<홈>/rules.md` 가 있으면 그 줄들(앞의 `- ` 를 뗀 내용)을 `rules` 로 옮깁니다. 결과가 `added` 이고 제안한 규칙이 같은 회고가 있으면 그 회고와 잇고, 없으면 사람이 쓴 규칙으로 둡니다. 옮긴 뒤 파일은 지우지 않고 `rules.md.imported` 로 이름을 바꿔, 고쳐도 반영되지 않는 파일임을 드러냅니다. 이름 바꾸기도 마이그레이션 트랜잭션 안에서 하므로, 실패하면 장부가 그대로 남습니다. 그 뒤로 nod 는 이 파일을 읽지도 쓰지도 않습니다.
- **워커는 규칙을 바꾸지 못합니다.** 워커의 샌드박스는 장부에 쓰지 못합니다(아래 「쓰기 경로를 열지 않았습니다」). `nod rule` 의 바꾸는 명령과 규칙 결정에 대한 답(`nod <결정> yes`)은 워커 환경(`NOD_TASK`)에서 부르면 거절해, 그 경계가 언젠가 열려도 워커가 다음 워커들의 규칙을 쓰지 못하게 합니다. 규칙 결정의 yes 는 결정 닫기와 규칙 넣기를 한 트랜잭션으로 하고 알림은 그 뒤에 보냅니다. 처음에는 알림 사이에 끊기면 결정은 닫히고 규칙은 없이 회고 작업이 실행 중으로 남았습니다.
- **정리.** 회고가 끝나면(규칙을 넣었거나, 버렸거나, 제안이 없거나, 할 일로 보냄) gc 가 바로 정리합니다. 회고의 결과물은 빈 폴더가 아니라 장부의 `retros` 줄과 회고 작업의 보고(턴의 `report`), 규칙 결정과 그 답, 받은 일함에 넣은 할 일이기 때문입니다. 처음에는 레포 없는 작업처럼 7일을 기다려서 끝난 회고가 `nod ls` 에 쌓였습니다(2026-10-23).
- **일부러 하지 않은 것.** 회고가 샌드박스 허용 도메인이나 nod 의 코드를 바꾸지는 않습니다. 그런 변경은 회고가 받은 일함에 넣고 사람이 직접 합니다. 작업마다 그때 받은 규칙을 복사해 두기, 작업 종류별 규칙 묶음, 웹 화면에서 규칙 고치기도 하지 않았습니다. 필요해지면 그때 더합니다.

**실측 (2026-10-06, haiku).** 지시는 "count.txt 에 3", 검증은 `grep -qx 4 count.txt` 로 일부러 어긋나게 넣었습니다. 워커가 3 을 쓰고 done 을 보고하자 검증이 되돌려 보냈고, 4 로 고쳐 통과했습니다(27초). 이어서 회고 작업이 스스로 떠서 "자동 승인 조건이 지시사항과 다르면 작업 시작 전에 보고" 를 제안했고, yes 로 답하자 그때 규칙을 두던 `rules.md` 파일에 붙었습니다. 다음에 띄운 워커의 실행 인자에 그 규칙이 들어 있었습니다. 다만 지금 워커는 검증 명령을 실패한 뒤에야 보기 때문에 이 규칙을 지킬 방법이 없습니다. 회고가 nod 자체의 빈틈(검증 명령을 처음부터 알려 주지 않음)을 드러낸 사례입니다. 이 빈틈은 실사용 개선에서 메웠습니다(아래).

## 독립 리뷰 (2026-10-19)

검증 명령과 커밋 확인만으로는 막지 못하는 빈틈이 셋 있었습니다. 워커가 테스트를 약하게 고쳐 검증 명령을 통과시켜도 nod 는 알 수 없었습니다. 검증 명령이 없는 작업은 워커의 말만 믿었습니다. 사람이 `nod tell` 로 지시를 바꾸면, `nod add` 때 정한 검증 명령은 바뀐 지시를 따라가지 못했습니다. 그래서 워커가 done 을 보고하고 검증 명령과 커밋 확인을 통과하면, 워커의 대화를 모르는 리뷰어가 결과를 한 번 더 봅니다.

- **리뷰어가 받는 것.** 지시, 그 뒤 사람이 한 말(`nod tell` 과 결정의 답)을 순서대로, 검증 명령과 통과 여부, 워커의 마지막 보고입니다. 워커가 답하는 도중에 보낸 `nod tell` 은 새 차례(시도)를 열지 않고 그 차례에 들어가므로, 장부의 `messages` 테이블(장부 v20)에 그 차례와 함께 남기고 리뷰어에게는 그 차례를 연 말 뒤에 놓습니다. 처음에는 시도의 지시만 읽어서, 작업 도중 방향을 바꾼 `nod tell` 두 번을 모르는 리뷰어가 원래 지시대로 실패시켰습니다. 레포 작업이면 브랜치가 시작된 뒤로 바뀐 파일 목록(`git diff --stat`)과 diff 전체를 nod 가 직접 뽑아 지시문에 넣습니다. 처음에는 리뷰어에게 `git diff` 로 읽으라고만 했는데, 그러면 diff 를 얼마나 읽을지 리뷰어가 정하게 되어 일부만 보고 넘어갈 수 있었습니다. 바뀐 파일 목록이 맨 위에 있으니 테스트 파일이 바뀌었는지도 바로 보입니다. diff 는 20만 자까지 넣고, 넘으면 어디서 잘렸는지 알려 나머지는 리뷰어가 직접 읽게 합니다. 시작 커밋은 브랜치 reflog 의 가장 오래된 항목에서 읽습니다. `worktree add -b` 가 시작점을 남기고, 이후 커밋은 항목을 더할 뿐이기 때문입니다.
- **판정.** 사람이 요청한 것을 하지 않았거나, 테스트·검증 명령을 약하게 고쳐 통과시켰거나, 보고가 결과와 다르면 실패입니다. 스타일이나 요청하지 않은 것으로는 실패시키지 않습니다. 실패하면 리뷰어의 지적이 검증 실패와 똑같이 같은 턴으로 돌아갑니다. 그래서 재시도 2회, 그 뒤 check_failed 결정, 끝난 뒤 회고까지 기존 흐름을 그대로 탑니다.
- **화면 없는 `claude -p`.** 워커를 대화형 세션으로 두는 이유는 맥락을 이어 받기 위해서입니다. 리뷰어는 판정을 한 번만 하고 이어 받을 맥락이 없어서 예외로 둡니다. Stop 훅 안에서 돌고 10분이 넘으면 끊깁니다. 검증 명령과 리뷰가 모두 훅 안에서 돌므로 Stop 훅 제한 시간을 30분으로 늘렸습니다.
- **판정하지 못하면 통과시키지 않습니다.** 리뷰어가 실패로 끝나거나, 판정 줄 없이 끝나거나, 레포 worktree 를 바꾸면 작업은 error 가 됩니다. 리뷰어는 Edit·Write 도구가 막혀 있고, 셸은 워커와 같은 샌드박스에서 돕니다. 다만 샌드박스는 작업 폴더 쓰기를 허용하므로, 리뷰가 끝난 뒤 HEAD 와 커밋하지 않은 변경을 확인합니다.
- **회고 작업은 리뷰하지 않습니다.** 회고의 결과는 규칙 제안이나 받은 일함의 할 일이고, 그 판단은 사람이 결정이나 받은 일함 정리로 합니다.
- **일부러 하지 않은 것.** 리뷰를 끄는 옵션은 두지 않았습니다. 필요해지면 그때 더합니다. 리뷰어가 테스트를 직접 돌려야 한다면 리뷰어용 worktree 를 따로 만들어야 합니다.

**실측 (2026-10-19, Claude Code 2.1.302, haiku).**

- 워커의 Stop 훅 안에서 `claude -p` 가 중첩으로 돌았고, 부모 세션 ID 를 이어받지 않고 새 세션으로 기록됐습니다. `--disallowedTools` 는 인자를 여러 개 받아 뒤에 오는 프롬프트까지 삼키므로, 지시는 stdin 으로 넘깁니다.
- 정상 경로: 버그가 있는 덧셈 함수를 고치라는 레포 작업에서 워커가 고치고 done 을 보고했습니다. 리뷰어는 "테스트·검증 게이트는 그대로이며 보고가 커밋과 일치한다"며 통과시켰습니다. 작업 전체는 47초였습니다.
- 약하게 고친 테스트: 버그는 두고 테스트 기댓값만 5 에서 -1 로 바꾼 커밋(`bun test` 는 통과)을 같은 지시문으로 리뷰하게 했습니다. 리뷰어는 구현이 그대로이고, 기댓값을 버그의 결과로 바꿨으며, 보고가 사실과 다르다고 짚어 실패로 판정했습니다. worktree 는 바뀌지 않았습니다.
- diff 를 지시문에 넣도록 바꾼 뒤 다시 쟀습니다. 테스트 기댓값만 바꾼 커밋은 실패로, 구현을 `a + b` 로 제대로 고친 커밋은 통과로 판정했습니다(각 1회). 두 경우 모두 worktree 는 바뀌지 않았습니다.

## 서브 에이전트 리뷰 (2026-10-23)

독립 리뷰는 워커가 테스트를 약하게 고쳐 통과시키지 않았는지, 보고가 결과와 맞는지를 보는 마지막 관문입니다. 정확성 버그까지 찾게 하면, 돌려보낼 때마다 워커의 재시도 2회 가운데 하나가 쓰이고 리뷰가 10분 안에 끝나야 하는 Stop 훅 안에서 돌아야 합니다. 사람이 바란 것도 독립 리뷰어를 넓히는 것이 아니라 워커마다 서브 에이전트로 리뷰받는 것이었습니다. 그래서 버그 찾기는 워커가 done 을 보고하기 전에 스스로 받는 서브 에이전트 리뷰로 둡니다.

- **두 리뷰가 보는 것.** 독립 리뷰는 done 뒤에 요청한 일을 했는지, 테스트·검증 명령을 약하게 고쳐 통과시키지 않았는지, 보고가 결과와 맞는지를 봅니다. 서브 에이전트 리뷰는 done 전에 요청한 것이 정말 됐는지, 새 테스트가 고치기 전 코드에서 실패하는지, 변경이 새로 만든 정확성 버그(경계값·에러 삼킴·경쟁 조건·데이터 유실·주입·비밀 유출)가 있는지를 봅니다.
- **지시.** 레포 작업의 워커만 시스템 프롬프트에서 `WORKER_PROMPT` 뒤에 `SUBAGENT_REVIEW_PROMPT` 를 받습니다. 워커는 먼저 커밋하고(diff 범위는 커밋한 것만 보여 줍니다), Agent 도구로 서브 에이전트를 띄워 지시, 그 뒤 사람이 한 말, `git diff <시작>..HEAD` 범위만 주고, 왜 그렇게 고쳤는지는 주지 않습니다. 그 diff 가 비어 있으면(리뷰만 하는 작업처럼 커밋할 것이 없는 작업) 건너뜁니다. done 은 서브 에이전트가 보고한 뒤에만 합니다. 서브 에이전트가 백그라운드로 떴으면 워커는 기다리는 동안 차례를 끝내도 되고, nod 가 그 차례를 기다림으로 둡니다(아래 「백그라운드 작업 기다리기」). 처음에는 같은 차례 안에서 기다리라고(포그라운드로 띄우고, 백그라운드로만 돌면 결과가 올 때까지 차례를 끝내지 말라고) 했습니다. 그런데 Agent 도구가 백그라운드로만 도는 환경에서 워커는 sleep·폴링으로 차례를 붙잡을 수 없어 지킬 수 없는 지시였고, 워커는 기다리겠다는 뜻으로 `NOD: question` 을 남겨 쓸모없는 결정이 열렸습니다. 이 기능을 만든 nod 워커에서도 Agent 도구는 백그라운드로만 돌았습니다. 서브 에이전트는 작업 폴더의 파일을 고치지 않고 발견마다 파일:줄, 재현 시나리오, 확신도를 보고합니다. 새 테스트를 고치기 전 코드에서 돌려 볼 때는 임시 폴더에 `git worktree add` 하거나 파일을 복사해서 하고, `git stash`·`checkout` 은 쓰지 않습니다. stash 는 같은 레포의 모든 worktree 가 함께 쓰는 스택이고, checkout 은 워커의 worktree 를 바꿉니다. 워커는 시나리오가 있는 발견을 고쳐 커밋하고 다시 리뷰받은 뒤, 최종 보고에 발견과 처리(고침, 또는 기각한 이유)를 적습니다. 시스템 프롬프트는 모든 차례에 실리므로 지시는 열 줄로 줄였습니다. 회고 워커가 받는 "모든 워커가 이미 받는 규칙"에는 이 지시를 넣지 않습니다. 레포 없는 워커는 받지 않기 때문입니다.
- **시작 커밋.** 워커가 diff 범위를 확실히 알도록 nod 가 첫 메시지에 "Your branch starts at commit <커밋>." 을 넣습니다. 값은 `worktree add -b` 직후 worktree 의 HEAD 라, 새로 만든 worktree 에서는 독립 리뷰가 브랜치 reflog 의 가장 오래된 항목에서 읽는 시작과 같습니다. 워커가 reflog 를 읽는 명령을 알려 주는 방법보다 단순하고, 워커가 줄을 잘못 고를 일이 없습니다.
- **일부러 하지 않은 것.** 시작 커밋은 첫 메시지에만 있어서 Claude Code 가 대화를 요약하면 잃을 수 있습니다. gc 가 브랜치를 지운 작업을 `nod tell`·`nod resume` 으로 다시 열면 worktree 를 새 브랜치로 다시 만들므로, 첫 메시지의 시작이 독립 리뷰의 시작과 달라집니다. 기록한 커밋까지 사라져 원격 기본 브랜치에서 다시 만들었다면 서브 에이전트가 그 사이 머지된 남의 변경까지 리뷰합니다. 이 기능 전에 시작한 레포 작업은 첫 메시지에 시작 커밋이 없습니다. 이런 일이 실제로 생기면 시작 커밋을 다시 알리거나 시스템 프롬프트로 옮깁니다. 서브 에이전트 리뷰를 했는지 nod 가 확인하지는 않습니다. 필요해지면 그때 더합니다.

## 백그라운드 작업 기다리기 (2026-10-25)

워커가 백그라운드 서브 에이전트(리뷰)나 셸(긴 테스트)을 띄우고 그것을 기다리며 차례를 끝내면, Stop 훅은 그 차례의 "기다리는 중" 이라는 말을 질문 결정으로 올렸습니다. 결과가 오면 Claude Code 가 저절로 다음 차례를 열어 그 결정은 곧 닫히는데도, 사람에게는 알림이 갔습니다. 장부에서 찾은 것만 하루에 다섯 건이었고(작업 둘), 사람은 "끝났으니 이어서 하라"고 답하거나 그냥 두었습니다. 그래서 차례가 끝날 때 그 세션에 아직 끝나지 않은 백그라운드 작업이 있으면, 결정을 열지 않고 그 차례를 기다림으로 기록합니다.

- **신호를 고른 과정 (Claude Code 2.1.309).** 질문 문장의 낱말로 짐작하지 않고, Claude Code 가 남기는 것 가운데서 찾았습니다. 셋을 쟀습니다.
  - 대화 기록(JSONL)의 차례 끝 `system`·`turn_duration` 항목에 `pendingBackgroundAgentCount` 가 있습니다. 기다림 결정 넷이 열린 차례는 모두 1, 진짜 질문을 남긴 차례는 0 이었습니다. 하지만 이 항목은 Stop 훅이 끝난 뒤에 쓰여 훅 안에서는 그 차례의 값을 읽을 수 없고, 에이전트만 셉니다. 백그라운드 셸이 끝나기를 기다린 다섯째 결정의 차례는 0 이었습니다.
  - 칸 화면의 "Waiting for N background agents" 줄은 바이너리에서 보니 같은 값으로 그리는 줄이라 같은 한계가 있고, 화면 문구에 기대게 됩니다.
  - Stop 훅 입력의 `background_tasks` 를 택했습니다. 바이너리에서 Stop 훅 입력을 만드는 곳이 세션의 작업 목록 가운데 실행 중이거나 곧 돌 것이고 포그라운드가 아닌 것을 `{id, type, status, description}` 으로 넣습니다. `type` 은 에이전트 `subagent`, 셸 `shell`, `monitor` 등입니다. `claude -p` 에 입력을 파일로 남기는 Stop 훅을 걸어 실제로 쟀습니다. 백그라운드 `sleep 40` 셸을 띄우고 끝낸 차례의 입력에 `{"type": "shell", "status": "running"}` 이 있었고, 그 셸이 끝나 Claude Code 가 스스로 연 다음 차례의 입력에는 빈 배열이었습니다. 백그라운드 에이전트도 `{"type": "subagent", "status": "running"}` 으로 같았습니다. 이 칸이 없는 옛 버전에서는 지금처럼 결정을 엽니다. 칸의 모양이 바뀌어도 훅은 실패하지 않습니다. 읽지 못한 항목도 하나로 세고, 목록 자체를 읽지 못하면 없는 것으로 봅니다. 처음에는 엄격하게 읽어, 항목 하나만 달라도 그 차례를 판정하지 못할 수 있었습니다(리뷰에서 찾음).
- **끝까지 잰 것.** 임시 nod 홈에 작업을 하나 두고, 그 세션 ID 로 띄운 실제 `claude -p`(2.1.309, haiku)에 nod 의 Stop 훅(`nod hook stop`)을 걸었습니다. 백그라운드 `sleep 20` 을 띄우고 `NOD: question | waiting for the sleep` 으로 끝낸 첫 차례는 `waiting` 으로 남고 결정이 열리지 않았습니다. 셸이 끝나 Claude Code 가 스스로 연 다음 차례는 `followup` 으로 기록됐고, 그 차례의 `NOD: question | which file next?` 만 결정이 됐습니다.
- **하는 일.** done 이 아닌 멈춤(question·failed·보고 줄 없음)에 `background_tasks` 가 비어 있지 않으면, 그 차례를 `waiting` 결과로 닫고 결정을 열지 않습니다(`settle`). 작업은 실행 중 그대로입니다. 백그라운드 작업이 끝나면 Claude Code 가 다음 차례를 스스로 열고, 훅이 그 차례를 `followup` 으로 기록해 그 차례의 멈춤이 평소처럼 판단합니다. failed 도 기다립니다. 다음 차례가 곧 오므로 지금 연 결정은 그 차례가 `(it went on without an answer)` 로 닫을 뿐이기 때문입니다. done 은 기다리지 않고 검증합니다. 개발 서버를 띄워 둔 채 끝낸 작업처럼, 백그라운드 작업이 남아 있다고 끝난 일을 미룰 까닭은 없습니다.
- **워커 지시.** 모든 워커가 받는 `WORKER_PROMPT` 에 "백그라운드 작업이 남은 채 멈추면 `NOD: question | <기다리는 것>` 으로 끝내라, nod 가 사람에게 묻지 않고 기다리고 그 작업이 끝나면 다음 차례가 열린다"를 넣었습니다. 보고 줄 형식은 그대로 두어, 상한에 걸려 결정이 열리면 사람이 무엇을 기다렸는지 읽습니다. 서브 에이전트 리뷰 규칙(`SUBAGENT_REVIEW_PROMPT`)의 "결과가 올 때까지 차례를 끝내지 말라"는 "보고가 온 뒤에만 done, 백그라운드면 기다리며 멈춰도 됨"으로 바꿨습니다.
- **상한.** 기다린 차례가 이어진 지 한 시간(`WAIT_LIMIT_MS`, 그 가운데 첫 차례가 끝난 때부터)이 넘으면 지금처럼 결정으로 올립니다. 다음 멈춤이면 백그라운드 작업이 아직 돌아도 결정을 열고, 질문 앞에 기다린 시간과 아직 도는 작업을 붙입니다. 다음 차례가 오지 않으면 tick 이 엽니다(`overdueWaits`, 기다린 차례의 마지막 보고로). 끝나지 않는 백그라운드 작업(띄워 둔 서버)이나 Claude Code·칸과 함께 사라진 작업은 다음 차례를 부르지 않고, 차례마다 백그라운드 작업을 새로 띄우는 워커는 끝없이 이어지기 때문입니다. 한 시간은 리뷰를 두세 번 받는 흐름(실측 한 번에 9~20분)이 넘지 않을 만큼으로 잡았습니다. 시간 하나로 두 경우를 함께 막으려고 차례 수 상한은 두지 않았습니다. tick 은 그 차례를 `waiting` 이고 뒤에 차례가 없을 때만 바꾸는 조건부 UPDATE 한 문장으로 먼저 차지합니다. 겹친 tick 둘이 결정을 둘 열지 않고, 그 사이 작업이 끝나 열린 차례가 있으면 그 차례에 맡깁니다.
- **일부러 하지 않은 것.** Claude Code 가 다시 뜨거나 칸이 사라져 백그라운드 작업이 함께 없어진 것을 그 자리에서 알아채지는 않습니다. 한 시간 뒤 tick 이 묻습니다. 계정 전환은 기다리는 워커를 쉬는 워커로 보고 바로 다시 띄워 백그라운드 작업이 끊깁니다. 전에도 그랬고(결정 대기도 바로 다시 띄움), 기다리게 하면 끝나지 않는 작업이 계정 전환을 영영 막습니다. 에이전트가 끝났지만 아직 알리지 않은 순간에 멈추면 `background_tasks` 에 없어 결정이 열리고, 곧 그 알림이 연 차례가 닫습니다. 예약 작업(`session_crons`)은 기다림으로 치지 않습니다. tick 은 `nod schedule on` 일 때만 돌므로, 끄면 끝나지 않는 백그라운드 작업을 기다리는 작업은 실행 중으로 남습니다. 칸째 사라진 차례(lostTurns)와 같습니다.

## 워커끼리 말하기 (2026-10-25)

워커는 서로 말할 수 없어서, 리뷰 작업이 찾은 문제를 사람(루트 세션)이 구현 작업에 손으로 옮겼습니다. 이제 워커가 보고의 마지막 줄 위에 `NOD: tell #<작업> <메시지>` 를 쓰면 nod 가 그 작업의 워커에 보냅니다. 리뷰를 마친 작업이 구현 작업에 지적을 보내고, 구현 작업이 고친 뒤 리뷰 작업에 다시 봐 달라고 보내는 흐름이 사람 손 없이 돕니다. 리뷰 전용 옵션은 두지 않았습니다. 사람이 "리뷰가 끝나면 지적을 #85 에 보내라"고 지시에 쓰면 됩니다.

- **읽는 곳.** `NOD: in` 과 같은 자리, 곧 nod 가 done 을 받는 길에서 읽습니다(`parseTells`). 한 줄에 하나이고, 형식이 틀린 줄과 보낼 수 없는 줄은 `NOD: in` 처럼 검증 전에 실패한 검증으로 같은 차례에 돌려보냅니다. 워커가 보고 줄이나 그 `NOD:` 를 굵게(`**…**`) 쓰는 일이 흔해서, 두 줄 모두 줄이 여는 `*`·백틱을 세어, `NOD:` 바로 뒤(`**NOD:** tell …`)나 줄 끝(`**NOD: tell …**`)에서 연 만큼만 닫고 읽습니다. 메시지가 `*`·백틱으로 끝나도 그대로 남습니다. 처음에는 백틱만 벗겨, 리뷰에서 굵게 쓴 `NOD: tell` 줄이 보내지지도 돌려보내지지도 않고 사라지는 것이 드러났습니다. 앞뒤의 `*`·백틱을 모두 벗기자 `src/**` 로 끝나는 메시지가 잘렸고, 짝을 맞추는 정규식으로 바꾸자 `**NOD:** tell … **중요**` 줄이 다시 사라지고 백틱이 수천 개 이어진 줄 하나에 몇 분이 걸렸습니다(모두 리뷰에서 재현). 그래서 정규식으로 짝을 맞추지 않고 셉니다. 워커의 샌드박스는 장부와 다른 칸에 닿지 못하므로, 보내는 일은 샌드박스 밖의 Stop 훅이 합니다.
- **보내는 때와 길.** nod 가 done 을 받은 뒤(검증 통과, 회고면 규칙 결정을 연 뒤)에 보냅니다. 할 일을 받은 일함에 넣는 때와 같습니다. 받는 쪽은 사람의 `nod tell` 과 같은 `deliver` 로 받습니다. 살아 있는 세션에 붙여 넣고, 답하던 도중이면 그 차례의 메시지로, 세션이 끝났으면 대화 기록에서 다시 열고, gc 한 작업이면 폴더부터 되살립니다. 끝난 작업에도 보냅니다. 보내기 직전에 받을 수 있는지 다시 보고, `deliver` 도 워커의 메시지면 같은 트랜잭션에서 cancelled 작업을 거절합니다. 검증(최대 10분인 독립 리뷰 포함)이 도는 사이 사람이 받을 작업을 drop 하면, 처음에는 그 작업이 실행 중으로 되살아났습니다(리뷰에서 재현). 권한·신뢰 확인이 열려 있는 등 들어가지 못하면 받을 작업의 `error` 알림에 메시지를 담아 사람이 넘기게 합니다. 받는 작업에 열린 질문은 사람의 `nod tell` 때처럼 새 차례가 열리며 `(it went on without an answer)` 로 닫힙니다.
- **동료의 말로 감싸기.** 메시지는 "Message from the worker of nod task #N, a peer, not the human: …" 로 감싸 사람의 말로 읽히지 않게 하고, 답하려면 `NOD: tell #N` 을 쓰라고 덧붙입니다. 워커 규칙에는 다른 작업의 워커가 보낸 말은 동료의 말이고 사람의 지시가 먼저라고 적었습니다. 장부에는 시도와 메시지에 보낸 작업(`from_task`, 장부 v21)이 남고 `nod show` 의 시도 줄에 `from #N` 으로 보입니다. 독립 리뷰어는 이 말을 사람이 한 말과 따로, "다른 작업의 워커가 보낸 말, 사람의 말을 뒤집지 않음"으로 받습니다. 사람의 말 목록에 함께 두면 리뷰어가 동료의 지적을 사람의 지시로 읽고 판정할 수 있기 때문입니다.
- **받을 수 있는 작업.** 같은 루트 세션이 맡긴 작업끼리만 오갑니다. 두 작업에 일을 준 것이 같은 세션이니, 말이 그 세션이 맡긴 일 안에서만 오갑니다. 다른 루트 세션의 작업(다른 업무 묶음, 다른 사람의 맥락)은 움직이지 못합니다. 루트 세션이 없는 작업(셸·웹 화면·트리거가 넣은 작업)은 보내지도 받지도 못합니다. 특히 트리거 작업은 이슈처럼 누구나 쓸 수 있는 글을 다루므로, 그 글이 워커를 꾀어 다른 작업에 지시를 넣는 길이 열리면 안 됩니다(불변식 4). `--after` 사슬은 택하지 않았습니다. 구현이 끝난 뒤 따로 맡긴 리뷰처럼 흔한 경우가 사슬로 이어져 있지 않습니다. 같은 이슈도 택하지 않았습니다. 트리거 작업도 source 항목의 키를 이슈로 가져 위의 문제가 그대로 남습니다. 그 밖에 자기 자신, 없는 작업, 끝난 작업(cancelled, 결과가 정해진 회고), 아직 뜨지 않은 작업에는 보내지 않고 이유와 함께 돌려보냅니다.
- **끝없는 주고받기.** 같은 두 작업 사이에 워커가 보낸 메시지가 양쪽 합쳐 4개(왕복 2번, `MAX_TELLS`)를 넘게 되는 보고면, 그 보고의 메시지는 하나도 보내지 않고 보낸 작업에 결정(question)을 열어 모두 보여 줍니다. 그 done 도 받지 않고 검증 전에 멈춥니다. 처음에는 넘친 메시지 하나만 보여 줘, 같은 보고의 다른 메시지는 보내지도 보이지도 않았습니다(리뷰에서 재현). 사람이 보낸 `nod tell` 은 세지 않습니다. 결정 종류를 새로 만들지 않고 question 을 쓴 것은, 답이 보낸 워커의 대화로 가는 기존 길 그대로이기 때문입니다. 메시지를 넘길지는 사람이 `nod tell` 로 직접 정합니다. 수는 검증 전에 세고 보내기는 검증 뒤에 하므로, 두 작업이 동시에 서로 보내면 하나씩 넘칠 수 있습니다.
- **일부러 하지 않은 것.** 여러 줄 메시지, done 이 아닌 보고(question·failed)에 쓴 `NOD: tell`, 아직 뜨지 않은 작업에 미뤄 두었다가 보내기, 메시지가 오갈 때마다 `<홈>/notify` 로 알리기는 하지 않았습니다. 검증에 되돌려진 뒤 이어진 차례의 보고에 `NOD: tell` 줄이 다시 없거나, 검증하는 사이 `nod tell` 로 다음 차례가 열리면 그 보고의 줄은 보내지 않습니다. `NOD: in` 도 같습니다. 받는 작업의 열린 질문을 지키려고 보내기를 미루지도 않았습니다. 사람의 `nod tell` 과 다르게 굴면 같은 메시지가 길에 따라 다르게 들어갑니다.

## 결과 올리기 (착지, 2026-10-26)

워커가 성공하고 독립 리뷰를 통과해도, 사람(루트 세션)이 손으로 최신 main 위로 rebase 하고, 충돌을 풀고, 전체 시험을 다시 돌리고, 공개 레포 점검을 하고, push·PR·머지·`nod link` 를 했습니다. 앞 PR 이 머지될 때마다 뒤 브랜치를 다시 옮겼습니다. 이 일을 레포마다 사람이 허락한 만큼 nod 가 맡습니다(`src/land.ts`). 정해진 단계는 샌드박스 밖의 nod 가 하고, 판단이 필요한 일만 그 작업의 워커가 같은 대화에서 합니다.

- **권한은 레포마다 장부에.** `nod repo <경로> off|pr|merge` 로 정합니다. 기본은 `off`(지금처럼 사람이 올림)이고, `pr` 은 PR 까지, `merge` 는 squash 머지까지입니다. 장부 v22 의 `repos` 에 두고, 바꿀 때마다 누가·무엇을·언제를 `repo_changes` 에 남깁니다. 레포 안 파일은 택하지 않았습니다. 워커가 자기 브랜치에서 권한을 올릴 수 있고, 공개 레포에 점검 패턴까지 실리기 때문입니다. `<홈>/repos.json` 은 누가·언제가 남지 않아 택하지 않았습니다(규칙을 파일에서 장부로 옮긴 이유와 같음). 작업마다 `nod add --land` 로 주는 것도 택하지 않았습니다. 그러면 매번 루트 세션이 정하게 되어 사람이 미리 해 둔 허락이 아니게 됩니다. 워커 환경(`NOD_TASK`)에서는 바꾸지 못하고, Claude 세션(`CLAUDECODE`)에서는 `off` 로 내리기만 합니다. 루트 세션이 스스로 머지 권한을 얻지 않게 하려는 것입니다. 다만 환경 변수로 가리므로 경계라기보다 실수를 막는 장치이고, 워커를 장부에서 떼어 놓는 것은 여전히 샌드박스입니다. Claude Code 의 `!` 명령이 세션 환경을 물려받으면 사람도 다른 터미널에서 올려야 합니다.
- **대상은 권한을 켠 뒤에 넣은 작업.** `off` 에서 올린 시각(`raised_at`) 이후에 넣은 작업만 저절로 올라갑니다. 켜자마자 쌓여 있던 성공 작업 수십 개가 PR 이 되지 않게 하려는 것으로, 트리거의 "처음 본 것만"과 같은 생각입니다. 그 전 작업은 `nod land <작업>` 으로 이름을 대면 올라가고, 한 번 착지를 시작한 작업(`landings` 에 줄이 있음)은 그 뒤로도 대상입니다. 남이 링크를 단 작업은 결과가 이미 다른 길로 나간 것으로 보고 건너뜁니다.
- **언제.** 스케줄의 tick 이 5분마다(감시·gc 와 같은 주기, 다른 일을 마친 뒤 gc 보다 먼저) 돌리고, `nod land` 는 바로 돌립니다. Stop 훅에서는 하지 않습니다. 훅은 이미 검증과 리뷰에 최대 30분을 쓰고, CI·리뷰·남의 머지는 어차피 다시 들여다봐야 하며, 레포마다 줄을 세우는 일은 한 곳에서 해야 서로 겹치지 않기 때문입니다. 대가는 스케줄이 꺼져 있으면 `nod land` 로만 된다는 것이라, `nod repo` 가 그렇다고 알립니다. OS 스케줄러는 tick 이 도는 동안 다음 tick 을 띄우지 않으므로, 오래 걸리는 검증 명령(30분까지)은 그만큼 다음 tick 의 트리거·감시를 늦춥니다. 착지가 tick 의 다른 일 뒤에 도는 까닭입니다. 두 프로세스가 같은 레포를 함께 올리지 않도록, 레포를 pid 로 차지합니다(`repos.lander`, 그 pid 가 죽었으면 다시 차지). 작업 순서는 넣은 순서라서, 같은 레포에서 `--after` 로 이은 작업은 앞 작업 뒤에 봅니다. 앞 작업이 머지되지 않았으면 뒤 작업은 기다립니다. 뒤 작업의 브랜치에는 앞 작업의 커밋이 들어 있기 때문입니다. 리뷰나 CI 를 기다리는 PR 은 줄을 막지 않습니다.
- **자기 일의 시작을 기록합니다.** 작업마다 `landings.base` 에 자기 커밋이 얹힌 커밋을 둡니다. 처음 값은 독립 리뷰가 읽는 것과 같은, 브랜치 reflog 의 가장 오래된 항목입니다. 사슬 뒤 작업이면 그때 앞 작업 브랜치의 끝입니다. rebase 할 때마다 옮겨 간 커밋으로 바꿉니다. 그래서 rebase 는 언제나 `git rebase --onto <원격 기본 브랜치 끝> <base>` 한 모양입니다. 앞 작업이 squash 로 들어갔든, 앞 작업이 rebase 됐든, main 이 그냥 움직였든 자기 커밋만 옮겨집니다. 독립 리뷰와 서브 에이전트 리뷰도 이 시작부터의 diff 를 봅니다. 착지 차례 메시지가 새 시작을 알리고, 리뷰어는 nod 가 착지하며 한 말(`land` 차례의 지시)을 사람의 말과 따로 받습니다.
- **언제 rebase 하나.** PR 을 열기 전에는 언제나 합니다. `merge` 단계는 머지하기 전마다 합니다. 머지하는 것이 그 끝 위에서 검증한 그대로여야 하기 때문입니다. 머지는 그 head 가 서비스에 그대로 있고 서비스가 바로 머지할 수 있다고 할 때만 하고, 머지 하나가 끝날 때마다 다시 fetch 합니다. `pr` 단계는 서비스가 충돌하거나 뒤처졌다고 할 때만 합니다. 리뷰 중인 PR 을 main 이 움직일 때마다 다시 쓰지 않으려는 것입니다. 사람이 `nod tell` 로 더 고친 작업은 head 가 검증을 통과한 head(`ready`)와 달라졌으므로 검증부터 다시 합니다.
- **nod 가 하는 것과 워커가 하는 것.** fetch, 기본 브랜치 읽기(`git ls-remote --symref`), rebase, 검증 명령, 점검, push, PR, 머지는 nod 가 샌드박스 밖에서 합니다. 워커 샌드박스에는 네트워크가 없고, `.claude/settings.json` 을 바꾼 main 위로 rebase 하다 반쯤 적용된 채 실패한 기록이 있습니다(「실사용에서 고친 것」). 충돌 풀기, rebase 뒤 실패한 검증 고치기, PR 제목·본문 쓰기는 워커가 합니다. 넘기는 길은 `nod tell` 과 같은 `deliver` 이고(새 시도 종류 `land`), 끝난 세션은 대화 기록에서, gc 한 작업은 폴더부터 되살립니다. 필요한 일은 한 차례에 모아 넘깁니다. 기본 나눔에서 다르게 한 곳이 하나 있습니다. 충돌이 없으면 검증 명령을 nod 가 tick 에서 직접 돌립니다. 검증만 하려고 워커에게 빈 차례를 여는 것을 피하려는 것입니다. 검증 명령은 레포의 것(`nod repo --check`, rebase 뒤의 전체 시험)이 있으면 그것을, 없으면 작업의 `--check` 를 쓰고, 30분이 지나면 끊습니다. nod 의 git 은 훅 없이 돌립니다(`core.hooksPath=/dev/null`). 브랜치가 바꾼 훅(husky 처럼 worktree 안을 가리키는 훅 경로)이 샌드박스 밖에서 돌지 않게 하려는 것입니다. rebase 에는 `--no-update-refs` 를 붙여, 사용자 설정 `rebase.updateRefs` 가 뒤 작업의 브랜치까지 옮기지 않게 합니다. nod 가 worktree 에서 rebase·검증을 하는 동안에는(`landings.busy`) 사람의 `nod tell`·답을 거절합니다. 워커가 움직이는 파일 위에서 일하지 않게 하려는 것입니다.
- **충돌.** rebase 가 멈추면 worktree 를 rebase 도중 상태로 두고 워커에게 넘깁니다. 메시지에는 옮기던 커밋, 충돌 파일, 원칙(main 쪽을 살리고 그 위에 브랜치 변경을 얹되 어느 쪽도 조용히 버리지 않는다), 보고할 표(`| 파일·위치 | main 이 바꾼 것 | 브랜치가 바꾼 것 | 고른 쪽과 이유 |`), 숫자·조건이 갈려 애매하면 `NOD: question` 으로 물으라는 말이 들어갑니다. 워커는 고친 파일을 `git add` 만 하고, 커밋이나 `rebase --continue`·`--abort` 는 하지 않습니다. 이 차례는 서브 에이전트 리뷰를 건너뜁니다. 워커가 done 을 보고하면 Stop 훅이 덜 병합된 파일이 남았는지 보고(남았으면 같은 차례로 돌려보냄), `rebase --continue` 를 합니다. 다음 커밋에서 또 멈추면 그 충돌을 같은 차례로 돌려보내는데, 이것은 실패가 아니라 착지가 이어지는 것이라 재시도(2회)로 세지 않습니다(새 시도는 `land`). 충돌이 아닌 까닭으로 이어 가지 못하면(풀이 옆에 stage 하지 않은 변경이 남는 등) git 이 한 말을 돌려보내고 재시도로 셉니다. 처음에는 모두 다음 충돌로 보아, 같은 말을 끝없이 돌려보내고 사람에게 묻지도 않았습니다(리뷰에서 재현). 충돌을 워커에게 넘기지 못하면(칸에 권한 확인이 떠 있는 등) rebase 를 되돌린 뒤 결정을 엽니다. 넘길 데가 없는데 rebase 도중으로 두면 yes 로 답해도 이어 갈 주체가 없었습니다(리뷰에서 재현). rebase 가 끝나면 검증 명령, 커밋 확인, 독립 리뷰를 거칩니다. 훅이 착지 일인 줄 아는 것은 시도 종류가 아니라 `landings.handed_at`(착지 일을 넘긴 시각)으로 봅니다. 사이에 답·`nod tell`·재시도 차례가 끼어도 착지 일로 판단하기 위해서입니다. 착지 일 차례가 성공해도 `succeeded` 알림은 다시 보내지 않습니다.
- **PR 글.** 처음 PR 을 열 때만 워커에게 맡깁니다. 워커는 보고 줄 위에 첫 줄을 제목으로, 그 아래를 본문으로 씁니다. `NOD:` 줄은 빼고 읽습니다. 보고 줄이 있는 done 에서, 받아 둔 글이 없을 때만 받습니다. 막힌 멈춤 뒤에 이어진 done 은 보고 줄을 흔히 빠뜨리는데, 그러면 "Fixed it." 같은 말이 제목이 되기 때문입니다(시험에서 드러남). 같은 착지의 뒤 done(두 번째 충돌, 고친 검증)은 그 일을 보고한 것이라, 처음에는 그 보고가 PR 글을 덮어써 "I added the missing file and committed it." 이 제목이 되었습니다(리뷰에서 재현). 점검이 실패하면 받아 둔 글을 지워 워커가 다시 씁니다. 그 결정의 답에는 nod 가 PR 글 쓰는 법을 붙여 보냅니다. 워커가 받는 것은 사람의 답뿐이라, 처음에는 "Done: I took the word out" 같은 답 문장이 그대로 PR 제목이 됐습니다(리뷰에서 재현). nod 가 PR 글을 직접 짓는 안(지시의 첫 줄과 마지막 보고)은 택하지 않았습니다. 보고는 사람과 nod 에게 쓴 글이라 공개 레포에 그대로 내기 어렵고, 지시에는 바깥에 내면 안 되는 맥락이 들어 있을 수 있기 때문입니다.
- **올리기 전 점검.** push 전마다 nod 는 merge commit 이 없는지와 작업 브랜치가 기본 브랜치가 아닌지 보고, 레포의 점검(`nod repo --gate`)을 worktree 에서 샌드박스 밖으로 돌립니다(5분까지). 점검은 `NOD_BASE..NOD_HEAD`(올릴 커밋)와 `NOD_PR`(PR 제목·본문 파일)을 받아 0 으로 끝나야 합니다. 점검은 레포 밖에 둡니다. 찾을 낱말(회사 이름 같은 것) 자체가 공개하면 안 되는 것이고, 브랜치 안의 스크립트는 워커가 자기 브랜치에서 약하게 고칠 수 있기 때문입니다. 실패하면 결정(check_failed)으로 올리고 답은 워커의 대화로 갑니다. PR 글·커밋 메시지·diff 가 모두 워커의 일이기 때문입니다. 재시도처럼 바로 워커에게 돌려보내지 않는 것은, 공개되면 안 되는 것이 걸린 일이라 사람이 한 번 보게 하려는 것입니다.
- **push.** 작업 브랜치에만, `--force-with-lease=refs/heads/<브랜치>:<nod 가 지난번 push 한 커밋>` 로 합니다. 처음에는 원격에 그 브랜치가 없어야 합니다. 있으면 그 내용이 작업 브랜치의 지난 끝(reflog) 어딘가에 들어 있을 때만 그것을 기대값으로 씁니다. 착지 전처럼 루트 세션이 작업 커밋을 push 해 둔 경우입니다. 그 밖이면 남의 커밋이 있는 것이라 결정으로 올립니다. 브랜치가 시작된 커밋 자체나 그보다 앞은 남의 것으로 칩니다. 처음에는 reflog 의 가장 오래된 항목(시작 커밋)의 조상이기만 하면 자기 것으로 봐서, 남의 브랜치에서 같은 이름으로 시작한 작업이 그 브랜치의 커밋을 원격에서 지웠습니다(리뷰에서 재현). 기본 브랜치에는 push 하지 않습니다. fetch·push 는 2분이 지나면 끊고, 비밀번호를 묻지 않게 합니다(`GIT_TERMINAL_PROMPT=0`). 아무도 답할 수 없는 tick 에서 멈추지 않게 하려는 것입니다. 감시처럼 자기 프로세스 그룹에서 돌려(`runGroup`), 시간이 지나면 git 이 띄운 원격 helper·ssh 까지 끝냅니다. 처음에는 git 만 끝내서, 출력을 쥔 helper 가 끝날 때까지 기다렸습니다(리뷰에서 재현: 0.5초 제한에 6초). 서비스 CLI 가 PATH 에 있는지는 push 하기 전에 봅니다. 없으면 브랜치가 원격에 올라간 뒤에야 결정이 열렸습니다(리뷰).
- **git 서비스.** `src/prs.ts` 를 넓혀 nod 의 PR 을 찾고, 열고, 상태를 읽고, squash 머지합니다(`serviceOf`). 서비스는 `remote.origin.url` 을 적힌 그대로(`insteadOf` 로 바꾸기 전) 읽어, `github.com` 이면 `gh`, 그 밖이면 `tea`(Gitea·Forgejo)로 고릅니다. gh 머지는 `--squash --match-head-commit` 으로 하고, `--auto`(머지 큐에서 나중에 머지)·`--admin`·`--delete-branch`(작업 worktree 에 체크아웃된 로컬 브랜치까지 건드림)는 쓰지 않습니다. 머지는 `mergeStateStatus` 가 `CLEAN` 일 때만 합니다. PR 을 연 뒤 상태를 읽지 못하는 것(로그아웃, 네트워크)은 결정이 아니라 기다리는 까닭(`landing` 알림)으로 남기고 다음 tick 이 다시 읽습니다. 찾을 때는 열린 PR 만 받습니다. 사람이 짓는 브랜치 이름은 다시 쓰일 수 있어서, 처음에는 같은 이름의 옛 머지된 PR 을 이 작업의 것으로 보고 머지된 것으로 쳤습니다(리뷰에서 재현). tea 는 모두 `tea api` 로, 레포 폴더에서 `-R origin` 으로 그 원격의 로그인을 골라 부르고, 머지는 `head_commit_id` 를 줍니다. Gitea 의 머지는 빈 몸통으로 답하므로, 몸통이 오면 거절로 보고 머지한 뒤 PR 이 정말 머지됐는지 다시 읽습니다. tea 가 거절에도 0 으로 끝날 수 있기 때문입니다.
- **사람에게 오는 것.** 워커 대화로 가는 결정은 애매한 충돌(question), 풀 수 없음(failed), 검증이 계속 실패(check_failed), 점검 실패(check_failed)입니다. nod 가 막힌 것은 새 결정 종류 `land` 로 엽니다. push 거절, 서비스가 PR 열기·머지를 거절, PR 이 머지 없이 닫힘, 서비스 CLI 가 PATH 에 없음, 서비스가 로그인이 안 돼 PR 을 열지 못함, 기본 브랜치 이름의 작업, 시작 커밋을 모름이 여기에 듭니다. 답이 `yes` 면 다시 시도하고(CLI 는 그 자리에서 `nod land`), 그 밖이면 그 작업의 착지를 멈춥니다. 어느 쪽이든 작업은 succeeded 로 남습니다. 알림 대신 결정으로 둔 것은 사람이 볼 곳을 `nod` 하나로 모으려는 것이고, 워커 대화로 보내지 않는 것은 워커는 네트워크가 없어 할 수 없기 때문입니다. 착지 중의 결정을 `nod drop` 하면 작업을 취소하지 않고 착지만 멈춥니다. 워커의 칸을 닫고, rebase 도중이면 `--abort` 로 브랜치를 되돌립니다. 취소하면 성공 기록이 취소로 바뀌고 뒤 작업까지 줄줄이 취소되기 때문입니다. 알림(`<홈>/notify`)은 `pr_opened`·`merged` 와, 착지가 기다리는 것이나 실패한 까닭(`landings.note`)이 바뀔 때마다 한 번씩 가는 `landing` 입니다. 노트북에서 흔한 fetch 실패도 여기에 들어가고, 다음 tick 이 다시 합니다. PR 을 열면 `nod link` 는 저절로 되고, 머지된 뒤에는 이미 있던 gc 신호("링크한 PR 머지")로 다음 sweep 이 정리합니다.
- **시험.** 가짜 `gh`·`tea`(`test/fake-git-service.ts`)가 로컬 bare 레포를 원격 삼아 PR 을 기록하고 squash 머지합니다. 클론의 원격 주소는 서비스가 아는 주소(`https://github.com/o/r`)이고, `url.<bare>.insteadOf` 로 push·fetch 는 bare 레포로 갑니다. 착지기 시험(`src/land.test.ts`)은 tmux 없이 돕니다. 워커에게 넘기는 길(`send`)을 바꿔 끼워 차례만 열고, 워커의 멈춤은 시험이 Stop 훅을 직접 불러 냅니다. 이 기능을 만든 워커의 샌드박스는 tmux 소켓을 만들지 못했기 때문입니다. 실제 GitHub·Gitea 에서 PR 을 열거나 머지해 보지는 않았습니다.
- **일부러 하지 않은 것.** 사슬 PR 쌓기(뒤 작업의 PR 을 앞 작업 브랜치 위에): 뒤 작업은 앞 작업이 머지될 때까지 기다립니다. CI 실패 고치기: 로그를 읽으려면 네트워크가 있어야 해서, 기다린다고 알리기만 합니다. 머지 큐·auto-merge·admin 머지. `origin` 이 아닌 원격, 포크에서 여는 PR, github.com 이 아닌 GitHub(Enterprise). 머지 뒤 원격 브랜치 지우기(서비스 설정에 맡김). PR 을 연 뒤 다시 착지할 때 PR 글 고치기(처음 글을 둠). 기본 브랜치가 아닌 곳으로 올리기, 서명, draft·리뷰어·라벨. 웹 화면에서 권한 바꾸기와 착지 보기. 판단이 필요한 점검(실명 찾기 같은 것): 점검 명령이 직접 부르면 됩니다. 작업마다 착지를 빼는 옵션: 레포를 `off` 로 내리거나, 그 작업에 링크를 달거나, 착지 결정에 no 로 답합니다. 머지 직전 fetch 와 머지 호출 사이(몇 초)에 main 이 움직이는 경쟁: 서비스의 "최신이어야 함" 보호 규칙이 막습니다. 착지가 시작되기 전에 gc 가 브랜치를 지운 작업은 되살린 브랜치의 reflog 가 지난 끝에서 시작해, 자기 커밋이 없는 것으로 읽힙니다. 성공한 직후 다음 tick 이 시작 커밋을 남기므로 스케줄이 꺼진 채 7일이 지나야 생깁니다.

## 할 일 (G1, 2026-10-20)

nod 장부에 사람이 할 일을 GTD 방식으로 둡니다. 목표와 단계는 이슈 #1, 이 단계는 #2 입니다. 할 일은 작업이 아닙니다. 사람이 할 일이고, G2 부터는 작업에 맡길 수 있습니다. 코드는 `src/todos.ts`(장부)와 `src/todo-cli.ts`(명령)에 따로 둡니다. `ledger.ts` 에는 마이그레이션(v10)을 더하고, 두 모듈이 함께 쓰도록 쿼리 빌더(`queryBuilder`)와 실행 함수(`runQuery`)를 꺼냈습니다.

### 할 일 장부로 답하는 질문

| 누가 | 질문 | 데이터 | 명령 |
|---|---|---|---|
| 사람 | 지금 이 상황에서 할 수 있는 다음 행동은? | 상태 next, 상황(없으면 어디서나) | `nod todo next --context @x` |
| 사람 | 받은 일함에 무엇이 언제부터 쌓였나? | 상태 inbox, 상태가 바뀐 시각 | `nod todo inbox` |
| 사람 | 무엇을 누구에게 기다리고 있고, 얼마나 됐나? | 상태 waiting, 기다리는 사람, 상태가 바뀐 시각 | `nod todo waiting` |
| 사람 | 다음 행동이 없는 프로젝트는? | 프로젝트별 next·waiting 수 | `nod project` |
| 사람 | 이 할 일은 어디서 왔나? | 통로(`source`)와 그 통로의 키, 링크 | `nod todo <할 일>` |
| 스킬 | 이 항목을 이미 받아 적었나? | 같은 통로의 같은 키 | `nod in --source <통로> --key <키>` |
| 사람 | 누가(사람·Claude 세션·워커) 무엇을 바꿨나? | 할 일·프로젝트 이력의 누가(`actor`) | `nod todo <할 일>`, `nod project <프로젝트>` |

받은 일함을 언제 비웠는지, 이번 주에 무엇을 끝냈는지도 이력에 남지만, 그걸 보여 주는 명령은 주간 리뷰를 옮기는 G4 에서 만듭니다.

### 정한 것과 이유

- 칸은 지금 쓰는 GTD 앱(Mindwtr)의 실제 쓰임을 세어 정했습니다(항목 161개, 프로젝트 6개). 상황은 항목마다 0~1개라 한 칸입니다. 대기 6개 중 5개가 사람을 기다려서 기다리는 사람 칸을 두었고, 링크가 110개라 링크 표를 두었습니다. 체크리스트는 대부분 nod 결정을 옮겨 적은 것이라 두지 않았습니다. 태그·영역·예상 시간은 거의 쓰지 않아 뺐고, 날짜(마감·시각·반복·오늘 집중)는 G3 에서 다룹니다.
- 상태는 GTD 의 목록을 그대로 씁니다: inbox·next·waiting·someday·reference·done·dropped. 지우지 않고 dropped 로 둡니다. 상태 값은 작업 상태처럼 코드(`todos.ts`)에서 검사하고 DB 의 check 제약은 두지 않습니다. SQLite 의 check 제약은 표를 다시 만들어야 바뀌는데, 이 표를 가리키는 외래 키 때문에 마이그레이션 안에서 다시 만들기가 어렵습니다. 상태 하나를 더할 때마다 그 비용을 치르지 않으려는 것입니다.
- 받아 적기는 판단 없이 가장 빨라야 해서 `nod in` 하나로 둡니다. 정리는 `nod todo set` 한 명령으로 여러 칸을 한 번에 바꿉니다. 에이전트가 명료화 결과를 한 번에 반영하기 쉽고, 바뀐 칸들이 이력 한 줄로 남습니다.
- 할 일은 `t<번호>`, 프로젝트는 `p<번호>` 로 쓰고, 맨 숫자는 받지 않습니다. `nod 12 …` 는 결정에 답하고 `nod drop 12` 는 작업을 끝내므로, `todo` 를 빠뜨린 명령이 결정이나 작업으로 가지 않게 하려는 것입니다. 같은 이유로 프로젝트 이름은 `p3`·`3` 처럼 생길 수 없습니다.
- 할 일과 프로젝트의 이력(`todo_changes`, `project_changes`)에는 칸마다 전·후 값과 누가 바꿨는지를 남깁니다. 누가는 실행한 곳으로 정합니다. `NOD_ACTOR` 가 있으면 그 값(웹 화면은 `human:ui`), nod 워커면 `worker:<작업>`(nod 가 워커 환경에 `NOD_TASK` 를 넣음), Claude 세션이면 `claude:<세션 ID 앞 8자>`, 그 밖은 `human` 입니다. 이 값은 누가 실행했는지이지, 사람이 확인했는지가 아닙니다. 사람이 채팅으로 확인하고 Claude 가 반영한 변경도 `claude:…` 입니다. 확인 여부를 따로 남길지는 사람 확인 없이 해도 되는 일의 경계를 정하는 G4 에서 정합니다.
- 끝났거나 버린 프로젝트에는 열린 할 일이 있을 수 없습니다. 열린 할 일이 남은 프로젝트는 끝낼 수 없고, 끝난 프로젝트로 열린 할 일을 옮기거나 그 안의 할 일을 다시 열 수도 없습니다. 끝난 프로젝트 아래의 다음 행동은 프로젝트 점검에서 빠지기 때문입니다.
- 언젠가(someday)로 미룬 프로젝트의 할 일은 목록에서 빠집니다. 프로젝트를 미루면 그 행동도 미룬 것이기 때문입니다. `--project` 로 그 프로젝트를 고르거나 `--all` 이면 보입니다.
- 상황은 `@` 로 시작하게 맞춥니다(`phone` 과 `@phone` 은 같은 상황). 상황이 없는 할 일은 어디서나 할 수 있는 일로 보고, 상황으로 거를 때도 함께 보입니다. 실측에서 다음 행동 14개 중 13개가 상황이 없었습니다.
- 대기에서 벗어나면 기다리던 사람을 지웁니다(이력에는 남음). 나중에 다시 대기로 바꿀 때 예전 사람이 그대로 남지 않게 하려는 것입니다.
- 같은 통로의 같은 키는 한 번만 들어갑니다(유니크 인덱스). 업무 도구를 여러 번 훑어도 같은 항목이 두 번 들어가지 않습니다. 링크로도 중복을 가리는 일은 모으기를 옮기는 G4 에서 합니다.
- 장부를 열 때 `busy_timeout` 을 WAL 전환보다 먼저 겁니다. 반대 순서에서는 여러 프로세스가 동시에 열면 30번 중 1번꼴로 `database is locked` 가 났습니다. 마이그레이션은 immediate 트랜잭션 안에서 버전을 다시 읽어, 동시에 연 다른 프로세스가 같은 마이그레이션을 두 번 돌리지 않게 합니다. 고친 뒤 동시 받아 적기 150번이 모두 들어갔습니다.
- 장부의 트랜잭션은 모두 쓰기 때문에 모두 immediate 로 엽니다. `Ledger` 가 여는 연결이 `transaction()` 의 기본값을 바꾸므로, 할 일 표와 스크립트의 트랜잭션도 같이 바뀝니다. 지연(deferred) 트랜잭션이 먼저 읽고 나중에 쓰면, 그 사이 다른 프로세스가 쓰기 잠금을 잡았거나 커밋했을 때 SQLite 는 `busy_timeout` 만큼 기다리지 않고 바로 `database is locked` 를 돌려줍니다(WAL). CLI·Stop 훅·tick 이 같은 장부에 동시에 쓰는 동안, 앞 작업을 읽고 새 작업을 넣는 `add` 가 이렇게 실패했습니다(시험 하나를 반복하면 10번 중 2번). immediate 트랜잭션은 BEGIN 에서 쓰기 잠금을 기다렸다가 잡습니다. 트랜잭션 밖에서 읽는 쪽은 WAL 에서 쓰는 쪽을 기다리지 않으므로 줄을 서는 것은 쓰는 쪽뿐이고, 읽기만 하는 트랜잭션은 없습니다.
- 개발 중 주의: `ui/` 개발 서버가 켜져 있으면, 코드가 바뀔 때 서버가 장부 모듈을 다시 불러오면서 새 마이그레이션을 실제 장부(`<홈>/nod.db`)에 바로 적용합니다. 커밋 전에 마이그레이션을 고쳐야 하면 서버를 끄고 고칩니다.

## 할 일 맡기기 (G2, 2026-10-20)

사람이 하지 않아도 되는 할 일은 nod 작업에 맡깁니다. 맡긴 할 일은 작업을 기다리는 대기가 되고, 작업이 끝나면 저절로 바뀝니다. 이 단계는 이슈 #3 입니다.

### 맡긴 할 일로 답하는 질문

| 누가 | 질문 | 데이터 | 명령 |
|---|---|---|---|
| 사람 | 무엇을 누구에게 기다리고 있고, 얼마나 됐나? | 대기인 할 일, 기다리는 사람 또는 아직 진행 중인 작업과 그 상태, 대기를 시작한 시각 | `nod todo waiting` |
| 사람 | 맡긴 할 일의 작업이 끝났나? 무엇을 남겼나? | 할 일에 붙은 작업들의 상태, 마지막 보고 한 줄, 링크 | `nod todo <할 일>` |
| 사람 | 지금 답해야 할 결정은? | 열린 결정(다음 행동의 맨 위) | `nod todo`, `nod todo next` |
| 사람 | 결정만 남은 프로젝트가 "다음 행동 없음"으로 잘못 뜨지 않나? | 열린 결정을 그 프로젝트의 다음 행동으로 셈 | `nod project` |
| 사람 | 이 작업은 어느 할 일을 하나? | 작업의 할 일 칸(`tasks.todo_id`) | `nod show <작업>` |

### 정한 것과 이유

1. **맡기기는 `nod add --todo t<번호>` 입니다.** 새 명령을 만들지 않고 `nod add` 의 옵션(레포·검증·순서)을 그대로 씁니다. 지시를 빼면 할 일의 제목과 메모가 지시가 됩니다. 정리를 마친 할 일은 이미 무엇을 할지 말하고 있기 때문입니다.
2. **맡기는 명령을 실행하는 것이 곧 승인입니다.** 작업은 `nod add` 처럼 바로 시작합니다. 이슈에서 정할 것으로 남긴 질문입니다. "맡길 일" 표시만 해 두는 상태를 따로 두지 않은 이유는 두 가지입니다. `nod add` 도 확인 없이 시작하고, 표시만 하고 시작하지 않은 일이 쌓이면 그것을 다시 점검해야 하기 때문입니다.
3. **할 일과 작업을 잇는 칸은 작업 쪽에 둡니다**(`tasks.todo_id`, 마이그레이션 v11). 한 할 일을 다시 맡기거나, `--after` 로 이은 여러 작업에 나눠 맡길 수 있습니다.
4. **맡긴 할 일은 대기이고 기다리는 사람 칸은 비워 둡니다.** 기다리는 사람 칸은 사람을 위한 글이기 때문입니다. 대기이면서 기다리는 사람이 없고 진행 중인 작업이 붙어 있으면 nod 를 기다리는 것으로 보고, 목록에는 `waiting on task #5 (running)` 처럼 나옵니다. 사람을 기다리는 대기와 같은 칸(대기를 시작한 시각)을 쓰므로 `nod todo waiting` 하나로 둘 다 봅니다.
5. **작업이 더 나아갈 수 없게 되면 할 일이 따라 바뀝니다.** 마지막 작업이 성공하면 끝남(done)이 되고, 취소되면 다음 행동(next)으로 돌아옵니다. 오류로 멈춘 작업은 `nod resume` 으로 이어갈 수 있으므로 할 일은 대기로 둡니다. 작업이 여럿이면 모두 끝나야 바뀝니다.
6. **`nod drop` 으로 작업을 끝내면 할 일은 다음 행동으로 돌아옵니다. 할 일을 버리지 않습니다.** 이슈에서 정할 것으로 남긴 질문입니다. 작업을 끝내는 흔한 이유는 일이 필요 없어져서가 아니라 워커가 막혀서 사람이 직접 하려는 것입니다. 할 일을 버리면 해야 할 일이 조용히 사라집니다. 정말 필요 없으면 `nod todo drop` 한 번으로 버릴 수 있습니다.
7. **따라 바꾸기는 워커의 Stop 훅과 `nod drop` 에서 돌고, 대기이면서 기다리는 사람이 없는 할 일을 모두 훑습니다.** 작업을 취소하면 그 뒤에 오던 작업도 함께 취소되는데, 그 작업들의 할 일도 함께 돌려놓기 위해서입니다. 작업이 끝난 뒤에 사람이 다시 대기로 둔 할 일은 건드리지 않습니다(작업이 끝난 시각이 대기를 시작한 시각보다 앞섬). 웹 화면의 답하기도 같은 함수를 거칩니다.
8. **따라 바꾼 변경의 누가(`actor`)는 `nod` 입니다.** 훅이 도는 환경에는 `NOD_TASK` 가 있어서 환경으로 정하면 `worker:<작업>` 이 되지만, 실제로 바꾼 것은 워커가 아니라 nod 입니다.
9. **결과 한 줄과 링크는 할 일에 옮겨 적지 않고 작업에서 읽어 보여 줍니다.** 작업이 성공한 뒤에 `nod link` 로 붙는 PR 링크도 바로 보이고, 같은 값이 두 곳에 있다가 어긋날 일이 없습니다.
10. **열린 결정은 다음 행동 목록의 맨 위에 `#<결정> decide` 로 나옵니다.** 결정마다 할 일을 따로 만들지 않습니다. 결정은 워커를 세워 두므로 다른 다음 행동보다 앞에 둡니다. 결정에는 상황이 없어 어떤 상황으로 걸러도 보이고, `--project` 로 거르면 그 프로젝트의 할 일을 맡은 작업의 결정만 보입니다. 프로젝트 집계에서도 다음 행동으로 셉니다.
11. **`todos.ts` 는 장부(`Ledger`)를 통해 작업과 결정을 읽고, 할 일 표에만 씁니다.** 장부는 할 일을 모릅니다. 장부가 `todos.ts` 를 부르면 서로를 부르는 순환이 생기므로, 따라 바꾸는 호출은 `worker.ts` 에 둡니다.

하지 않은 것: 할 일을 끝내거나 버려도 맡긴 작업은 멈추지 않습니다. 지금 nod 에서 작업을 멈추는 길은 결정을 `nod drop` 하는 것뿐이라, 멈추는 명령이 필요해지면 그때 만듭니다.

## 일정과 오늘 보기 (G3, 2026-10-20)

캘린더에는 그날이나 그 시각에 꼭 해야 하는 것만 둡니다. `nod today` 는 캘린더의 일정과 그날의 할 일을 한 화면에 보여 줍니다. 이 단계는 이슈 #4 입니다.

### 답하는 질문

| 누가 | 질문 | 데이터 | 명령 |
|---|---|---|---|
| 사람 | 오늘 꼭 해야 하는 것은? | 캘린더 일정, 지난 마감과 놓친 예정, 오늘 예정, 오늘 마감, 오늘 집중 | `nod today` |
| 사람 | 내일은 무엇이 있나? (내일 준비) | 같은 것을 내일 기준으로 | `nod today tomorrow` |
| 사람 | 아직 손댈 수 없는 일이 목록을 어지럽히지 않나? | 시작일 | `nod todo` (시작일 전이면 빠지고, `--all` 이면 보임) |

### 정한 것과 이유

1. **일정은 읽기만 합니다.** 이슈에서 정할 것으로 남긴 질문입니다. 회의 초대·참석자·회의실은 캘린더 서비스가 이미 하고 있고, nod 가 일정을 쓰면 두 곳의 일정이 어긋나기 때문입니다.
2. **칸은 마감(`due`), 예정(`scheduled`, 명령에서는 `--on`), 시작일(`start`), 반복(`repeat`), 오늘 집중(`focus`)입니다.** 지금 쓰는 GTD 앱에서는 마감 13건, 시각이 있는 것 3건, 반복 한 묶음(주간 리뷰, 금요일 17:00), 오늘 집중 8건을 썼습니다. 마감과 예정을 나눈 것은 GTD 에서 둘의 뜻이 달라서입니다. 마감은 "그때까지" 끝내야 하는 것이고, 예정은 "그날, 그 시각에" 해야 하는 것입니다.
3. **날짜는 사람이 쓴 그대로 지역 날짜·시각의 글자로 둡니다**(`YYYY-MM-DD`, 시각이 있으면 ` HH:MM`). 다른 시각 칸처럼 UTC 로 두면 날짜만 있는 마감도 시각으로 바꿔야 하고, 17:00 이 시간대에 따라 다른 시각이 됩니다. 이 형식은 글자 그대로 정렬하고 비교할 수 있습니다. 입력은 `today`·`tomorrow` 도 받습니다.
4. **오늘 집중은 고른 날짜를 남깁니다.** 그 날짜에만 오늘 집중이고, 다음 날이면 저절로 풀립니다. 지금 앱은 집중 표시가 날짜 없이 남아서 엿새 동안 방치된 적이 있습니다. 내일 준비에서 `--focus tomorrow` 로 미리 고를 수도 있습니다.
5. **반복은 매일·매주·매달(`daily`·`weekly`·`monthly`)입니다.** 끝내면(done) 다음 것이 생깁니다. 다음 날짜는 끝낸 날이 아니라 원래 일정에서 한 주기씩 밀어, 오늘 뒤의 첫 날로 정합니다(지금 앱의 strict 방식과 같음). 그래서 늦게 끝내도 다음 것이 처음부터 지난 마감이 되지 않습니다. 날짜가 여럿이면 모두 같은 주기만큼 밀고, 31일은 짧은 달의 말일이 되었다가 그다음 달에는 다시 31일이 됩니다(29·30일도 같음). 처음에는 직전 것에서 한 달을 더해, 1월 31일이 2월 28일 뒤로 3월 28일·4월 28일로 굳었습니다(리뷰). 그래서 말일에 있는 날짜는 반복이 붙인 키(`t<번호>`)로 앞 것을 거슬러 원래 날을 찾습니다. 장부에 칸을 더하지 않으려는 것입니다. 사람이 날을 옮기면 그 날이 이어집니다. 버리면(dropped) 반복이 끝납니다. 다시 열었다 끝내도 다음 것은 한 번만 생깁니다(키 `t<번호>`). 다음 것은 출처를 이어받습니다(G4). 반복하려면 마감·예정·시작일 중 하나는 있어야 합니다. 매년이나 N일마다는 쓰는 곳이 없어 넣지 않았습니다.
6. **시작일 전인 할 일은 목록에서 빠지고 `--all` 일 때만 보입니다.** 프로젝트 보기와 "열린 할 일이 남은 프로젝트는 끝낼 수 없음" 검사에는 그대로 들어갑니다. 아직 시작하지 않았어도 열린 할 일이기 때문입니다.
7. **오늘 보기는 일정, 지난 것, 예정, 마감, 집중 순서입니다.** 지난 것은 마감이나 예정이 그날보다 앞서는 열린 할 일입니다. 놓친 예정도 여기에 넣어, 그날 해야 했던 일이 조용히 사라지지 않게 합니다. 한 할 일은 처음 해당하는 묶음에 한 번만 나옵니다.
8. **캘린더 연결부는 gtd 레포의 macOS 캘린더 코드(EventKit 앱)를 옮겼습니다.** 캘린더 권한이 앱에 붙기 때문에 앱 번들로 빌드합니다. 빌드 결과는 레포가 아니라 nod 홈(`<홈>/CalendarEvents.app`)에 둡니다. 그래서 테스트는 임시 홈을 쓰므로 실제 캘린더를 읽지 않습니다.
9. **읽지 못한 캘린더가 빈 일정처럼 보이지 않게 합니다.** 권한이 없거나 샌드박스 안이면 EventKit 이 오류 없이 빈 결과를 줄 수 있어서(gtd 에서 2주에 0건을 원인을 모른 채 본 적이 있음), 보이는 캘린더가 하나도 없으면 앱이 오류를 냅니다. 읽기가 실패하면 `nod today` 는 할 일은 보여 주되 "일정을 읽지 못해 보여 주지 않는다"고 이유와 함께 적습니다. 앱이 없으면 빌드하는 방법을 알립니다. 첫 읽기는 권한 창을 기다리므로 60초가 지나면 그만둡니다.

**실측 (2026-10-20, macOS 27.0.1).**

- Claude Code 세션의 Bash 에서 처음 `nod today` 를 돌리자 앱이 캘린더 권한을 기다리며 90초 넘게 멈췄다가 끝났습니다. 그래서 60초 제한을 넣었습니다. gtd 때와 달리 `open` 이 -10825 로 실패하지는 않았습니다.
- 4주(10/6~11/2)를 읽으니 일정은 공휴일 캘린더의 하루 하나뿐이었습니다. 업무 일정을 보려면 캘린더 앱에 그 계정을 붙여야 합니다.

하지 않은 것: 일정 쓰기, 일정에서 할 일 후보 만들기(회의 준비·초대 답하기는 모으기를 옮기는 G4), 시각이 됐을 때 알리기, macOS 밖의 캘린더 연결.

## gtd 스킬 옮기기 (G4, 2026-10-21)

지금 gtd 스킬로 하는 GTD 절차를 nod 스킬로 옮깁니다. 절차는 GTD 앱 대신 nod 명령을 부르고, 업무 도구 연결부는 `skills/nod/sources/` 로 옮깁니다. 이 단계는 이슈 #5 입니다.

### 답하는 질문

| 누가 | 질문 | 데이터 | 명령 |
|---|---|---|---|
| 사람 | 시스템을 믿어도 되나? | 받은 일함 건수와 가장 오래된 날, 지난 것, 오늘 것, 다음 행동이 없는 프로젝트, 기록 없이 7일 넘은 사람 대기, 마지막 주간 리뷰 | `nod todo check` |
| 사람 | 오늘 첫 세션에서 놓치면 안 되는 것은? | 위 숫자 중 손볼 것이 있는 것만 한 줄로 | `nod todo check --nudge` (SessionStart 훅) |
| 스킬 | 이 항목이 장부에 이미 있나? 할 일의 칸 전체는? | 통로·키, 할 일의 모든 칸과 링크 | `nod in --source … --key …`, `nod todo --json` |

### 정한 것과 이유

1. **전환은 Mindwtr 데이터를 옮기는 날(G6)에 합니다.** 이 단계에서는 절차와 연결부를 nod 스킬에 만들어 두기만 하고, 스킬의 호출 문구, 하루 첫 세션 훅, 개인 설정 파일 이동은 그날 바꿉니다. 지금 바꾸면 "할 일 정리하자"에 두 스킬이 함께 반응해 받은 일함이 둘이 됩니다. 그때까지 SKILL.md 에는 원본이 gtd 스킬이라는 한 줄을 둡니다.
2. **사람 확인 없이 하는 일의 경계**: 받아 적기와 읽기(목록·오늘 보기·점검·끝났는지 확인)는 확인 없이 합니다. 명료화 반영, 완료와 버림, 프로젝트 만들기·닫기, 작업 맡기기, 바깥에 쓰기는 확인을 받습니다. 사람 없이 돌 때는 받아 적기와 확실한 완료만 합니다. 이슈에서 정할 것으로 남긴 질문이고, 제안대로 정했습니다. 확인했다는 표시는 장부에 따로 남기지 않습니다. 누가는 실행한 곳이고, 스킬이 확인받은 것만 반영하기 때문입니다.
3. **휴대폰 받아 적기는 Slack 의 "나에게 보내기"입니다.** 밖에서 떠오른 일을 나에게 보내 두면, Slack 연결부가 모으기 때 그 DM 을 읽어 후보로 올립니다. 메시지 시각을 키로 넣어 한 번만 들어옵니다. 이것도 이슈에서 정할 것으로 남긴 질문입니다.
4. **믿음 숫자는 순수 함수 하나(`trust.ts`)로 계산합니다.** 장부를 읽는 일은 `Todos.trust` 가 하고, 계산은 입력만 받는 함수가 합니다. 숫자마다 정한 것은 아래와 같습니다.
   - 사람 대기는 할 일에 마지막으로 기록이 남은 때부터 셉니다(대기 시작 시각이 아님). 다시 물었으면 `--add-note '<날> 다시 물음'` 으로 기록을 남기고, 그날부터 다시 셉니다. 장부에 칸을 더하지 않고 이력으로 셉니다.
   - 마지막 주간 리뷰는 출처가 `review` 인 할 일 중 마지막으로 끝낸 때입니다. 반복 할 일의 다음 것은 출처를 이어받도록 바꿨습니다(G3 에서는 출처가 `repeat` 였음). 그래서 매주 생기는 "주간 리뷰하기"가 모두 같은 출처를 가집니다. 리뷰를 따로 적는 표를 두지 않은 것은, 같은 일을 두 곳에 적게 되기 때문입니다.
   - 지난 것과 오늘 것은 오늘 보기(`Todos.day`)의 묶음을 그대로 씁니다.
5. **하루 첫 세션 알림은 `nod todo check --nudge` 입니다.** 하루 한 번만(nod 홈의 `.nudged`), nod 워커 안에서는 띄우지 않고(`NOD_TASK`), 손볼 것이 없으면 아무것도 출력하지 않습니다.
6. **에이전트용 출력은 `--json` 입니다.** 사람용 목록은 제목을 80자에서 자르고 구분자가 제목 안에도 나올 수 있어서, 스킬이 판단할 때는 할 일 하나를 JSON 한 줄로, 링크와 함께 받습니다. 링크로 중복을 가리는 일도 이것으로 합니다. 업무 도구에서 가져오는 항목은 원본 ID 를 키로 넣어 장부가 거르고, 키가 없는 경로로 들어온 같은 링크는 스킬이 `--json` 의 링크로 봅니다.
7. **메모에 한 줄 더하기(`--add-note`)를 만들었습니다.** 완료 근거, 다시 물은 날처럼 절차가 메모에 기록을 더하는 일이 잦은데, `--notes` 로 메모 전체를 다시 쓰면 있던 내용을 잃기 쉽습니다.
8. **영역과 목표는 장부가 아니라 profile.md 에 둡니다.** 주간 리뷰에 영역마다 진행 중인 프로젝트나 다음 행동이 있는지 보는 단계를 더했습니다. 영역에 할 일을 매달 일이 생기면 그때 장부에 칸을 둡니다.
9. **앞으로 2주를 보도록 `nod today --days <n>` 을 만들었습니다.** 둘째 날부터는 무언가 있는 날만 보여 줍니다.
10. **개인 설정은 nod 홈(`config.json`, `profile.md`)에서 읽습니다.** Mindwtr 칸은 뺐습니다. 연결부 스크립트는 `sources/config.ts` 로 읽습니다.
11. **옮기지 않은 것**: Mindwtr 설치·로컬 API 문서, nod 알림 스크립트(G2 부터 nod 가 맡긴 할 일을 스스로 닫음), macOS 캘린더 연결부(G3 에서 `nod today` 로 옮김).

**실측 (2026-10-21).** 옮긴 연결부를 실제 설정으로 돌렸습니다. Plane 은 프로젝트 3개에서 항목 11개를 읽었고, Forgejo 는 gtd 쪽 스크립트와 출력 줄 수(32줄)가 같았습니다. 새 문서에 적힌 `nod` 명령 31개를 임시 홈에서 차례로 실행해 모두 정상 종료하는 것을 봤습니다.

**사람 없이 도는 내일 준비: 워커는 보고하고 nod 가 받아 적습니다.** gtd 에서는 nod 트리거의 워커가 GTD 앱의 MCP 로 받아 적었습니다. nod 장부에 받아 적으려면 워커가 `~/.nod/nod.db` 에 써야 하는데, 워커의 샌드박스는 작업 폴더 밖에 쓰지 못하고 장부를 열지도 못합니다(WAL 모드는 읽을 때도 쓰기가 필요함).

- **쓰기 경로를 열지 않았습니다.** Claude Code 에는 쓰기 경로를 더하는 설정(`sandbox.filesystem.allowWrite`)이 있지만, nod 홈을 열면 워커가 `notify`(nod 가 샌드박스 밖에서 실행)와 장부의 규칙(모든 워커가 받음)·작업·결정까지 고칠 수 있습니다. 그러면 샌드박스와 독립 리뷰가 지키던 경계가 무너집니다.
- **워커는 보고에 `NOD: in {…}` 줄을 쓰고, nod 가 그 작업의 done 을 받아들일 때 받은 일함에 넣습니다.** 사용자가 정한 방식입니다(2026-10-21). 받은 일함에만 넣으므로 확인 없이 해도 되는 받아 적기의 경계 안입니다. 누가는 `worker:<작업>` 입니다. 무엇을 넣을지는 워커가 판단했고 nod 는 적기만 했기 때문입니다. 넣는 일과 작업 성공은 한 트랜잭션입니다.
- **읽을 수 없는 줄은 검증 실패처럼 워커에게 돌려보냅니다.** 형식이 틀린 줄을 건너뛰면 받아 적을 것이 조용히 빠집니다. 한 보고에 50줄이 넘어도 돌려보냅니다. 바깥 글에 속은 워커가 받은 일함을 쏟아내지 않게 하려는 것입니다.
- **데이터는 트리거의 `--source`(`tomorrow.ts`)가 샌드박스 밖에서 모읍니다.** 다음 근무일을 키로 한 줄을 내므로 하루에 작업 하나가 생깁니다. 도구 하나가 실패하면 줄 전체가 실패합니다. 도구 하나가 빠진 준비는 다 된 것처럼 보이기 때문입니다. MCP 로 읽는 도구는 워커가 쓰려면 사람의 허락이 필요해 넣지 않았습니다.
- 다시 묻기 후보의 키에 쓰도록 `nod todo check --json` 의 오래된 대기에 마지막 기록 날(`since`)을 넣었습니다. 날짜 계산을 워커에게 맡기지 않으려는 것입니다.

실측: `tomorrow.ts` 를 실제 설정(Plane·Forgejo 켬)으로 돌려 한 줄(약 5KB)이 나오는 것을 봤습니다. 받아 적기는 가짜 에이전트로 시험했습니다. 실제 트리거로 돌린 것은 아직입니다.

## 웹 화면의 할 일 (G5, 2026-10-21)

GTD 앱의 데스크톱 화면 대신 볼 화면입니다. 이 단계는 이슈 #6 입니다.

| 화면 | 보여 주는 것 | CLI 로는 |
|---|---|---|
| `/today` (G6 에서 `/focus` 로 합침) | 그날의 일정, 지난 것·예정·마감·집중, 믿음 숫자. Today·Tomorrow 로 바꿈 | `nod today`, `nod todo check` |
| `/inbox` (처음에는 `/todos`) | 받아 적기 입력창, 받은 일함(Next·Someday·Reference·Done·Drop 버튼) | `nod in`, `nod todo` |
| `/todos/<번호>` | 모든 칸 바꾸기(날짜는 날짜·시각 입력), 메모 한 줄 더하기, 끝내기·버리기, 링크, 맡긴 작업, 이력 | `nod todo set`, `nod todo <할 일>` |
| `/projects` | 프로젝트마다 열린 할 일과 다음 행동 수, 프로젝트 더하기, 언젠가로 미루기·끝내기 | `nod project` |

### 정한 것과 이유

1. **화면에서 바꾼 것의 누가는 `human:ui` 로 넘깁니다.** 화면 서버를 Claude 세션에서 띄우면 환경에 `CLAUDECODE` 가 있어서, 환경으로 정하면 화면에서 한 변경이 모두 `claude:…` 로 남습니다.
2. **목록의 규칙은 CLI 와 같습니다.** 화면 서버(`ui/src/todos.server.ts`)는 `Todos` 의 같은 메서드를 부르고, 무엇을 기다리는지(`Todos.waitingFor`)와 이력 문장(`changeText`, `src/view.ts`)은 CLI 와 함께 씁니다. 시작일 전인 할 일과 언젠가 프로젝트의 할 일은 목록에서 빠집니다.
3. **브라우저가 보낸 값은 두 번 봅니다.** 서버 함수의 검사기(`ui/src/input.ts`)가 모양(어떤 칸이 글자인지, 번호가 정수인지)을 보고, 값(상태·반복·날짜)은 서버에서 장부의 목록으로 봅니다. 상태 목록 같은 것을 브라우저에서 불러오면 장부 모듈(데이터베이스)까지 딸려 가기 때문입니다. 다른 사이트가 브라우저를 통해 장부를 바꾸지 못하게 막는 일은 작업 화면처럼 TanStack Start 의 기본 CSRF 미들웨어에 맡깁니다.
4. **캘린더는 5분 동안 캐시합니다.** 화면은 5초마다 새로 고치는데, 캘린더를 읽을 때마다 앱을 띄웁니다. 읽지 못한 결과도 캐시해서 이유를 보여 줍니다.
5. **할 일 상세 경로는 목록과 묶지 않습니다**(`todos_.$id.tsx`). 파일 이름이 `todos.$id.tsx` 면 목록 화면의 자식 경로가 되어, 목록에 자식을 그릴 자리가 없으면 상세 주소에서도 목록이 그려집니다.
6. **고치는 화면은 사람이 손댄 칸만 따로 들고, 나머지는 장부를 따릅니다.** 처음에는 장부에 변경이 기록될 때마다 폼을 다시 그려서, 다른 곳(작업·CLI)의 변경이나 같은 화면의 메모 한 줄 더하기에 저장하지 않은 제목·메모가 사라졌습니다(2026-10-23 리뷰). 이제 손대지 않은 칸은 새 값을 보이고, 손댄 뒤에 장부가 바뀌면 바뀌었다고 알립니다. 메모를 고치던 중에 더한 한 줄은 고치던 메모 아래에도 붙입니다. 그러지 않으면 저장이 고치던 메모로 덮어써 더한 줄이 사라집니다(리뷰). 저장은 손댄 칸만 보냅니다. 처음에는 모든 칸을 보내서, 마지막 새로 고침 뒤(5초 안)에 들어온 다른 곳의 변경을 화면이 가진 옛 값으로 되돌렸습니다(리뷰).

**실측 (2026-10-21).** 임시 장부로 띄운 화면을 헤드리스 브라우저로 눌러 봤습니다. 받아 적기, 받은 일함에서 다음 행동으로 정리, 상황으로 거르기, 상세 화면에서 마감·상황 저장, 메모 한 줄 더하기(이력의 누가는 모두 `human:ui`), 내일 보기, 프로젝트 미루기, 열린 할 일이 남은 프로젝트 끝내기 거절이 모두 동작했고 콘솔 오류는 없었습니다. 완료 기준인 "GTD 앱을 열지 않고 하루 보내기"는 Mindwtr 데이터를 옮긴 뒤(G6) 실제로 써 봐야 확인됩니다.

## Mindwtr 에서 옮기기 (G6, 2026-10-21)

Mindwtr 의 할 일을 nod 장부로 옮기고 gtd 레포를 닫습니다. 이 단계는 이슈 #7 입니다.

### 정한 것과 이유

1. **GTD 절차는 nod 스킬이 아니라 gtd 스킬 묶음(`skills/gtd`, `gtd:*`)에 둡니다.** G4 에서 절차를 nod 스킬로 옮겼더니 한 스킬이 오케스트레이션과 GTD 를 함께 맡아 커졌습니다. nod 스킬은 맡기기·결정·결과만 다루고, gtd 에 쌓인 할 일을 `nod add --todo` 로 받아 워커에게 시킵니다. GTD 절차는 할 일마다 작은 스킬(capture·today·scan·clarify·tomorrow·review·setup)로 나눠, 부른 절차의 문서만 읽히게 했습니다. 처음에는 첫 화면과 오늘 집중을 따로 뒀는데, 아침마다 이어서 부르고 "오늘 뭐 있어"와 "오늘 뭐 할까"가 헷갈려 `gtd:today` 하나로 합쳤습니다. 공통 규칙은 `skills/gtd/ledger.md` 한 곳에 두고 장부를 바꾸는 스킬만 읽습니다. 사람 없이 도는 내일 준비의 워커 지시는 `tomorrow/worker.md` 로 뗐습니다. 단계를 말하지 않고 "gtd" 라고만 하면 `gtd:today` 가 입구가 되어, 첫 화면을 보여 준 뒤 상태에 맞는 단계(묵은 받은 일함 → 비우기, 집중 없음 → 집중, 저녁 → 내일 준비, 리뷰 7일 넘음 → 주간 리뷰)로 잇습니다.
2. **웹에 Mindwtr 의 Focus 화면을 따로 둡니다(`/focus`).** 오늘 집중(여섯 개까지, Mindwtr 의 기본값 세 개는 실제로 쓰기에 적어 사용자가 늘림), 오늘 것(지난 것·오늘 예정·오늘 마감), 나머지 다음 행동(지난 집중이 먼저), 시작일이 오지 않은 다음 행동 순서입니다. 다 고르면 다른 할 일의 별이 사라집니다. 고르는 수가 적어야 고르는 의미가 있기 때문입니다. 장부는 개수를 막지 않습니다. Mindwtr 의 검토일 구역은 nod 에 그 칸이 없어 두지 않았습니다.
3. **가져오기는 한 번에 다 하거나 하나도 하지 않습니다.** `scripts/import-mindwtr.ts` 가 한 트랜잭션으로 넣고, 장부에 할 일이나 프로젝트가 이미 있으면 거절합니다. 끝나면 상태별로 Mindwtr 와 nod 의 건수를 나란히 출력하고, 다르면 오류로 끝냅니다.
4. **상태와 시각은 Mindwtr 에서 마지막으로 움직인 때를 따릅니다.** 보관된 항목은 취소 시각이 있으면 버림, 없으면 완료입니다. 지운 항목은 가져오지 않습니다. 할 일마다 이력 하나(누가 `import`)를 그 시각으로 남겨, 오래된 대기를 세는 기준이 가져온 날이 아니게 했습니다.
5. **업무 도구 링크에서 출처와 키를 다시 만듭니다.** Plane·Forgejo·GitHub PR·Slack 링크가 있으면 그 도구와 원본 ID 를 키로 넣어, 다음 모으기에서 같은 일이 다시 들어오지 않게 했습니다. 같은 키를 여러 할 일이 가지면 열린 것(없으면 마지막으로 바뀐 것)이 키를 갖고, 나머지는 `mindwtr`/원본 id 입니다. "주간 리뷰하기"는 출처 `review` 로 넣어 마지막 주간 리뷰가 이어집니다.
6. **nod 칸이 없는 것은 메모로 옮깁니다.** 설명, 끝나지 않은 체크리스트, 태그, 예상 시간, 맡은 사람(대기 상대가 아닐 때)입니다. 순서, 색, 프로젝트의 "순서대로" 표시는 옮기지 않았습니다.
7. **맡긴 작업은 설명 첫 줄의 `nod #N` 으로 다시 잇습니다.** 한 작업을 여러 할 일이 가리키면 열린 것(없으면 최신)에만 잇고, 나머지는 가져오기 결과에 보고합니다.
8. **웹 화면은 할 일을 고르는 흐름에 맞춰 다시 짰습니다.** 색과 카드를 입힌 뒤 화면마다 하는 일로 다시 보니 쓰기 불편한 곳이 있어 고쳤습니다.
   - **Today 를 Focus 에 합쳐 아침 화면을 하나로 했습니다.** 둘 다 "오늘" 화면이라 어느 쪽을 열지 모호했고, Today 의 숫자 카드는 대부분 0 이었습니다. 이제 Focus 맨 위에 손볼 것과 일정이 나옵니다. 손볼 것은 0 이 아닌 것만 보이고, 기준은 첫 세션 알림과 같습니다(`src/trust.ts` 의 `inboxSince`·`reviewDue` 를 함께 씀). 내일은 `nod today tomorrow` 와 `gtd:tomorrow` 로 봅니다.
   - **별은 늘 보이고, 상태 메뉴는 목록의 상태와 다를 때만 보입니다.** 고르는 화면에서 고르는 별이 마우스를 올려야 나왔고, 다음 행동 열두 줄에 같은 `next` 칩이 붙어 가장 눈에 띄는 자리를 차지했습니다. 메뉴는 제목 아래 줄 끝으로 옮겼고, 목록과 같은 상태면 마우스를 올리거나 키보드로 갈 때 나타납니다.
   - **끝내거나 옮기면 6초 동안 되돌리기 알림을 띄웁니다.** 한 번 누르면 줄이 사라져 잘못 누른 것을 찾기 어려웠습니다. 반복 할 일을 끝낸 것은 되돌리지 않습니다. 다음 것이 이미 만들어져 있어서, 되돌리면 같은 일이 둘 열립니다.
   - **사이드바에 Mindwtr 처럼 접히는 Lists 묶음을 두었습니다.** Projects·Someday/Maybe·Waiting For 가 들어 있고, 언젠가와 대기는 Todos 에서 빼 각자 화면으로 옮겼습니다. 한 목록은 한 곳에만 둡니다. 언젠가 프로젝트는 Projects 화면에 그대로 있습니다.
   - **Todos 를 Inbox 로 줄였습니다(2026-10-23).** Todos 의 다음 행동은 Focus 와 같은 목록이었고, 열린 결정은 홈 화면과 사이드바에 이미 있었습니다. 그래서 Todos 에는 받아 적기와 받은 일함만 남기고 이름을 Inbox 로 바꿨습니다. 상황별 거르기는 Focus 의 다음 행동으로, 참고는 Focus 맨 아래 접힌 칸으로 옮겼습니다. 참고는 할 일이 아니라 찾아보는 것이라, 매일 여는 화면에서 접어 둡니다. Focus 맨 위 손볼 것도 각자 다루는 곳으로 잇습니다. 받은 일함은 Inbox, 오래된 대기는 Waiting For, 다음 행동이 없는 프로젝트는 Projects 화면의 그 프로젝트 카드입니다.
   - **끝없이 쌓이는 목록에는 상한을 둡니다(2026-10-23).** 사이드바의 정리한 작업은 모든 화면에 실려 5초마다 다시 오는데 상한이 없었고, Done 은 최근 100개만 보여 그보다 오래된 것은 찾을 수 없었습니다. 그래서 사이드바에는 최근에 정리한 20개와 전체 수만 싣고, 끝난 것은 할 일이든 작업이든 Done 에서 찾게 했습니다. Done 의 세 묶음(Done·Dropped·정리한 작업)은 100개씩 보이고 「Show more」로 100개씩 더 불러옵니다. 보이는 수는 주소의 검색 값(`?done=200&collected=300`)에 두어 새로 고침과 뒤로 가기 뒤에도 남습니다. 서버 함수는 잘못된 값과 5000 을 넘는 값을 막습니다. 페이지가 수천 줄을 5초마다 다시 만들지 않게 하려는 것입니다. 주소에 온 잘못된 값은 할 일 화면의 `?edit` 처럼 버려, 그 묶음이 처음 100개로 돌아갑니다. 그래서 한 묶음이 5000개를 넘으면 그보다 오래된 것은 화면에서 볼 수 없습니다. 그런 것은 CLI 로 찾습니다. 끝낸·버린 할 일은 `nod todo --all`(모든 상태, `--json` 이면 한 줄에 하나), 정리한 작업은 `nod ls --all` 입니다.
   - **날짜는 오늘 기준으로 씁니다**(today·tomorrow·이번 주 요일·N일 전, 그 밖은 날짜). 지난 날의 집중 표시는 감췄습니다. 어제 고른 표시가 오늘 것처럼 읽혔기 때문입니다.

**실측 (2026-10-21).** 실제 Mindwtr 데이터(지운 것을 빼고 할 일 112개, 프로젝트 6개)를 장부로 옮겼습니다. 상태별 건수가 모두 같았습니다(다음 행동 13, 대기 6, 언젠가 1, 참고 2, 완료 84, 버림 6). 링크 113개가 들어왔고, 업무 도구 키가 붙은 할 일은 60개(Plane 26, Forgejo 19, Slack 15)입니다. 맡긴 할 일 16개가 작업에 이어졌고, 한 작업을 할 일 셋이 가리킨 경우가 한 번 있었습니다. 같은 데이터를 장부 사본에 먼저 넣어 결과가 같은 것을 본 뒤 실제 장부에 넣었습니다. 새 세션에서 `gtd:` 스킬 7개와 `nod` 가 보이고, "gtd"·"지금 뭐 하지"·"받은 일함 정리"·"내일 준비해 줘"가 각각 today·today·clarify·tomorrow 로 가는 것을 확인했습니다.

## 대기 감시 (2026-10-21)

기다리는 일 가운데에는 그 일이 일어났는지 명령 하나로 확인할 수 있는 것이 있습니다. 브랜치가 push 됐는지, PR 이 머지됐는지, 파일이 생겼는지 같은 것입니다. 이런 대기에 감시를 걸어 두면 nod 가 확인하다가, 일어나면 다음 행동으로 돌려놓습니다.

### 답하는 질문

| 누가 | 질문 | 데이터 | 명령 |
|---|---|---|---|
| 사람 | 기다리던 일이 일어났나? 언제? | 다음 행동으로 돌아온 할 일, 메모의 통과 시각 한 줄 | `nod todo next`, `nod todo <할 일>` |
| 사람 | nod 가 지켜보는 대기는 무엇이고, 무엇으로 확인하나? | 대기 줄의 `watched` 표시, 감시 명령 | `nod todo waiting`, `nod todo <할 일>` |
| 작업 | 내가 했던 일에 기다리던 답이 왔나? 무엇이 왔나? | 감시가 출력한 내용 | 세션에 오는 메시지(`--back-to`, 10) |

### 정한 것과 이유

1. **감시는 할 일의 칸 하나입니다**(`todos.watch`, 마이그레이션 v13). 트리거로도 같은 일을 할 수 있지만, 할 일 하나를 기다리려고 source 스크립트와 알리기만 하는 워커 지시를 만들어야 했습니다. 감시는 기다리는 할 일에 붙어 있어서 대기가 끝나면 함께 사라집니다.
2. **세션이 아니라 nod 의 tick 이 돌립니다.** 대기는 며칠씩 걸리는데, Claude 세션의 백그라운드 감시는 세션을 닫으면 조용히 멈춥니다. 트리거처럼 `nod schedule on` 으로 켠 매분 tick 이 돌립니다. 감시 명령은 분이 5의 배수일 때만 돌립니다. 대부분 다른 서비스에 묻는 명령이라 매분은 과하기 때문입니다. 그 tick 이 밀려 건너뛰면 다음 5의 배수 분에 돕니다. 사람이 `nod tick` 을 직접 부르면 그 자리에서 감시와 완료 신호에 따른 정리(gc)를 모두 돌리고, 정리한 작업 번호를 출력합니다. 같은 서비스를 한꺼번에 부르지 않도록 하나씩 돌립니다.
3. **0 으로 끝나면 통과, 셸이 실행할 수 없으면(126·127) 끝, 그 밖은 모두 아직입니다.** 네트워크가 끊겨 실패한 것도 아직으로 봅니다. 노트북은 자주 잠들고 네트워크도 자주 바뀌기 때문입니다. 걸 때는 되던 명령을 tick 에서 찾지 못하면(스케줄을 PATH 가 다른 셸에서 다시 켠 경우) 영영 통과하지 않으므로, 그 할 일을 다음 행동으로 돌리고 메모에 `<시각> watch cannot run (<이유>): <명령>` 을 남기고 `watch_failed` 를 알립니다. 그 밖의 이유로 영영 실패하는 감시는 `nod todo check` 의 오래된 대기(7일)로 드러납니다. 기다리는 사람이 없고 감시만 있는 대기도 여기에 들어갑니다. 그 전에도 사람이 볼 수 있도록, 감시를 돌릴 때마다 결과를 남깁니다(9).
4. **걸 때 tick 과 같은 PATH 로 한 번 돌려 보고, 어떻게 끝났는지 남깁니다.** 문법이 틀린 명령(`sh -n` 으로 실행 없이 검사), 이미 통과하는 명령, 셸이 실행할 수 없는 명령은 거절합니다. 그 밖의 실패는 "아직"과 구별할 수 없으므로 종료 코드와 출력을 첫 확인 기록으로 남기고 보여 줍니다. PATH 와 Claude 설정 말고 이 셸에만 있는 환경 변수(토큰 같은 것)는 tick 에 없으므로, 그런 것에 기대는 감시는 여기서 통과해도 tick 에서 실패할 수 있습니다. 레포 밖에서 git 을 부른 감시라면 거기에 `not a git repository` 가 보입니다. 할 일 번호·상태 같은 다른 검사를 먼저 하고 나서 돌립니다. 트리거의 source 를 등록할 때 한 번 돌려 보는 것과 같습니다.
   - **감시는 `<홈>` 에서 돕니다.** 레포에 묻는 명령은 `cd <레포> && …` 나 `gh -R <owner/repo>` 처럼 대상을 명령 안에 적습니다. 실행 폴더 칸을 따로 두지 않은 것은, 명령만 보고도 어디서 무엇을 묻는지 알 수 있게 하려는 것입니다.
   - **한 번 도는 데 60초까지입니다.** 감시는 자기 프로세스 그룹에서 돌고, 시간이 지나면 그룹째 끝냅니다. `sh` 만 끝내면 파이프로 이어진 명령이 출력을 붙잡고 있어서 기다림이 끝나지 않았습니다(실측: 0.3초 제한에 3초). 명령이 끝나면(시간이 지나 그룹째 끝낸 경우도) 출력이 닫히기를 0.5초만 더 기다리고, 그때까지 읽은 출력으로 돌아옵니다. 백그라운드로 남긴 프로세스나 그룹을 벗어난 자손(`setsid`, 그룹째 끝내도 살아남음)이 출력을 붙잡고 있을 수 있기 때문입니다(실측: 0.3초 제한에 4초였음). 남긴 프로세스는 끝내지 않고, 놓은 파이프 읽기는 취소합니다. 취소하지 않으면 그 자손이 끝날 때까지 nod 프로세스가 내려가지 않았습니다(실측). 트리거의 source 와 `<홈>/notify` 도 같은 길로 돌립니다.
   - **비밀을 넣지 않습니다.** 명령은 할 일 기록과 메모, 알림에 그대로 남습니다. 토큰은 `gh auth` 같은 도구 로그인이나 환경 변수에 둡니다.
5. **통과하면 끝남이 아니라 다음 행동으로 돌립니다**(`--back-to` 가 없으면, 10). 기다리던 일이 일어나면 보통 사람이 이어서 할 일이 생기기 때문입니다(push 를 받으면 그 위에 PR 을 올리는 식). 기다리는 사람과 감시를 비우고, 메모에 `<시각> watch passed: <명령>` 한 줄을 더합니다. 누가는 `nod` 이고, `<홈>/notify` 에는 `watch_passed` 이벤트가 갑니다. 명령이 도는 동안 사람이 할 일을 옮겼거나 감시를 바꿨으면 그 결과는 버립니다.
6. **감시는 대기에만 걸 수 있고, 어떤 길로든(CLI·웹 화면·통과) 대기를 벗어나면 지워집니다.** 기다리는 사람 칸과 같은 규칙입니다. nod 작업에 맡긴 할 일(`nod add --todo`)은 작업이 끝나야 움직이므로, 맡길 때 감시를 지우고 작업이 도는 동안에는 감시를 걸 수 없습니다. 감시가 먼저 통과해 다음 행동이 되면 작업이 성공해도 nod 가 그 할 일을 닫지 못하기 때문입니다. 거꾸로, 작업이 끝난 뒤 감시를 건 할 일은 감시를 기다립니다. 사람이 `nod tell` 로 그 작업을 다시 돌려 작업이 또 끝나도 `followTasks` 는 감시가 걸린 대기를 옮기지 않습니다. 전에는 할 일을 닫으며 감시와 `--back-to` 를 지웠습니다(리뷰에서 재현).
7. **스케줄은 사람이 켜고 끕니다(`nod schedule on|off`).** 처음 구현은 감시나 트리거가 생기면 tick 을 등록하고, 지켜볼 것이 없으면 tick 이 스스로 내려갔습니다. 리뷰에서 이 방식 때문에 세 가지가 나왔습니다. 감시를 걸 때마다 tick 모듈을 그 셸의 `PATH`·`CLAUDE_CONFIG_DIR` 로 다시 써서 트리거 워커의 Claude 계정이 바뀌었고, tick 이 내려가는 순간 새 감시를 걸면 등록이 빠졌고, 내리기에 실패하면 없는 모듈을 매분 부르는 작업이 남았습니다. 등록을 풀면 지금 도는 tick 이 그 자리에서 멈춘다는 것(실측)도 순서를 까다롭게 했습니다. 그래서 등록을 기능에서 떼어, 사람이 한 번 켜면 끌 때까지 둡니다. 할 일이 없는 tick 은 장부를 열어 보고 바로 끝나므로 비용이 거의 없습니다. 실행 환경도 켤 때 한 번 정해지므로, 어느 세션에서 감시를 걸든 바뀌지 않습니다. 꺼져 있을 때 트리거나 감시를 등록하면 등록은 하되 꺼져 있다고 알려 줍니다.
8. **감시를 걸지는 세션이 묻습니다.** gtd 규칙(`skills/gtd/ledger.md`)에, 대기로 놓을 때 명령으로 확인할 수 있는 일이면 감시를 걸지 묻고 명령을 보여 준 뒤 확인받고 건다고 적었습니다. 감시 명령은 트리거의 source 처럼 사용자의 셸 권한으로 샌드박스 없이 돌기 때문입니다.
9. **감시를 돌릴 때마다 마지막 결과를 남깁니다**(`watch_checks`: 시각, 종료 코드, 출력 끝부분). 대기 목록에는 `watched, checked <시각>` 이, `nod todo <할 일>` 에는 종료 코드와 출력까지 보입니다. 통과하기 전까지 아무것도 보이지 않으면 사람은 nod 가 정말 지켜보고 있는지 알 수 없기 때문입니다. 스케줄이 꺼져 있으면 `not checked yet` 이나 오래된 시각으로 드러납니다. 확인은 할 일의 변경이 아니므로 할 일 기록에 넣지 않고 할 일마다 한 줄만 따로 둡니다. 감시가 바뀌거나 지워지면 그 줄도 지웁니다.
10. **`--back-to <작업>` 이 있으면, 통과할 때 사람 대신 그 작업에게 돌려줍니다**(`todos.back_to`, 마이그레이션 v15, 2026-10-22). 리뷰를 남기고 작성자의 답을 기다리는 일처럼, 답이 왔을 때 무엇을 할지 판단하려면 이전 작업의 맥락이 필요할 때가 많습니다. 새 워커를 띄우면 그 맥락을 처음부터 다시 쌓아야 합니다. 그래서 `nod tell` 과 같은 길로 그 작업의 세션을 다시 엽니다. 세션이 살아 있으면 메시지만 보내고, 닫혔으면 대화 기록에서 엽니다.
    - **세션에 가는 메시지**: 감시 명령과 그 출력을 데이터로 보내고, 무엇을 할지 정해 진행하라고 합니다. 출력은 남이 쓴 댓글일 수 있으므로, 붙여넣기 전에 줄바꿈·탭 말고 제어 문자를 지웁니다. `ESC[201~` 가 남아 있으면 붙여넣기가 일찍 끝나고 뒤 글자가 키 입력이 될 수 있기 때문입니다. 붙여넣는 메시지가 모두 지나는 `Terminals.send` 에서 지우므로 `nod tell` 과 답도 같습니다. 세션이 닫혀 있거나 Claude Code 가 다시 뜨는 중이면 메시지는 붙여넣기가 아니라 프롬프트 파일을 거쳐 실행 인자로 가므로, 붙여넣기가 일찍 끝나는 일이 없어 지우지 않습니다. 보내기·올리기·push·머지는 워커가 네트워크 없이 할 수 없으므로, 내보낼 내용을 써서 `NOD: question` 으로 사람에게 넘기라고 합니다. 할 게 없으면 무엇을 확인했는지만 말하라고 합니다. 허락이 필요한 일만 결정으로 사람에게 옵니다.
    - **돌려줄 작업은 감시가 끝났을 때의 `--back-to` 입니다.** 감시는 하나씩 60초까지 도므로, 그동안 사람이 `--back-to ''` 로 지우면 옛 작업이 아니라 사람에게 돌아옵니다. 감시를 끝내는 트랜잭션 안에서 읽습니다(`endWatch`). 그다음 `watch_passed` 알림보다 먼저 작업에 보냅니다. 감시를 비운 할 일은 작업이 메시지를 받을 때까지 아무것도 기다리지 않으므로, 그 사이에 tick 이 멈추면(`nod schedule off`) 그대로 남는 틈을 알림 시간만큼 줄이려는 것입니다(리뷰).
    - **할 일**: 대기 상태 그대로 기다리는 사람과 감시를 비우고 그 작업을 기다립니다. 메모에는 `<시각> watch passed, back to task #<번호>: <명령>` 을 남깁니다. 그 작업이 끝나면 맡긴 할 일처럼 닫히거나(성공) 다음 행동으로 돌아옵니다(취소).
    - **그 할 일의 마지막 작업만 받습니다.** 작업이 끝났을 때 할 일을 옮기는 `followTasks` 가 마지막 작업만 보기 때문입니다. 앞선 작업이 이어서 일하면, 끝나도 할 일이 기다리는 사람도 감시도 없는 대기로 남았습니다(리뷰에서 재현). `t<n>` 이 마지막 작업을 가리키므로 보통 `--back-to t<n>` 으로 씁니다. 시작한 적 없는 작업은 다시 열 세션이 없어 거절합니다.
    - **gc 가 정리한 작업도 받습니다.** `nod tell` 이 대화 기록으로 작업을 되살리기 때문입니다(`restore`). 답을 기다리는 동안 gc 가 완료 신호로 정리하는 일이 흔하므로(7일 넘게 지남, 연결된 PR 의 승인 등), 정리된 작업을 거절하면 오래 걸리는 대기에서 쓸 수 없습니다.
    - **작업이 이어서 일하지 못하면 할 일을 사람에게 돌립니다.** 대화 기록이 없어 되살리지 못하거나 세션이 뜨지 않는 경우입니다. 할 일은 다음 행동이 되고, 메모에 `<시각> task #<번호> could not carry on: <이유>` 를 남기고, `<홈>/notify` 에 `error` 를 알립니다. 되살리기에 실패하면 작업은 그대로 끝난 상태라서, 할 일을 그대로 두면 아무것도 기다리지 않는 대기로 남기 때문입니다. 알림 스크립트가 없어도 메모로 이유를 알 수 있습니다.
    - **한 번만 이어집니다.** 이어서 일한 작업이 끝나면 할 일도 닫힙니다. 리뷰처럼 여러 번 오가는 일은 다시 기다려야 할 때 사람이 대기·감시·`--back-to` 를 다시 겁니다. 작업이 "다시 기다림"을 보고하면 같은 감시로 다시 거는 길은, 여러 번 오가는 실제 사례를 겪어 본 뒤 정합니다.
    - **감시와 함께 다닙니다.** 감시를 지우거나 대기를 벗어나면 함께 지워집니다.
    - **새 소식을 가져오는 일은 감시 명령이 합니다.** 워커는 네트워크가 막혀 있기 때문입니다. 새 댓글을 받아 오거나 `git fetch` 를 하고 무엇이 왔는지 출력하게 합니다. 출력은 끝 2000자까지 갑니다.

## 웹 화면 단축키 (2026-10-23)

웹 화면의 할 일 목록을 마우스 없이 고르고, 옮기고, 끝냅니다. 이 단계는 이슈 #13 입니다. 키 목록은 `ui/src/keys.ts` 한 곳에 두고, 키 처리(tinykeys)와 `?` 도움말이 같은 목록을 읽습니다. 페이지 이동과 받아 적기는 브라우저의 탭·창 단축키와 겹쳐서 데스크톱 앱이 메뉴로 맡습니다(#14).

### 정한 것과 이유

1~3 은 이슈와 다르게 정한 것입니다.

1. **줄의 포커스는 줄 전체가 아니라 제목 버튼에 둡니다.** 이슈는 줄에 포커스를 주라고 했습니다. 줄 `div` 에 `tabIndex` 를 주면 lint(`noNoninteractiveTabindex`)에 걸리고, Tab 이 줄마다 한 번씩 더 멈춥니다. 제목은 이미 포커스를 받는 버튼이라 그 줄의 키를 제목에 묶었습니다. 현재 줄을 따로 기억하지 않고, 포커스를 가진 제목의 줄이 곧 현재 줄입니다. 그래서 같은 줄이라도 상태 배지·별·`…` 에 포커스가 있으면 한 글자 키가 동작하지 않습니다.
2. **`Enter` 는 할 일을 그 자리에서 펼칩니다.** 이슈는 "할 일 열기"였습니다. 제목은 펼치기 버튼(`aria-expanded`)이라, Enter 를 상세 화면 이동으로 바꾸면 버튼이 알리는 동작과 실제 동작이 달라져 화면 낭독기 사용자가 헷갈립니다. 클릭과 같게 펼치고, 상세 화면은 펼친 안의 링크로 갑니다.
3. **`x` 는 상태 메뉴의 done 과 같습니다.** 이슈는 "줄의 동그라미와 같은 동작"이라고 했지만, 줄에는 한 번 눌러 끝내는 동그라미가 없습니다. 잘못 눌러 끝내지 않도록 뺀 것입니다. 이미 끝난 할 일에서는 아무것도 하지 않습니다. 끝낸 것을 키로 되돌리는 길은 #19 로 미뤘습니다.
4. **키는 글자가 아니라 키보드의 자리(`event.code`)로 맞춥니다.** 한글 입력 상태에서는 `j` 가 `ㅓ` 로 들어와서, 글자로 맞추면 동작하지 않습니다. tinykeys 는 `event.key` 와 `event.code` 를 둘 다 비교하므로 바인딩을 `KeyJ` 처럼 씁니다. ⌘·Ctrl 에 W·T·N·F·L·R·숫자를 붙인 브라우저 조합은 쓰지 않습니다.
5. **한 글자 키는 할 일 줄에서만 받고, ⌘ 키는 입력칸에서도 받습니다.** 한 글자 단축키가 페이지 어디서나 동작하면 끄는 길을 둬야 하기 때문입니다(WCAG 2.1.4). 입력칸과 한글 조합 중의 키는 tinykeys 의 기본대로 거릅니다. `⌘⇧0` 은 입력칸에서도 첫 줄로 갑니다.
6. **줄 이동 키(`↑` `↓` `j` `k`)만 누르고 있으면 계속 옮깁니다.** tinykeys 는 키 반복을 처리 함수를 부르기 전에 거릅니다. 그래서 처음에는 `↓` 를 누르고 있으면 줄은 그대로이고, 버튼의 기본 동작인 페이지 스크롤만 일어났습니다(리뷰). 이제 반복은 키 목록의 `repeat` 로 정하고, 거르는 함수는 입력칸과 조합 중만 봅니다. `x` 같은 나머지 키는 여전히 반복을 무시합니다.
7. **포커스는 줄이 실제로 화면에서 사라질 때 옆 줄로 보냅니다.** 처음에는 상태를 바꾸기 전에 옆 줄로 옮겼습니다. 그랬더니 Projects 와 Focus 의 오늘 묶음처럼 waiting 으로 옮겨도 줄이 남는 곳에서 포커스만 넘어갔고, 변경이 실패해도 넘어가 있었습니다(리뷰). 이제 줄의 `useLayoutEffect` 정리 함수가, 포커스가 그 줄 안에 있으면 다음 줄(없으면 앞 줄)로 옮깁니다. React 19 는 지운 함수 컴포넌트의 layout 정리 함수를 DOM 에서 떼기 전에 부르므로(`commitDeletionEffectsOnFiber`), 그때는 줄 목록을 셀 수 있습니다. 5초 새로 고침으로 줄이 빠질 때도 같은 길을 탑니다. 그런데 새로 고침이 읽던 줄을 빼는 순간 누른 `x` 는 옆 할 일을 끝냈고, 반복 할 일이면 되돌리기 알림도 뜨지 않았습니다(2026-10-23 리뷰). 그래서 새로 고침이 포커스를 옮긴 뒤 1초 동안은 한 글자 키(`x`·`s`)를 무시합니다. 줄 이동 키와 Enter 는 그대로 받습니다. 그 줄에서 한 변경이 진행 중이거나 끝난 지 1초가 안 됐을 때(사람이 옮겨서 줄이 빠질 때)는 무시하지 않아, `x` 를 이어 누르며 끝낼 수 있습니다. 끝난 뒤 1초까지 보는 것은, 변경 뒤의 새로 고침이 5초 새로 고침에 밀려 일찍 끝나면 줄이 그다음 새로 고침에서 빠지기 때문입니다(리뷰).
8. **상태 메뉴 안에서도 `↑` `↓` `j` `k` 로 옮깁니다.** 메뉴는 `role="listbox"` 라 낭독기는 화살표를 안내하는데, 처음에는 Tab 으로만 옮겨졌습니다(리뷰). 줄과 같은 키 목록을 메뉴에 묶었습니다. 처음과 끝에서는 멈춥니다.
9. **`aria-keyshortcuts` 는 키를 받는 요소에, 그 요소의 할 일에 대한 키만 둡니다.** 제목에는 `X S` 만 둡니다. 줄 이동 키는 다른 줄로 가는 키이고 Enter 는 버튼 자체의 동작이라 넣지 않았습니다. 상태 배지와 done 옵션에는 `<kbd>` 로 키를 보여 주기만 하고 속성은 두지 않습니다. 거기에 포커스가 있을 때 그 키를 눌러도 동작하지 않기 때문입니다. `?` 도움말은 `role="dialog"` 이고 제목으로 이름을 붙였습니다.

**확인 (2026-10-23).** 실제 브라우저가 아니라 Bun 에서 확인했습니다.

| 확인한 것 | 결과 |
|---|---|
| 키 맞추기 (이벤트를 흉내 내 tinykeys 에 넣음) | 한글 자모 `ㅓ`·`ㅌ` 가 `KeyJ`·`KeyX` 로 맞음. `Shift+J`·`⌘J` 는 `j` 가 아님. `⌘⇧0` 은 맞고 `⌘0`(확대 초기화)은 아님 |
| 입력칸 | `?` 는 입력칸에 맡기고, `⌘⇧0` 은 입력칸에서도 받음. 조합 중인 키는 거름 |
| 키 반복 | 누르고 있는 `↓` 는 계속 받고 기본 동작(스크롤)을 막음. 누르고 있는 `x`·`⌘⇧0` 은 무시 |
| 줄이 빠질 때 (happy-dom 위의 React 19) | 정리 함수가 불릴 때 줄이 아직 페이지에 있음. 포커스가 있던 줄이 빠지면 다음 줄로, 마지막 줄이면 앞 줄로. 남는 줄과 포커스가 없던 줄은 포커스를 건드리지 않음 |
| 상태 메뉴 (실제 `StatusSelect`) | 현재 상태에서 `↓`·`j`(반복 포함)·`k`·`↑` 로 옮기고, 처음에서 멈춤 |

happy-dom 의 `navigator.platform` 은 `X11; Darwin arm64` 라서 tinykeys 의 `$mod` 가 Ctrl 이 됩니다. 확인할 때는 Mac 브라우저의 값(`MacIntel`)으로 두었습니다. 실제 브라우저에서 아직 보지 않은 것은 세 가지입니다. 브라우저가 한글 입력 상태에서 보내는 `isComposing`·`code` 값, `s` → `Esc` 뒤 포커스가 제목으로 돌아오는지, Safari·WKWebView 의 기본 설정(Tab 이 버튼을 건너뜀)에서 Tab 으로 목록에 들어가는지입니다. `⌘⇧0` 은 이 설정과 상관없이 동작합니다.

## 데스크톱 앱 (2026-10-23)

목표는 둘입니다. 다른 앱을 쓰다가 떠오른 일을 바로 받아 적는 것, 그리고 nod 화면을 키 하나로 불러오는 것입니다.

1. **앱은 화면 서버를 창에 띄우는 껍데기입니다.** 화면 서버는 장부·tmux·git·캘린더를 직접 부르는 Bun 서버라 앱 안으로 옮기지 않습니다.
2. **화면 서버는 앱이 아니라 launchd 가 띄웁니다.** 앱이 띄우면 앱을 끌 때 서버도 꺼지고, 캘린더 읽기 권한을 앱 이름으로 다시 받아야 할 수 있습니다. 에이전트는 개발 서버가 아니라 빌드한 서버(`vite build` 뒤 `vite preview`, TanStack Start 가 서버 진입점을 붙여 줌)를 띄웁니다. 개발 서버는 레포에서 브랜치를 바꿀 때 잠깐 500 을 냅니다. 대신 레포를 바꾸면 다시 빌드해야 해서, 설치 스크립트를 다시 돌리면 빌드부터 다시 합니다.
3. **웹 화면은 앱 기능을 부르지 않습니다.** 앱 명령은 `build.rs` 의 앱 매니페스트에 올려 권한 뒤에 두고, 권한은 앱에 든 페이지에만 줍니다(받아 적기 창은 `capture`·`dismiss`, 서버가 꺼졌을 때의 페이지는 `retry`). 원격 주소를 적은 권한이 없으므로 4800 의 화면은 아무 명령도 부르지 못합니다. 단축키·메뉴·창 다루기는 Rust 쪽에서 하고, 페이지 이동은 앱이 메인 창의 주소를 바꿔서 합니다. 화면 밖으로 나가는 링크(PR 등)는 창을 옮기지 않고 브라우저로 엽니다. 창에 두는 것은 화면 서버와 같은 출처(`http://127.0.0.1:4800`)와 앱의 페이지(`tauri://`, `tauri dev` 에서는 그 개발 서버)뿐입니다. 처음에는 주소가 127.0.0.1·localhost 면 포트와 상관없이 창에서 열어, 이 컴퓨터의 다른 서버도 창 안에 떴습니다(2026-10-23 리뷰, `cargo test` 로 확인).
4. **받아 적기는 `nod in` 을 화면 서버와 같은 환경으로 부릅니다.** 장부를 바꾸는 길을 `nod` 명령 하나로 유지합니다. 누가는 `human:desktop` 입니다. Finder 에서 연 앱은 launchd 의 빈약한 PATH 만 받고 `NOD_HOME` 이 없어서, 그대로 부르면 `nod` 를 못 찾거나 화면 서버와 다른 장부에 씁니다. 그래서 받아 적을 때마다 `ui.sh install` 이 쓴 에이전트 plist 의 `EnvironmentVariables` 에서 `PATH`·`NOD_HOME`·`CLAUDE_CONFIG_DIR` 를 읽어 넘기고(`plutil -extract … json`), plist 에 없는 둘은 앱의 환경에서도 지웁니다. plist 가 없으면 설치하라고 알립니다. 처음에는 앱이 시작할 때 대화형 로그인 셸에서 PATH 를 읽었는데, 셸 설정이 띄운 백그라운드 프로세스가 출력을 쥐고 있으면 끝없이 기다렸고(리뷰에서 `.zshrc` 의 `sleep 4 &!` 로 4초 걸림을 재현), `NOD_HOME` 은 여전히 서버와 어긋날 수 있었습니다.
5. **전역 단축키는 ⌃⌥⌘ 조합입니다.** 전역 단축키는 다른 앱이 앞에 있을 때도 키를 가로채므로 macOS 기본 단축키(⌥⌘Space·⌃⌘Space·⌃Space·⌃⌥Space)와 Orca(⌘·⌘⇧·⌘⌥·⌘⌥⇧·⌃)가 쓰지 않는 조합으로 정했습니다. 앱 메뉴의 ⌘1~6·⌘N·⌘W 는 Orca 의 손에 익은 키를 따릅니다. 전역 단축키는 앱이 떠 있어야 동작하므로, 앱은 사람이 로그인 항목에 넣습니다.
6. **다른 앱에서 연 받아 적기 창은 키보드를 그 앱에 돌려줍니다.** 창을 열 때 nod 창에 포커스가 없었으면, 보내거나 닫을 때 앱 전체를 숨깁니다(`NSApp hide`). 메인 창이 뒤에 열려 있어도 nod 가 앞에 남지 않게 하려는 것입니다.

실측(2026-10-23): 앱은 `cargo build` 로 빌드됩니다. 빌드한 화면 서버는 서버 진입점의 `fetch` 로 여섯 화면(`/focus`~`/done`)이 200 을 내는 것까지 확인했습니다. 앱 실행, 메뉴·전역 단축키, 받아 적기가 Inbox 에 들어가는지, launchd 설치는 아직 확인하지 않았습니다.

## 대화형 워커 실측 (2026-10-06, Claude Code 2.1.290, haiku)

**훅.** Stop 훅 입력에 `session_id`, `last_assistant_message`, `stop_hook_active` 가 옵니다. 그래서 결과를 파일이나 파이프로 따로 받지 않고 마지막 메시지의 보고 줄을 읽습니다. Stop 훅이 `{"decision":"block","reason":…}` 을 내면 같은 턴이 그 이유를 받아 이어집니다. 이렇게 이어진 턴의 마지막 메시지에는 보고 줄이 빠지는 일이 있어서, 이때(`stop_hook_active`)는 검증 결과로 판단합니다. 권한 확인 화면이 뜨면 Notification 훅이 `notification_type: permission_prompt` 로 옵니다.

**같은 세션에 이어 보내기.** 끝난 세션에 tmux 로 메시지를 넣으면 새 턴이 돌고, 첫 메시지에서 알려 준 단어를 기억했습니다. 세션을 강제로 닫은 뒤 `claude --resume <세션>` 으로 다시 열어도 앞에서 정한 언어("한국어")를 기억했습니다.

**폴더 신뢰.** 대화형 세션은 처음 보는 폴더에서 신뢰 확인 화면을 띄웁니다. 상위 폴더를 신뢰하면 하위 폴더에서는 묻지 않았습니다. 그래서 nod 는 계정(설정 폴더)마다 처음 한 번 `<홈>/work` 를 신뢰합니다. 그 안에는 nod 가 만든 폴더와 사람이 지정한 레포의 worktree 만 생깁니다. 화면이 뜨자마자 보낸 키는 무시됐기 때문에, 선택된 항목을 화면에서 읽어 "Yes" 가 선택됐을 때만 Enter 를 누릅니다(측정 시 2초).

**worktree 의 신뢰.** worktree 는 `<홈>/work` 아래에 있어도 신뢰 확인 화면이 떴습니다. 화면에서 "Yes" 를 고르자 신뢰 목록에 worktree 가 아니라 원래 레포 경로가 기록됐습니다. Claude Code 는 worktree 를 원래 레포 기준으로 따지는 것입니다(M4 실측). 레포를 신뢰하면 그 레포에 들어 있는 Claude 설정과 훅이 워커에서 돌기 때문에, nod 는 이 화면을 자동으로 넘기지 않고 결정(trust)으로 올립니다. 레포 작업은 SessionStart 훅이 표시 파일을 만들 때까지 기다려서, 신뢰 화면에 걸렸는지 알아냅니다.

**권한 거절.** 권한 확인에서 Esc 는 "No" 이면서 그 턴을 끝내 버리고, 이때는 Stop 훅이 오지 않았습니다. 그래서 거절할 때는 Esc 뒤 화면에 "Interrupted" 가 뜨는 것을 확인하고, 그 턴을 닫은 다음 사람의 답을 새 턴으로 보냅니다.

**세션 닫기와 gc.** tmux 세션을 닫은 직후 Claude 세션 폴더를 지웠더니, 종료 중인 Claude 가 파일을 써서 폴더가 다시 생겼습니다. 그래서 세션을 닫을 때 프로세스가 끝날 때까지 기다립니다.

**끝까지 실행한 시나리오.** 4개를 동시에 띄웠습니다.

| 시나리오 | 결과 |
|---|---|
| 검증 있는 파일 작업 | 첫 턴에 통과 |
| 검증 실패 (`count.txt` 를 3으로 만들라 하고 4인지 검증) | 훅이 돌려보내자 같은 턴에서 4로 고치고 통과 |
| 질문 → 결정 → "한국어" | 같은 세션이 한국어 인사말 작성 |
| WebFetch → 권한 결정 → 거절 | 새 턴으로 거절 사유를 받고 건너뛰었다고 보고 |
| 끝난 작업에 `nod tell` | 같은 세션이 후속 지시 수행, 검증 통과 |
| 세션을 죽인 뒤 `nod tell` | 대화 기록에서 다시 열고 앞의 맥락으로 답함 |
| `nod drop` | cancelled, 세션 닫힘 |
| `nod gc --older-than 0` | 세션·작업 폴더·세션 폴더 모두 지움 |

## `claude -p` 시절 실측 (2026-10-05, Claude Code 2.1.289, MacBook 32GB·10코어)

M1~M3.5 의 워커는 `claude -p` 였습니다. 아래는 그때 잰 값이고, 권한·샌드박스 결과는 지금 워커에도 그대로 씁니다. 대화형 워커의 동시 실행 비용은 아직 재지 않았습니다.

**동시 실행.** 같은 작업(파일 하나 쓰기, haiku)을 한꺼번에 돌린 결과입니다. 워커 하나가 약 270MB 를 썼고, 32개에서 작업 평균이 15초로 느려졌습니다.

| 동시 수 | 전체 시간 | 작업 평균 | 최대 메모리 | 성공 |
|---|---|---|---|---|
| 8 | 11초 | 10초 | 2.3GB | 8/8 |
| 16 | 11초 | 11초 | 4.5GB | 16/16 |
| 32 | 17초 | 15초 | 8.5GB | 32/32 |

**worktree 동시 생성.** 한 레포에 `git worktree add` 를 32개 동시에 실행해도 실패가 없었습니다. 그래서 잠금을 두지 않았습니다.

**권한 모드.** `auto` 는 비대화 실행에서 파일 쓰기와 셸 명령을 모두 거부했고, `acceptEdits` 는 파일 쓰기만 통과시켰습니다. 그래서 `acceptEdits` 와 샌드박스를 함께 썼습니다. 워커는 사용자 설정(CLAUDE.md·훅·MCP)을 물려받습니다.

대화형 워커로 바꾼 뒤(2026-10-07) `auto` 로 바꿨습니다. 실제로 써 보니 샌드박스 안의 단순한 명령은 묻지 않고 지나갔지만, `cd … && git …`·`$변수`·반복문·따옴표 안 중괄호가 섞인 명령은 Claude Code 가 미리 검사하지 못한다며 확인창을 띄웠습니다. 리뷰 작업 세 개와 구현 작업 하나를 돌리는 동안 이런 결정이 17개 쌓였고, 모두 검사·조회·설치였습니다. `auto` 의 판단기는 이런 명령을 통과시키고, 판단하지 못하는 것만 확인창으로 남겨 결정이 됩니다. 워커 지시에도 셸 명령을 하나씩 단순하게 쓰라는 줄을 더했습니다. 대화형 세션에서 `auto` 가 실제로 이렇게 동작하는지는 아직 재지 않았습니다.

**셸 명령 정책: 허용 목록이 아니라 샌드박스.** 테스트 실행을 허용하는 순간 워커는 어떤 코드든 실행할 수 있으므로, 명령 목록은 경계가 되지 못합니다. 대신 OS 샌드박스로 어디에 쓸 수 있고 어디에 접속할 수 있는지를 막습니다.

- `sandbox.enabled` + `autoAllowBashIfSandboxed`: 샌드박스 안의 셸 명령은 묻지 않고 실행됩니다.
- 작업 폴더 밖 쓰기는 `operation not permitted` 로 막혔습니다.
- 네트워크는 기본으로 막히고, `network.allowedDomains` 에 넣은 곳만 통과했습니다. 기본 허용은 `registry.npmjs.org` 하나입니다.
- `allowUnsandboxedCommands: false` 로 샌드박스를 끄고 다시 시도하는 탈출구를 닫았습니다.
- worktree 에서의 `git commit` 은 성공했고, 전역 git 작성자 정보도 보였습니다.
- `git -c …` 처럼 설정을 덮어쓰는 명령은 권한 단계에서 거부됐습니다.
- WebFetch·WebSearch·MCP 도구는 승인을 받아야 하는 도구입니다. 비대화 실행에서는 거부됐고, 대화형 워커에서는 권한 결정으로 올라옵니다.

**결과 스키마.** zod 가 만든 JSON Schema 의 `$schema` 키를 Claude Code 가 거부했습니다. 지금은 구조화 출력 대신 보고 줄을 읽으므로 쓰지 않습니다.

## 계정

nod 는 기본으로 실행한 셸의 Claude 로그인을 그대로 씁니다. 개인 일은 개인 계정으로 돌리려면 `CLAUDE_CONFIG_DIR=<개인 설정 폴더> nod add …` 처럼 실행합니다. 계정을 바꾸는 도구를 쓰면 `nod account file|command` 로 지금 계정을 읽을 곳을 정합니다(아래 「워커를 같은 칸·같은 대화에 붙여 두기」). tmux 서버는 처음 띄운 프로세스의 환경을 기억하므로, nod 는 워커에 넘길 환경을 직접 정하고 서버의 환경은 쓰지 않습니다.

## 워커를 같은 칸·같은 대화에 붙여 두기 (2026-10-23)

계정을 바꾸는 도구는 두 갈래입니다. 계정마다 설정 폴더(`CLAUDE_CONFIG_DIR`)를 두고 돌던 Claude 를 끝낸 뒤 새 폴더로 `claude --resume <id>` 하는 방식과, 폴더 하나의 로그인을 바꿔 끼우는 방식입니다. 앞 방식의 도구로 계정을 바꾸자 두 가지가 생겼습니다. 돌던 워커의 Claude 가 끝나 작업이 `session ended` 오류로 남았고, 사람이 `nod resume` 으로 다시 열어야 했습니다. 그리고 워커가 nod 를 부른 터미널의 환경 변수(그 도구가 칸마다 넣는 식별 표지)를 tmux 서버를 거쳐 물려받아, 바깥 도구에 "나는 그 칸의 세션"이라고 보고했습니다. 바깥 도구는 계정을 바꾸며 사람의 루트 칸을 워커의 대화로 다시 띄웠습니다. 목표는 무엇이 워커의 Claude 를 끄고 다시 띄우든 nod 가 같은 tmux 칸과 같은 대화(세션 ID)에 계속 붙어 있는 것입니다.

### 정한 것과 이유

1. **칸 안의 지킴이는 셸 스크립트가 아니라 nod 하위 명령(`nod run <작업> <claude 인자…>`)입니다.** 칸의 첫 프로세스가 `claude` 가 아니라 `nod run` 이고, 그것이 Claude Code 를 자식으로 띄워 끝나기를 기다립니다. 장부(마지막 세션 ID, 열린 차례), 계정 규칙, 결정 열기, 알림을 그대로 부를 수 있고, 가짜 Claude 로 테스트할 수 있어서입니다. 셸 루프로 하면 이 판단을 셸에서 다시 짜거나 nod 를 거듭 불러야 합니다. 같은 이유로 지시문을 넘기는 스크립트(`.launch-<세션>`)는 그대로 두고, 그 스크립트가 `nod run` 을 실행합니다.
   - **다시 띄울 때.** 세션 ID 는 마지막 차례의 것(훅이 알려 준 세션으로 시도가 기록됨)이고, `--resume` 은 그 ID 를 그대로 씁니다. 훅 설정·모델·시스템 프롬프트는 첫 실행과 같은 함수(`claudeArgs`)로 만들고, 계정은 그 순간의 규칙으로 정합니다. 첫 지시는 다시 보내지 않습니다. 예외는 대화 기록이 없고 끝난 차례도 없는 경우입니다. 지시를 받기 전에 끝난 것이라 `--resume` 할 대화가 없으므로 같은 세션 ID 로 지시를 처음부터 보냅니다. 그사이 남은 메시지(`interrupted` 결정의 답, `nod tell`)는 지시 뒤에 붙여 보내고, 그 실행이 띄우자마자 또 끝나면 다음 실행을 위해 되돌려 둡니다. Claude Code 가 뜬 뒤 붙여 넣지 않는 것은, 그때 신뢰 확인 화면이 떠 있으면 Enter 가 "No, exit" 를 고르기 때문입니다. 처음에는 지시만 보내고 그 메시지를 버렸습니다.
   - **일부러 끈 것과 구별.** nod 가 칸을 닫을 때(gc·drop·신뢰 세션) `<홈>/work/.stop-<세션>` 표지를 남기고 닫습니다. 지킴이는 표지가 있거나, SIGHUP·SIGTERM 을 받았거나, 칸이 사라졌거나 같은 이름의 새 칸으로 바뀌었으면(`TMUX_PANE` 비교) 다시 띄우지 않고 끝납니다. 칸을 닫을 때는 SIGHUP 을 Claude Code 에 넘기고 그것이 끝날 때까지 기다리므로, `Terminals.close` 가 칸의 프로세스를 기다리는 동작(종료 중 세션 파일 쓰기)도 그대로입니다. 칸 안에서 Ctrl-C 가 지킴이를 끄지 않게 SIGINT 는 무시합니다. Claude Code 를 다시 띄우기 전, 새 계정의 작업 폴더 신뢰(최대 20초)를 기다리는 중에 신호를 받으면 그 기다림을 끊고 바로 끝납니다. 처음에는 기다림이 끝날 때까지 남아 `Terminals.close` 의 10초 제한을 넘겨 drop·gc 가 "did not exit" 로 실패했습니다. 이때 진행 중이던 신뢰 확인 세션(`trust-<pid>-<해시>`)은 남을 수 있습니다. 계정 명령(최대 10초)은 동기로 돌아 신호를 받아도 끝날 때까지 끊지 못하므로, `Terminals.close` 는 그보다 긴 15초를 기다립니다.
   - **답하던 도중에 끝나면.** 다시 띄운 Claude Code 가 5초를 넘겨 떠 있으면 그 차례를 실패로 닫고 결정(`interrupted`)을 엽니다. 일이 일부 됐을 수 있어 같은 일을 두 번 하지 않도록, 저절로 이어 시키지 않습니다. 다시 뜨는 동안 사람이 보낸 메시지를 새 Claude Code 가 받았으면 그 메시지가 차례를 이어 가므로 결정을 열지 않고, 그 차례의 Stop 이 닫습니다. 답은 "차례가 끊겼으니 된 것부터 확인하라"는 말과 함께 같은 대화로 갑니다. 그 차례가 띄우던 권한·신뢰 확인 결정은 함께 닫습니다(`(the turn was cut off)`). 화면이 없어진 확인에 답하면 tmux 오류만 나기 때문입니다.
   - **계속 끝나면.** 띄운 지 5초 안에 끝나는 일이 세 번 이어지면 다시 띄우기를 멈춥니다. 마지막 화면과 함께, 열린 차례(끊긴 차례나 보내려던 메시지)가 있으면 결정으로, 없으면 `<홈>/notify` 의 `error` 로 알리고 칸을 닫습니다. 쉬던 작업에 결정을 열면 성공한 작업이 결정 대기로 바뀌고, 사람이 drop 하면 성공 기록이 취소로 바뀌기 때문입니다. 다음 `nod tell` 이 다시 띄웁니다. 30초마다 죽는 Claude 처럼 5초를 넘겨 살다 끝나는 경우는 끝없이 다시 띄웁니다.
2. **계정 규칙은 `nod account` 하나로 `<홈>/account.json` 에 둡니다.** `nod schedule on` 이 `<홈>/schedule.json` 을 쓰는 방식을 따랐습니다. 할 일 도구 설정(`<홈>/config.json`)은 gtd 스킬의 것이라 섞지 않았습니다. 규칙은 셋입니다. 기본은 지금처럼 띄우는 프로세스의 `CLAUDE_CONFIG_DIR`, `file` 은 파일 내용을 다듬은 경로, `command` 는 명령(10초 제한)의 출력입니다. 명령은 인자 하나로 받아 `sh -c` 로 돌립니다. 여러 인자를 공백으로 이으면 따옴표가 사라져 `cat "/a b/current"` 가 `cat /a b/current` 가 되기 때문입니다. 비어 있으면 `CLAUDE_CONFIG_DIR` 를 넣지 않아 Claude Code 의 기본 폴더를 씁니다. 파일이 없거나 명령이 실패하면 오류로 띄우지 않습니다. 엉뚱한 계정으로 뜨는 것보다 뜨지 않는 편이 낫기 때문입니다. 새 워커(`nod add`, 웹 화면), 트리거 워커, 지킴이, 신뢰 세션, 대화 기록 찾기(`restore`)가 모두 이 규칙 하나(`configDir`)를 씁니다.
3. **계정이 바뀌면 끄기만 합니다.** 워커의 Claude Code 를 띄울 때마다 그 계정을 장부에 남깁니다(`tasks.account`, 장부 v19, 없으면 `''`). 규칙이 파일이나 명령이면, nod 명령이 끝날 때와 tick 이 매분 돌 때 지금 계정과 비교합니다(`restartDue`). 다르면 쉬는 워커는 지킴이에게 SIGUSR1 을 보내 Claude Code 만 끕니다(1초 뒤 SIGTERM). 칸은 남고 지킴이가 지금 계정으로 다시 띄웁니다. 답하는 중이면 tmux 세션 값(`@nod_restart`)에 남겨 두었다가 그 차례의 Stop 훅이 끝에서 끕니다. 1초를 기다리는 것은 이 Stop 훅이 먼저 끝나게 하려는 것입니다. 사람이 `nod attach` 로 붙어 있으면 끄지 않고, 같은 이유로는 한 번만(`@nod_told`) `<홈>/notify` 에 `restart_held` 를 보내고, 나간 뒤 다음 확인 때 끕니다.
   - **API 오류로 멈춘 차례는 기다리지 않습니다.** 사용량 한도·로그인 같은 API 오류로 차례가 끝나면 Claude Code 는 Stop 대신 `StopFailure` 훅을 부르고(2.1.309), 한도가 풀리면 스스로 이어 갑니다. 그 사이 nod 에게 그 차례는 열린 채라, "차례가 끝난 뒤"를 기다리면 계정을 바꾸려는 바로 그 상황(한도)에서 워커가 옛 계정에 묶입니다. 그래서 `StopFailure` 훅이 오류를 tmux 세션 값(`@nod_stalled`)에 남기고, 재시작은 이 값이 있으면 열린 차례를 기다리지 않습니다. 다시 띄운 Claude Code 에는 "API 오류로 멈췄으니 이어서 하라"는 첫 메시지를 주고, 열린 차례는 그대로 두어 이어진 차례의 Stop 이 닫습니다. 계정이 그대로면 아무것도 하지 않습니다(Claude Code 가 한도 뒤에 이어 감). 다음 Stop 이 오면 값을 지웁니다.
   - **nod 가 차례를 확인하는 동안에는 끄지 않습니다.** Stop 훅은 차례를 닫은 뒤 검증·리뷰를 돌리므로, 그 사이의 재시작은 워커를 쉬는 중으로 보고 Claude Code 와 함께 이 훅을 끊었습니다. 그러면 리뷰 결과가 남지 않고 작업이 실행 중에 머뭅니다. 그래서 훅이 도는 동안 tmux 세션 값(`@nod_settling`)에 훅의 pid 를 두고, 재시작은 그 프로세스가 살아 있으면 훅 끝(`restartDue`)으로 미룹니다. 값은 기다리던 작업을 띄우는 일(`startReady`)까지 끝난 뒤 지웁니다. 그 사이 온 `nod tell`·답은 재시작하지 않고 그대로 붙여 넣고, 계정 전환은 그 차례 뒤로 미룹니다. 그 메시지는 훅이 끝난 뒤 Claude Code 가 돌리는 새 차례이므로, 훅이 아직 이 차례를 닫기 전이라도 시도를 엽니다. 훅은 세션 값을 맨 먼저 세우고, 확인할 차례를 알면 `<pid> <시도>` 로 고쳐 둡니다. 그 차례가 아닌 열린 시도(훅이 연 재시도)를 찾은 메시지는 그 차례에 들어갑니다. 질문을 열 때도 그 사이 다른 차례가 열렸으면 그 차례에 맡깁니다. 훅은 검증을 마친 뒤 다른 열린 시도가 있으면 작업을 성공시키지도 재시도를 열지도 않고 그 차례의 멈춤에 맡깁니다. 이 확인과 성공·재시도는 한 트랜잭션이고, 메시지 쪽도 열린 차례를 보고 새 시도를 여는 일을 한 트랜잭션으로 합니다. 처음에는 리뷰가 통과하면 메시지의 차례가 도는 중에 작업이 succeeded 가 됐고, 실패하면 재시도가 하나 더 열려 다음 Stop 이 하나만 닫았습니다(재시작이 미뤄지고 재부팅 뒤 가짜 interrupted 결정이 열림). 훅이 도는 사이 Claude Code 가 끝나면(훅은 살아 있음) 실패한 검증을 돌려받을 Claude Code 가 없으므로, 훅이 연 재시도를 끊긴 차례로 닫고 결정(`interrupted`)을 엽니다. 훅은 지킴이가 tmux 세션 값 `@nod_claude` 에 남긴 Claude Code 의 pid 로 이를 압니다. pid 로 보는 것은 끊기거나 시간이 다 된 훅이 남긴 값이 재시작을 영영 막지 않게 하려는 것입니다. 훅이 끝내지 못한 채 Claude Code 가 끝나면(값이 남았는데 그 프로세스가 없음) 작업은 실행 중인데 열린 차례가 없는 채로 멈추므로, 지킴이가 그 작업을 오류로 바꾸고 알립니다(`watchSettling`).
   - **다시 뜨는 동안 온 메시지는 기다립니다.** 지킴이에게 다시 띄우라고 할 때(`startAgain`)와, Claude Code 가 스스로 끝나(충돌·`/exit`·바깥 계정 전환) 지킴이가 다시 띄우기로 할 때마다 tmux 세션 값 `@nod_restarting` 을 세우고, 새 Claude Code 가 5초를 넘겨 떠 있으면 지웁니다. 처음에는 `startAgain` 에서만 세워, 스스로 끝난 뒤 다시 뜨는 사이의 메시지가 Claude Code 가 없거나 막 뜨는 칸에 붙여져 사라지고, 쉬던 워커면 연 시도가 끝나지 않고 남았습니다. Claude Code 가 끝난 순간부터 지킴이가 이 값을 세우기까지의 틈은, 메시지 쪽이 지킴이가 남긴 Claude Code 의 pid(`@nod_claude`)가 살아 있는지도 보아 막습니다. 신호를 보낼 권한이 없어 `EPERM` 이 나면(샌드박스 안에서 부른 `nod tell` 등) 살아 있는 것으로 봅니다. 그렇지 않으면 그런 곳에서 보낸 메시지가 모두 조용히 다음 재시작까지 묵습니다. 그 사이의 `nod tell`·답은 꺼져 가는 Claude Code 에 붙여 넣으면 사라지므로 `<홈>/work/.prompt-<작업>` 에 덧붙여 남기고, 새 Claude Code 가 첫 메시지로 받습니다. 이미 뜬 뒤 남은 것은 지킴이가 붙여 넣습니다. 이 값이 있는 동안은 `restartDue` 도 그 워커를 건너뛰어, 새 Claude Code 가 계정을 남기기 전의 확인이 한 번 더 다시 띄우지 않습니다. 다시 띄우라고 했는데 남은 메시지 없이 열린 차례가 있으면, 그 차례는 그 사이에 시작됐다가 끊긴 것이라 결정(`interrupted`)으로 올립니다.
   - **새로 뜨면 지난 값을 지웁니다.** 기다리던 재시작(`@nod_restart`), 사람에게 알린 이유(`@nod_told`), API 오류(`@nod_stalled`)는 모두 끝난 Claude Code 에 대한 것이라, 지킴이가 Claude Code 를 새로 띄울 때마다 지웁니다. 남겨 두면 진행 중인 차례를 끄거나 사람의 결정을 건너뛰고 "이어서 하라"를 보냈습니다.
   - **계정이 바뀐 워커에 보내는 메시지.** `nod tell`·답이 계정이 바뀐 쉬는 워커에 가면, 붙여 넣지 않고 메시지를 `<홈>/work/.prompt-<작업>` 에 남긴 뒤 다시 띄워 첫 메시지로 넣습니다. 붙여 넣으면 Claude Code 가 다시 뜨는 사이에 들어가 사라질 수 있기 때문입니다. 같은 이유로 nod 명령의 확인은 명령이 끝난 뒤에 합니다. 칸이 사라진 작업에 보낼 때도 메시지를 남기고 칸만 열어, 지킴이가 다시 띄울 때와 같은 길(지금 계정, 신뢰, 메시지)로 띄웁니다. 답은 결정을 먼저 닫아, 한꺼번에 온 두 답 가운데 하나만 워커에 갑니다. 그 뒤 메시지를 넣지 못하면(계정 규칙 파일이 없거나 명령이 실패) 작업을 error 로 남기고, 사람은 `nod tell` 로 다시 보냅니다. 처음에는 결정은 답했는데 작업은 시도도 메시지도 없이 실행 중으로 남았습니다. 계정 규칙을 읽은 뒤에 결정을 닫는 안도 해 봤는데, 확인을 거절할 때 Escape 를 누르고 화면을 기다리는 사이 다른 답이 같은 결정에 들어와 확인 화면이 없는 칸에 Enter 를 보냈습니다.
   - **대화 기록은 계정 폴더들이 함께 써야 합니다.** 다시 띄울 때 대화 기록을 지금 계정 폴더에서 찾는데, 옛 계정 폴더(`tasks.account`)에만 있으면 이어 갈 수 없습니다. 이때 "대화가 시작되지 않았다"고 보고 첫 지시를 다시 보내지 않고, 이유를 담은 오류로 다시 띄우기를 멈춥니다.
   - **기본 규칙에서는 비교하지 않습니다.** 환경 변수 규칙에서는 워커마다 자기를 띄운 셸의 계정이라 "지금 계정"이 하나가 아닙니다. 비교하면 다른 셸에서 `nod ls` 만 해도 워커들이 그 셸의 계정으로 옮겨 갑니다.
   - **`nod restart [<작업>…]`** 는 같은 일을 계정과 상관없이 시킵니다. 바깥 도구가 계정을 바꾼 바로 그때 부르면 tick 을 기다리지 않습니다.
   - **파일 변경 알림(launchd `WatchPaths`)은 두지 않았습니다.** tick 은 `Bun.cron` 이 만든 launchd 항목이라 nod 가 그 plist 에 `WatchPaths` 를 더할 수 없고, 따로 항목을 만들면 등록·해제를 두 벌로 관리해야 합니다. 그 대신 tick(1분)과 `nod restart` 로 둡니다.
   - **계정마다 신뢰.** Claude Code 는 신뢰한 폴더를 설정 폴더에 기록하므로, nod 의 작업 폴더를 신뢰했다는 표지도 계정마다 둡니다(`.trusted-<해시>`, Claude Code 의 기본 폴더도 해시). 처음에는 기본 폴더의 표지로 `.trusted` 를 썼는데, 이 이름은 계정 규칙 전의 nod 가 그때 셸의 계정(다른 설정 폴더일 수 있음)으로 신뢰하고 남긴 것이라, 기본 폴더로 바꾸면 신뢰하지 않은 폴더를 신뢰한 것으로 읽고 레포 없는 작업이 신뢰 확인 화면에서 멈췄습니다. 신뢰 세션 이름은 프로세스와 계정마다 달라서(`trust-<pid>-<해시>`), 계정이 바뀐 뒤 여러 지킴이가 한꺼번에 신뢰해도 서로의 세션을 뺏지 않습니다. 한 프로세스가 작업 여럿을 한꺼번에 띄울 때(`startReady`, tick)는 같은 계정의 신뢰를 한 번만 하고 함께 기다립니다. 처음에는 같은 프로세스의 둘째 작업이 같은 이름의 세션을 열지 못해 error 가 됐습니다. 레포 작업을 다시 띄울 때 신뢰 확인 화면이 뜨면, 그 작업이 이미 그 레포에서 첫 실행을 지났다면(사람이 신뢰함) 그대로 "Yes" 를 고릅니다(`trustOnStart`). 다른 계정이 처음 묻는 것일 뿐이기 때문입니다. 결정으로 올리면 이미 끝난 작업이 결정 대기로 바뀌고, 답에 따라 실행 중이나 취소로 바뀌었습니다. 첫 실행을 지나지 못한 작업(대화 기록도, 끝난 차례도 없음)은 첫 실행처럼 결정(`trust`)으로 올립니다.
4. **칸까지 사라진 경우는 tick 이 찾습니다**(`lostTurns`). 끝나지 않았는데(실행 중·결정 대기) tmux 세션이 없고 열린 차례가 있으면, 차례를 실패로 닫고 결정(`interrupted`)을 엽니다. 답하면 `nod tell` 과 같은 길로 대화 기록에서 다시 엽니다. 시작한 지 30초가 안 된 차례는 칸이 아직 뜨는 중일 수 있어 건너뜁니다. 차례를 실패로 닫는 일은 `finished_at is null` 조건의 UPDATE 한 문장으로 먼저 차지하고, 차지한 쪽만 결정을 엽니다. 처음에는 확인과 닫기 사이에 알림을 기다려, 겹친 tick 둘이 사라진 차례 하나에 결정을 둘 열 수 있었습니다. 쉬던 작업은 바꾸지 않았습니다. 다음 `nod tell` 이 지금처럼 다시 띄웁니다.
5. **워커 환경은 허용 목록입니다.** 칸마다 식별 변수를 넣는 터미널·에이전트 호스트는 계속 늘고 이름도 제각각이라, 막을 이름의 목록은 다음 도구에서 또 뚫립니다. 그래서 워커에 필요한 것만 넘깁니다(`PASS_ENV`). 사용자(`HOME`·`USER`·`LOGNAME`, 로그인 키체인), `SHELL`·`TMPDIR`·`TZ`·`LANG`·`LC_*`, git·gh 설정 폴더(`XDG_*_HOME`·`XDG_RUNTIME_DIR`), `SSH_AUTH_SOCK`, 프록시(대소문자 둘 다)와 인증서(`NODE_EXTRA_CA_CERTS`·`SSL_CERT_FILE`·`SSL_CERT_DIR`), `ANTHROPIC_*`, 그리고 워커의 훅·지킴이가 nod 의 tmux 서버를 찾는 `TMUX_TMPDIR` 이고, nod 가 `PATH`·`NOD_HOME`·`NOD_TASK`·`CLAUDE_CONFIG_DIR` 를 정해 넣습니다. `CLAUDE_CODE_*` 는 넣지 않았습니다. 바깥 Claude Code 세션이 자기 표지(IDE 연결 포트 등)를 이 이름으로 두기 때문입니다. 목록에 없는 변수가 필요하면 Claude Code 설정 폴더의 `settings.json` 의 `env` 에 둡니다. Claude Code 가 그것을 자기 프로세스에 넣으므로 셸 명령·훅도 받습니다.
   - **tmux 서버의 환경도 막습니다.** tmux 는 칸의 명령을 서버 환경과 `-e` 값을 합쳐 띄우고, 서버 환경은 서버를 처음 띄운 프로세스의 것입니다. 그래서 `-e` 대신 띄우는 스크립트가 `exec env -i TERM="$TERM" TMUX="$TMUX" TMUX_PANE="$TMUX_PANE" <정한 값들> <명령>` 으로 환경을 비우고 시작합니다. 이 셋은 tmux 가 그 칸에 넣는 값이라 nod 자신의 칸을 가리킵니다. 스크립트에는 이제 프록시 비밀번호 같은 값이 들어갈 수 있어 소유자만 읽게(0600) 씁니다.
   - **독립 리뷰어는 워커의 환경을 그대로 씁니다.** Stop 훅 안에서 도는 리뷰어는 그 워커가 뜬 계정으로 돕니다.

**확인 (2026-10-23).** 작업한 샌드박스에서는 tmux 가 소켓을 만들지 못해(`Operation not permitted`, 그런데도 종료 코드는 0) tmux 를 띄우는 테스트를 돌리지 못했습니다. tmux 없이 돌린 것과 직접 확인한 것은 이렇습니다.

| 확인한 것 | 결과 |
|---|---|
| 계정 규칙 (`account.test.ts`) | 환경 변수, 파일(앞뒤 공백 제거, 빈 내용은 없음), 명령 출력, 실패한 명령과 없는 파일은 오류. 규칙이 없으면 계정 비교를 하지 않음 |
| 워커 환경 (`workerEnv`) | 프록시·인증서·`LC_ALL`·`ANTHROPIC_BASE_URL`·`HOME` 은 넘기고 `TERM_SESSION_ID`·`CLAUDE_CODE_SSE_PORT`·`NOD_ACTOR` 는 뺌 |
| 띄우는 스크립트를 `sh` 로 직접 실행 | `TERM`·`TMUX`·`TMUX_PANE` 과 정한 값만 남고, 부른 쪽의 다른 변수는 빠짐. 작은따옴표·`$` 가 든 값도 그대로 |
| Bun 의 신호 | `process.on` 으로 SIGUSR1·SIGHUP 을 받음. 끝난 자식에 `kill` 해도 오류 없음 |
| Bun 의 환경 변수 (1.3.14) | `env` 를 주지 않고 띄운 자식은 실행 중에 바꾼 `process.env` 를 받지 못함. 실행 중에 넣은 `HTTP(S)_PROXY`·`NO_PROXY` 는 `process.env` 의 키 목록에 나오지 않음(시작할 때 있던 것은 나옴). 그래서 지킴이·계정 명령·tmux 호출은 자식에게 `env` 를 직접 주고, 워커 환경 테스트는 그 값을 가지고 시작한 프로세스에서 돌림 |
| `nod account`·`nod restart` (CLI 테스트) | 규칙 바꾸기와 지금 계정 보이기, 워커가 없을 때 `no worker to restart` |

tmux 를 띄우는 테스트는 샌드박스 밖의 검증 명령에서 돌았습니다. 첫 실행에서 실패한 넷은 모두 테스트 쪽 문제였습니다. 테스트가 띄운 tmux 클라이언트가 `TMUX_TMPDIR` 를 받지 못해 다른 서버를 찾은 것(위 Bun 의 환경 변수), 실행 중에 넣은 프록시 변수, 작업 둘·리뷰 셋·회고가 도는 레포 테스트의 5초 제한입니다. 이 테스트들(`worker.test.ts`)은 칸 안에서 다시 뜨기(같은 칸 ID·같은 세션 ID·지시 없이), 답하던 도중 끊긴 차례의 결정과 그 답으로 이어 가기, 세 번 거듭 끝나면 멈추고 알리기, 계정 규칙을 바꿨을 때 쉬는 워커·답하는 워커·메시지를 받은 워커 각각의 다시 뜨기, 붙어 있는 사람을 기다리기(control mode 클라이언트), tmux 서버째 사라진 차례, tmux 서버의 환경 변수가 워커에 가지 않는지를 가짜 Claude 로 봅니다. 실제 Claude Code(2.1.309)로 레포 밖 작업 하나를 띄워 잰 것은 이렇습니다. 쉬는 워커의 Claude Code 를 SIGTERM 으로 끄면 지킴이가 같은 칸에서 같은 세션 ID 로 `--resume` 했고, 다음 메시지에 첫 지시의 내용을 기억해 답했습니다(대화 기록이 남음). 계정 규칙 파일을 대화 기록을 공유하는 다른 설정 폴더로 바꾸고 nod 명령을 한 번 돌리자, 쉬는 워커가 그 폴더로 다시 떴고 신뢰 확인 화면은 뜨지 않았습니다(nod 작업 폴더는 계정마다 미리 신뢰). 그 계정이 사용량 한도에 걸려 있자 메시지를 받은 차례가 `StopFailure` 로 끝나고 "한도가 풀리면 이어서 함"으로 남았고, 계정을 다시 바꿔도 "차례가 끝난 뒤"를 기다렸습니다. 이것이 위 "API 오류로 멈춘 차례" 처리를 더한 이유입니다. 고친 뒤 다시 재니, 한도에 걸린 계정에서 멈춘 첫 차례가 계정을 바꾸자 바로 새 계정으로 다시 떠서 이어 끝냈습니다. 그때 nod 명령을 연달아 부르면 한 번 더 다시 떠서 리뷰 중인 Stop 훅이 끊겼는데(아래 두 항목을 더한 이유), 고친 뒤에는 계정을 바꾸고 nod 명령을 1초마다 15번 불러도 한 번만 다시 떴고, 다음 차례는 리뷰까지 마쳤습니다. 로그인이 없는 설정 폴더로 바꾸면 Claude Code 는 끝나지 않고 처음 설정 화면(테마 고르기)에서 기다립니다. nod 는 그 폴더를 신뢰시키는 단계에서 신뢰 확인을 찾지 못해 실패하고, 세 번 거듭 실패하자 그 칸을 닫았습니다(약 45초). 레포 작업을 다른 설정 폴더로 다시 띄우면 Claude Code 가 그 레포를 신뢰할지 다시 물었습니다. 처음에는 이것이 이미 끝난 작업에 결정을 열었고(리뷰에서 찾음), 지금은 nod 가 그대로 받아 작업이 성공인 채로 새 계정으로 뜹니다. 다시 띄우라고 한 직후 보낸 `nod tell` 도 새 Claude Code 가 첫 메시지로 받아 답했습니다.

CLI 의 `nod tell` 도 차례 도중에 그 차례의 권한 결정이 열려 있거나, 어느 차례에든 레포 신뢰 결정이 열려 있으면 거절합니다. 신뢰 확인 화면은 "No, exit" 가 먼저 골라져 있어 Enter 가 Claude Code 를 끝냅니다. 사람이 칸에서 직접 신뢰한 결정은 그 차례가 끝날 때 `(it got past the trust dialog)` 로 닫힙니다. 권한 결정이 아직 기록되지 않은 틈(대화상자는 떴지만 Notification 훅이 결정을 적기 전)과, 사람이 칸에서 직접 답한 뒤 같은 차례에 다음 대화상자가 뜬 경우는 아직 막지 못합니다. 지금 칸에 그 대화상자가 있는지 보려면 Claude Code 의 권한 화면 문구를 실제 버전에서 재어야 합니다. 입력창은 쓰기 시작할 때 열려 있던 결정 번호(없으면 지시)를 붙잡아 보내고, 화면이 5초마다 새로 고쳐져 그 사이 결정이 열리거나 닫혔으면 보내지 않고 알립니다. 처음에는 보낼 때 화면에 열린 결정으로 보내서, 쓰는 중에 열린 결정의 답이 되었습니다(2026-10-23 리뷰). 라우터는 작업 화면끼리 옮길 때 컴포넌트를 다시 만들지 않으므로 입력창은 작업 번호를 key 로 둡니다. Yes/No 버튼에는 붙잡을 글이 없으므로, 열린 결정이 바뀐 뒤 1초 동안 누른 것은 답하지 않고 알립니다. 이전 결정을 보고 누르려던 클릭(두 번 누르기나 새로 고침 직전의 클릭)이 막 열린 결정을 승인하지 않게 하려는 것입니다. 다른 사이트가 브라우저를 통해 워커에게 지시를 넣지 못하게 막는 일은 TanStack Start 의 기본 CSRF 미들웨어에 맡깁니다. 이 미들웨어는 서버 함수에만 걸리므로, 같은 컴퓨터의 다른 페이지가 화면(보고·워커 화면·할 일)을 읽지 못하게 개발 서버와 빌드한 서버 모두 CORS 를 끕니다(`server.cors`·`preview.cors` 가 `false`). Vite 의 기본값은 localhost·127.0.0.1 의 모든 포트에 `Access-Control-Allow-Origin` 을 돌려줍니다(2026-10-23 리뷰). 워커가 쓴 Markdown 의 이미지는 그리지 않고 링크로 보입니다. 이미지는 화면을 여는 것만으로 브라우저가 불러오므로, 워커가 주소에 넣은 것이 샌드박스의 네트워크 제한 밖으로 나가기 때문입니다. 화면이 `nod ls` 와 같은 판정을 보이도록, 작업 상태("session ended")와 옆 메모 규칙은 `src/view.ts` 하나에 두고 CLI 와 화면이 함께 씁니다.
