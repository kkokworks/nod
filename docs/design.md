# nod 설계

nod 는 여러 에이전트를 동시에 돌려 일을 처리하고, 사람에게는 결정만 넘기는 오케스트레이터입니다. 사람은 고개만 끄덕이면(nod) 됩니다.

## 불변식

깨지면 안 되는 규칙입니다. 기능을 더할 때마다 이 다섯 가지를 지키는지 먼저 확인합니다.

1. 되돌릴 수 없는 일과 외부로 나가는 일은 사람의 결정 없이 일어나지 않습니다. 프롬프트로 부탁하지 않고 권한 설정으로 막습니다.
2. 모든 상태는 장부(SQLite)에 남습니다. 프로세스가 죽어도 무엇이 어디까지 됐는지 알 수 있습니다.
3. 워커가 끝났다고 보고해도 nod 가 직접 검증하기 전에는 끝난 것이 아닙니다.
4. 이슈·웹 문서처럼 밖에서 들어온 텍스트는 데이터일 뿐 지시가 아닙니다.
5. 동시에 돌면 안 되는 작업 조합(같은 파일 수정, 같은 포트)은 같이 돌리지 않습니다. 개수 자체는 제한하지 않습니다.

## 구조

```
사람 ─▶ Claude 세션(/nod 스킬) ─▶ nod CLI ─▶ 장부(~/.nod/nod.db)
                                     │            ▲
                                     ▼            │ Stop·Notification 훅
                              tmux 세션마다 Claude Code 워커 (작업 폴더 또는 worktree)
```

워커는 작업마다 nod 가 tmux 안에 띄운 실제 Claude Code 세션입니다. 화면 없는 `claude -p` 를 쓰지 않는 이유는, 한 작업 동안 같은 세션이 살아 있으면서 질문·검증 실패·후속 지시를 같은 맥락에서 이어 받게 하려는 것입니다. 이어 받을 맥락이 없는 독립 리뷰어만 `claude -p` 로 돕니다(아래 독립 리뷰). 사람은 `nod attach` 로 들어가 보거나 끼어들 수 있습니다. 상주하는 실행기는 없습니다. `nod add` 가 워커를 바로 띄우고, 워커가 멈출 때마다 Claude Code 의 훅이 `nod hook` 을 불러 장부를 갱신합니다. 앞 작업을 기다리는 작업도 앞 작업의 Stop 훅이 띄웁니다.

| 파일 | 하는 일 |
|---|---|
| `src/ledger.ts` | 장부. 작업(tasks)·시도(attempts)·결정(decisions)·작업 순서(task_deps)를 SQLite 에 기록합니다. 시도는 워커 세션의 한 턴입니다. 스키마는 `pragma user_version` 으로 버전을 매기고, 마이그레이션은 덧붙이기만 합니다. |
| `src/tmux.ts` | 워커 터미널. nod 홈마다 tmux 서버(소켓)를 따로 두고, 작업마다 tmux 세션 하나를 둡니다. 띄우기, 메시지 보내기(붙여넣기 + Enter), 키 보내기, 화면 읽기, 닫기를 합니다. |
| `src/worker.ts` | 워커 생명주기. 띄우기, Stop 훅 처리(보고 읽기 → 검증 → 다시 시키거나 결정 열기), Notification 훅 처리(권한 확인 → 결정), 답·후속 지시를 같은 세션에 보내기, 끝난 세션을 대화 기록에서 다시 열기, 앞 작업이 끝나면 기다리던 작업 띄우기. |
| `src/triggers.ts` | 트리거. 일정 계산, source 명령의 출력에서 새 항목 고르기, 때가 된 트리거로 작업 넣기(tick), OS 스케줄러에 매분 tick 등록·해제. |
| `src/notify.ts` | 결정이 열리거나 작업이 끝나는 등의 일이 생기면 사람이 둔 `<홈>/notify` 를 부릅니다. |
| `src/rules.ts` | 사람이 받아들인 규칙(`<홈>/rules.md`)과, 문제가 있었던 작업의 회고 지시. |
| `src/review.ts` | 독립 리뷰어가 받는 지시. 지시와 그 뒤 사람이 한 말, 검증 명령, 워커의 보고, 레포면 바뀐 파일 목록과 diff. |
| `src/gc.ts` | 오래전에 끝난 작업의 세션을 닫고, 작업 폴더·worktree·Claude 세션 폴더를 지웁니다. |
| `src/todos.ts` | 사람의 할 일과 프로젝트(GTD). 받아 적기, 명료화·정리, 완료, 칸마다 누가 무엇을 바꿨는지의 이력. |
| `src/todo-cli.ts` | `nod in`, `nod todo`, `nod project` |
| `src/cli.ts` | `nod`, `nod <결정> <답>`, `nod drop`, `nod add`, `nod tell`, `nod resume`, `nod attach`, `nod watch`, `nod ls`, `nod show`, `nod stats`, `nod gc`, `nod trigger add·ls·rm`, `nod tick`, `nod hook` |
| `skills/nod/SKILL.md` | Claude 세션을 앞단으로 만드는 스킬입니다. 요청을 작업으로 나눠 넣고, `nod watch` 를 Monitor 로 걸어 결정을 바로 전합니다. 결정은 대신 내리지 않습니다. |
| `skills/wide-research/`, `agents/wide-item.md` | 항목 여러 개 × 같은 칸 비교 조사. 세션 안 서브 에이전트로 돌고 nod 장부·워커는 쓰지 않습니다. 항목마다 맥락을 새로 써야 뒤 항목의 조사가 얕아지지 않고, 결과가 세션으로 바로 돌아와 표로 합치기 쉬워서입니다. `merge.ts` 가 결과 줄을 검사해 표·CSV 로 합칩니다. |

## 장부로 답하는 질문

장부 구조는 아래 질문에서 출발해 정했습니다. 새 컬럼을 더할 때도 어느 질문에 답하는지 먼저 적습니다.

| 누가 | 질문 | 데이터 | 명령 |
|---|---|---|---|
| 사람 | 지금 내가 결정할 게 뭐지? | 열린 결정, 질문, 작업 | `nod` |
| 사람 | 일하는 중에 결정할 게 새로 생겼나? | 새로 열린 결정 | `nod watch` (Claude 세션이 알림으로 받음) |
| 사람 | 이 작업 지금 어디까지 됐지? | 작업 상태, 턴 수, 마지막 보고, 세션이 살아 있는지 | `nod ls` |
| 사람 | 이 작업에 무슨 일이 있었지? | 턴 이력(종류·결과·검증·세션 ID), 결정과 답 | `nod show <작업>` |
| nod | 이 훅은 어느 작업의 것이지? | 시도의 세션 ID | `nod hook` |
| nod | 이 작업은 지금 띄울 수 있나? | 작업 순서, 앞 작업들의 상태 | `nod hook`, `nod add --after` |
| 사람 | 이 작업은 무엇을 기다리지? | 작업 순서 | `nod ls`, `nod show <작업>` |
| 사람 | 세션이 끊긴 작업을 어디서 이어 가지? | 마지막 세션 ID (Claude Code 가 대화 기록을 가짐) | `nod resume <작업>` |
| 사람 | 이 방식이 효과가 있나? | 결정 없이 끝난 작업 수, 턴·재시도 수, 결정 대기 시간 중앙값 | `nod stats` |
| nod | 지금 돌릴 트리거가 있나? | 트리거의 일정, 마지막 실행 시각 | `nod tick` |
| nod | 이 항목은 이미 작업이 됐나? | 트리거가 본 항목과 그 작업 | `nod tick` |
| 사람 | 이 작업은 어디서 왔지? 트리거가 왜 안 돌지? | 작업을 넣은 트리거, 마지막 실행의 오류 | `nod show`, `nod trigger ls` |
| nod | 이 작업을 회고할까? | 재시도 턴, failed·check_failed 결정, 이미 있는 회고 | `nod hook`, `nod drop` |
| 사람 | 이 규칙은 어디서 나왔지? | 회고 작업이 돌아본 작업(`retro_of`) | `nod show <회고 작업>` |
| 사람 | 이 작업의 결과는 어디로 갔지? 아직 안 내보낸 건 뭐지? | 작업의 링크(PR·게시한 리뷰 주소), 링크 전에는 작업 브랜치를 품은 원격 브랜치 | `nod link`, `nod ls`, `nod show <작업>` |
| 사람 | 아직 손볼 작업은 뭐지? | gc 한 시각(`collected_at`) | `nod ls` (gc 한 작업은 `--all` 로만) |

`succeeded` 는 워커가 자기 몫을 끝냈다는 뜻이지, 결과가 머지됐다는 뜻이 아닙니다. 결과를 내보내는 일은 루트 세션이 nod 밖에서 하므로, nod 는 머지 여부를 직접 확인하지 않고 결과가 간 곳의 주소만 기록합니다. 머지를 기준으로 작업을 닫지 않는 이유는 세 가지입니다. 결과가 PR 이 아닌 작업이 있고, 작업과 PR 이 1:1 이 아니며, 코어가 특정 git 서비스에 묶이기 때문입니다. 링크를 달기 전에는 작업 브랜치의 끝 커밋을 품은 원격 브랜치를 git 으로 찾아 보여 줍니다(`pushed`). 다른 세션이 다른 이름으로 push 해도 찾을 수 있고, nod 는 fetch 하지 않으므로 마지막 fetch 기준입니다. 이 브랜치를 PR 주소로 바꿔 링크하는 일은 스킬이 git 서비스 CLI 로 합니다. 대신 사람이 결과를 다 처리했다고 gc 하면, 그 시각을 남기고 `nod ls` 에서 뺍니다. gc 는 Claude 세션 폴더도 지우므로 그 뒤에는 resume 할 수 없습니다. 그래서 리뷰가 끝난 뒤에 합니다.

결정 대기 시간(결정이 생겨서 사람이 답할 때까지)이 가장 중요한 지표입니다. 여러 에이전트를 돌리면 병목은 사람의 판단으로 옮겨 가기 때문입니다. 대화형 세션은 비용을 알려 주지 않아서, 지금은 비용을 기록하지 않습니다(`claude -p` 시절 시도에만 남아 있음).

## 작업 흐름

```
nod add ─▶ tmux 에 워커 세션 (지시가 첫 메시지)
워커가 멈춤 ─▶ Stop 훅이 마지막 메시지의 보고 줄(NOD: done|question|failed)을 읽음
   ├─ done ─▶ 회고 작업이면 검증 없이 ─▶ 규칙 결정(rule), 규칙이 없으면 완료
   │          검증 통과 (검증 명령, 레포면 커밋, 독립 리뷰) ─▶ 완료 ─▶ 기다리던 작업 중 앞 작업이 모두 성공한 것을 띄움
   │          검증 실패 ─▶ 훅이 멈춤을 막고(block) 실패 출력을 돌려줌 ─▶ 같은 턴이 이어짐 (최대 2회) ─▶ 그래도 실패면 결정
   ├─ question, 또는 보고 줄 없음 ─▶ 결정(question)
   └─ failed ─▶ 결정(failed)
권한 확인 화면 ─▶ Notification 훅 ─▶ 결정(permission), 화면 내용 포함
아직 신뢰하지 않은 레포 ─▶ 신뢰 확인 화면 ─▶ 결정(trust)
결정 ─▶ nod <결정> <답> ─▶ 살아 있는 같은 세션에 "Human decision: <답>"
        permission: yes ─▶ Enter / 그 밖 ─▶ Esc 로 거절하고 새 턴으로 답을 전함
        trust: yes ─▶ 신뢰하고 시작 / 그 밖 ─▶ cancelled, 세션 닫음
        rule: yes ─▶ <홈>/rules.md 에 추가 / 그 밖 ─▶ 버림
검증에 되돌려졌거나 failed·check_failed 였던 작업이 끝남(성공 또는 drop) ─▶ 회고 작업 ─▶ 규칙 제안 ─▶ 결정(rule)
     └▶ nod drop <결정> ─▶ cancelled, 세션 닫음
nod tell <작업> <지시> ─▶ 같은 세션에 후속 지시 (세션이 끝났으면 대화 기록에서 다시 열고 보냄)
nod add --after <작업> ─▶ 대기(queued) ─▶ 앞 작업이 모두 성공하면 그 Stop 훅이 띄움 (같은 레포면 앞 작업의 브랜치에서 시작)
                       └▶ 앞 작업이 cancelled ─▶ 함께 cancelled
```

워커는 최소한의 맥락만 받습니다. 작업 지시와 짧은 워커 규칙(`WORKER_PROMPT`)뿐이고, 워커끼리는 서로를 모릅니다. 사람이 워커 화면에 직접 입력한 턴도 멈출 때 훅이 받아 `followup` 시도로 기록합니다.

## 작업 순서 (M4)

계획은 루트 세션이 세웁니다. 사용자의 맥락을 가진 쪽이 루트 세션이기 때문입니다. nod 는 그 계획을 지키는 장치만 둡니다.

- **잇기.** `nod add --after 3,4` 로 넣은 작업은 대기(queued)하다가, 앞 작업이 모두 성공하는 순간 마지막으로 성공한 작업의 Stop 훅이 띄웁니다. 두 워커가 동시에 끝나도 한 번만 뜨도록, 띄울 작업을 고르고 running 으로 바꾸는 일을 SQL 문장 하나로 합니다.
- **같은 레포는 이어 쌓기.** 처음에는 "경로가 겹치는 작업을 떼어 놓기"를 계획했습니다. 그런데 워커마다 worktree 가 따로 있어서 실행 중에 파일이 겹칠 일은 없고, 진짜 문제는 나중에 브랜치를 합칠 때의 충돌입니다. 그래서 같은 레포에서 이어지는 작업은 앞 작업의 브랜치에서 worktree 를 만듭니다. 한 레포 안에서는 앞 작업을 하나만 둘 수 있습니다. 두 갈래를 nod 가 합치면 merge commit 이 생기고, 충돌이 나면 어느 쪽을 살릴지 판단해야 하기 때문입니다.
- **브랜치와 worktree 에 이름.** 처음에는 `nod/<작업>` 브랜치와 `<홈>/work/<작업>` 폴더를 썼는데, 번호만으로는 무슨 일인지 알 수 없었습니다. 그래서 레포 작업은 `--branch` 로 이름을 받고, worktree 를 `<홈>/work/<레포 폴더 이름>/<브랜치>` 에 둡니다. 브랜치 이름이 겹치지 않으면 폴더도 겹치지 않습니다. worktree 를 레포 옆에 두는 안도 있었지만, gc 의 「`<홈>/work` 밖은 지우지 않는다」는 안전장치를 풀어야 해서 택하지 않았습니다.
- **gc 의 브랜치 정리.** 브랜치는 원격 브랜치가 그 커밋을 갖고 있을 때 지웁니다. squash 머지 뒤 원격 브랜치를 지우면 커밋을 가진 원격 브랜치가 남지 않으므로, 원격 기본 브랜치가 그 브랜치가 바꾼 파일을 같은 내용으로 갖고 있어도 머지된 것으로 봅니다. 둘 다 아니면 브랜치가 유일한 사본이라 남깁니다.
- **커밋 확인.** 이어 쌓으려면 앞 작업이 커밋을 남겨야 합니다. 그래서 레포 작업은 검증 명령이 통과해도 커밋하지 않은 변경이 있으면 같은 턴으로 돌려보냅니다. `nod gc` 도 커밋만 남기므로 원래 필요한 확인이었습니다.
- **앞 작업의 보고 전달.** 뒤 작업의 첫 메시지에 앞 작업들의 지시와 보고 한 줄을 덧붙입니다. 워커는 첫 메시지 밖의 것을 모르기 때문입니다.
- **앞 작업이 끝나지 못하면.** 사람이 drop 해서 cancelled 가 되면 기다리던 작업도 연쇄로 cancelled 가 됩니다. error 는 `nod resume` 으로 살릴 수 있어서 뒤 작업을 그대로 기다리게 둡니다.

**실측 (2026-10-06, Claude Code 2.1.290, haiku).** 처음 보는 레포에 작업 1(hello.txt 만들기)과 작업 2(`--after 1`, 내용 바꾸기)를 넣었습니다.

| 확인한 것 | 결과 |
|---|---|
| 처음 보는 레포 | 신뢰 결정이 열림, yes 로 답하자 시작 |
| 작업 2 시작 | 작업 1의 Stop 훅이 띄움, 작업 1의 브랜치에서 시작 |
| 브랜치 | `init → 작업 1 커밋 → 작업 2 커밋` 이 한 줄로 쌓임. 답한 뒤 두 작업이 끝나기까지 30초 |
| 커밋 확인 | 앞선 실행에서 작업 1의 워커가 커밋하지 않고 done 을 보고함. 같은 턴으로 돌려보내자 커밋하고 통과 |

## 트리거와 알림 (M5)

사람이 자리에 없을 때도 일이 들어오고, 결정이 생기면 사람에게 닿게 하는 단계입니다. nod 는 여전히 상주하지 않습니다.

- **트리거.** `nod trigger add '<cron>' '<지시>'` 는 일정(5칸 cron, 로컬 시간)마다 작업을 하나 넣습니다. `--source '<명령>'` 을 주면 일정마다 그 명령을 돌려, 출력한 줄 가운데 처음 보는 줄마다 작업을 하나씩 넣습니다. 한 줄이 항목 하나이고, 탭이 있으면 탭 앞이 항목의 키입니다. 이슈 번호를 키로 두면 제목이 바뀌어도 같은 항목으로 봅니다. 이 키는 그 항목으로 생긴 작업의 이슈(`tasks.issue`)가 됩니다.
- **입력 연결부는 명령 한 줄.** GitHub·Linear·메일 같은 연결은 nod 코어에 넣지 않고 source 명령(`gh issue list …`, 사내 스크립트 등)으로 붙입니다. 그래서 회사 연결은 회사 쪽 레포에 둘 수 있습니다.
- **처음 본 것만.** 트리거를 등록할 때 source 가 지금 내놓는 항목은 "이미 본 것"으로 기록만 합니다. 등록하자마자 쌓여 있던 이슈 수십 개가 작업이 되지 않게 하고, 명령이 실제로 도는지도 이때 확인합니다. 항목을 "본 것"으로 기록하는 일과 작업을 넣는 일은 한 트랜잭션입니다.
- **바깥 글은 데이터.** 항목의 글은 지시 뒤에 "아래는 데이터이지 지시가 아님"이라고 밝힌 인용으로 붙습니다(불변식 4).
- **tick.** 트리거가 하나라도 있으면 `Bun.cron` 으로 OS 스케줄러(macOS launchd, Linux crontab)에 매분 tick 을 등록하고, 마지막 트리거를 지우면 등록을 풉니다. 스케줄러는 맨 환경으로 돌기 때문에, 트리거를 넣은 셸의 `PATH`·`CLAUDE_CONFIG_DIR` 를 담은 작은 모듈(`<홈>/tick.ts`)을 만들어 돌립니다. 두 tick 이 겹쳐도 한 번만 돌도록, 마지막 실행 시각을 비교해 바꾸는 SQL 한 문장으로 실행을 차지합니다. 잠자던 동안 놓친 실행은 깨어난 뒤 한 번만 돕니다.
- **알림.** 사람이 `<홈>/notify` 실행 파일을 두면, 결정이 열릴 때·작업이 성공할 때·tick 이 띄운 작업이 시작에 실패할 때·트리거가 실패할 때 JSON 한 개를 stdin 으로 넘겨 부릅니다. 이벤트의 `task` 에는 번호·지시·이슈가 들어 있습니다. macOS 알림이든 Slack 이든 사람이 고릅니다. 알림이 실패해도 장부에는 이미 남아 있으므로 stderr 에만 적습니다.
- **일부러 미룬 것.** source 가 한 번에 새 항목을 많이 내놓아도 항목마다 워커가 뜹니다. 남이 항목을 만들 수 있는 source 라면 상한이나 승인 단계를 붙일 자리입니다.

**실측.** Bun 1.3.14 의 `Bun.cron.parse` 는 `tz` 옵션이나 `TZ` 환경변수와 관계없이 모든 일정을 UTC 로 읽었습니다("0 9 * * *" 의 다음 실행이 한국 시간 18시). 그래서 로컬 시각을 UTC 인 것처럼 넣고 결과를 되돌려 씁니다. 일광 절약 시간이 바뀌는 날에는 한 시간 어긋날 수 있습니다.

끝까지 돌린 시나리오(2026-10-06, macOS, haiku): 파일을 `cat` 하는 source 트리거를 `* * * * *` 로 등록하고 파일에 한 줄을 더했습니다.

| 확인한 것 | 결과 |
|---|---|
| 등록 | launchd 에 `bun.cron.nod-tick-<홈 ID>` 가 올라감. 그때 비어 있던 source 는 "0개를 이미 봄"으로 기록 |
| 실행 | 15:29:55 에 한 줄 추가 → 15:30 tick 이 작업을 넣고 워커를 띄움 → 15:30:17 검증 통과. launchd 에서 띄운 워커도 Claude 로그인을 그대로 씀 |
| 알림 | `<홈>/notify` 가 `succeeded` 이벤트를 받음 |
| 해제 | `nod trigger rm` 뒤 launchd 목록과 LaunchAgents 에서 사라짐 |

## 회고와 규칙 (M6)

같은 실패가 되풀이되지 않게, 문제가 있었던 작업에서 규칙을 뽑아 사람이 받아들인 것만 모든 워커에 줍니다.

- **언제 회고하나.** 검증이 워커를 되돌려 보낸 적이 있거나(재시도 턴), 워커가 포기했거나(failed), 재시도를 다 써도 검증이 실패한(check_failed) 작업이 끝날 때입니다. 끝난다는 것은 성공했거나 사람이 drop 한 것입니다. 질문·권한·신뢰는 평범한 결정이라 회고하지 않습니다. 한 작업에 회고는 한 번이고, 회고 작업은 다시 회고하지 않습니다.
- **회고 워커.** 회고도 작업 하나이고(`retro_of` 가 돌아볼 작업을 가리킴), 빈 폴더에서 같은 모델로 돕니다. 첫 메시지에는 그 작업의 지시·턴(결과, 보고, 검증 출력)·결정과 답, 그리고 워커가 이미 받는 규칙 전부가 데이터로 들어갑니다. 원래 작업의 대화나 루트 세션의 맥락은 받지 않습니다. 다른 작업에도 쓸 만한 규칙 한 줄을 보고하거나, 없으면 `none` 을 보고합니다.
- **결정.** 제안은 결정(rule)이 되고, 사람이 yes 라고 답하면 `<홈>/rules.md` 에 한 줄이 붙습니다. 그 밖의 답이면 버립니다. 규칙은 다음에 뜨는 모든 워커의 시스템 프롬프트에서 기본 규칙 뒤에 붙습니다. 파일은 사람이 직접 고쳐도 됩니다.
- **일부러 하지 않은 것.** 회고가 샌드박스 허용 도메인이나 nod 의 코드를 바꾸지는 않습니다. 그런 변경은 사람이 직접 합니다.

**실측 (2026-10-06, haiku).** 지시는 "count.txt 에 3", 검증은 `grep -qx 4 count.txt` 로 일부러 어긋나게 넣었습니다. 워커가 3 을 쓰고 done 을 보고하자 검증이 되돌려 보냈고, 4 로 고쳐 통과했습니다(27초). 이어서 회고 작업이 스스로 떠서 "자동 승인 조건이 지시사항과 다르면 작업 시작 전에 보고" 를 제안했고, yes 로 답하자 `rules.md` 에 붙었습니다. 다음에 띄운 워커의 실행 인자에 그 규칙이 들어 있었습니다. 다만 지금 워커는 검증 명령을 실패한 뒤에야 보기 때문에 이 규칙을 지킬 방법이 없습니다. 회고가 nod 자체의 빈틈(검증 명령을 처음부터 알려 주지 않음)을 드러낸 사례입니다. 이 빈틈은 실사용 개선에서 메웠습니다(아래).

## 독립 리뷰 (2026-10-19)

검증 명령과 커밋 확인만으로는 막지 못하는 빈틈이 셋 있었습니다. 워커가 테스트를 약하게 고쳐 검증 명령을 통과시켜도 nod 는 알 수 없었습니다. 검증 명령이 없는 작업은 워커의 말만 믿었습니다. 사람이 `nod tell` 로 지시를 바꾸면, `nod add` 때 정한 검증 명령은 바뀐 지시를 따라가지 못했습니다. 그래서 워커가 done 을 보고하고 검증 명령과 커밋 확인을 통과하면, 워커의 대화를 모르는 리뷰어가 결과를 한 번 더 봅니다.

- **리뷰어가 받는 것.** 지시, 그 뒤 사람이 한 말(`nod tell` 과 결정의 답)을 순서대로, 검증 명령과 통과 여부, 워커의 마지막 보고입니다. 레포 작업이면 브랜치가 시작된 뒤로 바뀐 파일 목록(`git diff --stat`)과 diff 전체를 nod 가 직접 뽑아 지시문에 넣습니다. 처음에는 리뷰어에게 `git diff` 로 읽으라고만 했는데, 그러면 diff 를 얼마나 읽을지 리뷰어가 정하게 되어 일부만 보고 넘어갈 수 있었습니다. 바뀐 파일 목록이 맨 위에 있으니 테스트 파일이 바뀌었는지도 바로 보입니다. diff 는 20만 자까지 넣고, 넘으면 어디서 잘렸는지 알려 나머지는 리뷰어가 직접 읽게 합니다. 시작 커밋은 브랜치 reflog 의 가장 오래된 항목에서 읽습니다. `worktree add -b` 가 시작점을 남기고, 이후 커밋은 항목을 더할 뿐이기 때문입니다.
- **판정.** 사람이 요청한 것을 하지 않았거나, 테스트·검증 명령을 약하게 고쳐 통과시켰거나, 보고가 결과와 다르면 실패입니다. 스타일이나 요청하지 않은 것으로는 실패시키지 않습니다. 실패하면 리뷰어의 지적이 검증 실패와 똑같이 같은 턴으로 돌아갑니다. 그래서 재시도 2회, 그 뒤 check_failed 결정, 끝난 뒤 회고까지 기존 흐름을 그대로 탑니다.
- **화면 없는 `claude -p`.** 워커를 대화형 세션으로 두는 이유는 맥락을 이어 받기 위해서입니다. 리뷰어는 판정을 한 번만 하고 이어 받을 맥락이 없어서 예외로 둡니다. Stop 훅 안에서 돌고 10분이 넘으면 끊깁니다. 검증 명령과 리뷰가 모두 훅 안에서 돌므로 Stop 훅 제한 시간을 30분으로 늘렸습니다.
- **판정하지 못하면 통과시키지 않습니다.** 리뷰어가 실패로 끝나거나, 판정 줄 없이 끝나거나, 레포 worktree 를 바꾸면 작업은 error 가 됩니다. 리뷰어는 Edit·Write 도구가 막혀 있고, 셸은 워커와 같은 샌드박스에서 돕니다. 다만 샌드박스는 작업 폴더 쓰기를 허용하므로, 리뷰가 끝난 뒤 HEAD 와 커밋하지 않은 변경을 확인합니다.
- **회고 작업은 리뷰하지 않습니다.** 회고의 결과는 규칙 제안이고, 그 판단은 사람이 결정으로 합니다.
- **일부러 하지 않은 것.** 리뷰를 끄는 옵션은 두지 않았습니다. 필요해지면 그때 더합니다. 리뷰어가 테스트를 직접 돌려야 한다면 리뷰어용 worktree 를 따로 만들어야 합니다.

**실측 (2026-10-19, Claude Code 2.1.302, haiku).**

- 워커의 Stop 훅 안에서 `claude -p` 가 중첩으로 돌았고, 부모 세션 ID 를 이어받지 않고 새 세션으로 기록됐습니다. `--disallowedTools` 는 인자를 여러 개 받아 뒤에 오는 프롬프트까지 삼키므로, 지시는 stdin 으로 넘깁니다.
- 정상 경로: 버그가 있는 덧셈 함수를 고치라는 레포 작업에서 워커가 고치고 done 을 보고했습니다. 리뷰어는 "테스트·검증 게이트는 그대로이며 보고가 커밋과 일치한다"며 통과시켰습니다. 작업 전체는 47초였습니다.
- 약하게 고친 테스트: 버그는 두고 테스트 기댓값만 5 에서 -1 로 바꾼 커밋(`bun test` 는 통과)을 같은 지시문으로 리뷰하게 했습니다. 리뷰어는 구현이 그대로이고, 기댓값을 버그의 결과로 바꿨으며, 보고가 사실과 다르다고 짚어 실패로 판정했습니다. worktree 는 바뀌지 않았습니다.
- diff 를 지시문에 넣도록 바꾼 뒤 다시 쟀습니다. 테스트 기댓값만 바꾼 커밋은 실패로, 구현을 `a + b` 로 제대로 고친 커밋은 통과로 판정했습니다(각 1회). 두 경우 모두 worktree 는 바뀌지 않았습니다.

## 할 일 (G1, 2026-10-20)

nod 장부에 사람이 할 일을 GTD 방식으로 둡니다. 목표와 단계는 이슈 #1, 이 단계는 #2 입니다. 할 일은 작업이 아닙니다. 사람이 할 일이고, G2 부터는 작업에 맡길 수 있습니다. 코드는 `src/todos.ts`(장부)와 `src/todo-cli.ts`(명령)에 따로 둡니다. `ledger.ts` 에는 마이그레이션(v10)을 더하고, 두 모듈이 함께 쓰도록 쿼리 빌더(`queryBuilder`)와 실행 함수(`runQuery`)를 꺼냈습니다.

### 할 일 장부로 답하는 질문

| 누가 | 질문 | 데이터 | 명령 |
|---|---|---|---|
| 사람 | 지금 이 상황에서 할 수 있는 다음 행동은? | 상태 next, 상황(없으면 어디서나) | `nod todo next --context @x` |
| 사람 | 받은 일함에 무엇이 언제부터 쌓였나? | 상태 inbox, 상태가 바뀐 시각 | `nod todo inbox` |
| 사람 | 무엇을 누구에게 기다리고 있고, 얼마나 됐나? | 상태 waiting, 기다리는 사람, 상태가 바뀐 시각 | `nod todo waiting` |
| 사람 | 다음 행동이 없는 프로젝트는? | 프로젝트별 next·waiting 수 | `nod project` |
| 사람 | 이 할 일은 어디서 왔나? | 통로(`source`)와 그 통로의 키, 링크 | `nod todo <할 일>` |
| 스킬 | 이 항목을 이미 받아 적었나? | 같은 통로의 같은 키 | `nod in --source <통로> --key <키>` |
| 사람 | 누가(사람·Claude 세션·워커) 무엇을 바꿨나? | 할 일·프로젝트 이력의 누가(`actor`) | `nod todo <할 일>`, `nod project <프로젝트>` |

받은 일함을 언제 비웠는지, 이번 주에 무엇을 끝냈는지도 이력에 남지만, 그걸 보여 주는 명령은 주간 리뷰를 옮기는 G4 에서 만듭니다.

### 정한 것과 이유

- 칸은 지금 쓰는 GTD 앱(Mindwtr)의 실제 쓰임을 세어 정했습니다(항목 161개, 프로젝트 6개). 상황은 항목마다 0~1개라 한 칸입니다. 대기 6개 중 5개가 사람을 기다려서 기다리는 사람 칸을 두었고, 링크가 110개라 링크 표를 두었습니다. 체크리스트는 대부분 nod 결정을 옮겨 적은 것이라 두지 않았습니다. 태그·영역·예상 시간은 거의 쓰지 않아 뺐고, 날짜(마감·시각·반복·오늘 집중)는 G3 에서 다룹니다.
- 상태는 GTD 의 목록을 그대로 씁니다: inbox·next·waiting·someday·reference·done·dropped. 지우지 않고 dropped 로 둡니다. 상태 값은 작업 상태처럼 코드(`todos.ts`)에서 검사하고 DB 의 check 제약은 두지 않습니다. SQLite 의 check 제약은 표를 다시 만들어야 바뀌는데, 이 표를 가리키는 외래 키 때문에 마이그레이션 안에서 다시 만들기가 어렵습니다. 상태 하나를 더할 때마다 그 비용을 치르지 않으려는 것입니다.
- 받아 적기는 판단 없이 가장 빨라야 해서 `nod in` 하나로 둡니다. 정리는 `nod todo set` 한 명령으로 여러 칸을 한 번에 바꿉니다. 에이전트가 명료화 결과를 한 번에 반영하기 쉽고, 바뀐 칸들이 이력 한 줄로 남습니다.
- 할 일은 `t<번호>`, 프로젝트는 `p<번호>` 로 쓰고, 맨 숫자는 받지 않습니다. `nod 12 …` 는 결정에 답하고 `nod drop 12` 는 작업을 끝내므로, `todo` 를 빠뜨린 명령이 결정이나 작업으로 가지 않게 하려는 것입니다. 같은 이유로 프로젝트 이름은 `p3`·`3` 처럼 생길 수 없습니다.
- 할 일과 프로젝트의 이력(`todo_changes`, `project_changes`)에는 칸마다 전·후 값과 누가 바꿨는지를 남깁니다. 누가는 실행한 곳으로 정합니다. `NOD_ACTOR` 가 있으면 그 값(웹 화면은 `human:ui`), nod 워커면 `worker:<작업>`(nod 가 워커 환경에 `NOD_TASK` 를 넣음), Claude 세션이면 `claude:<세션 ID 앞 8자>`, 그 밖은 `human` 입니다. 이 값은 누가 실행했는지이지, 사람이 확인했는지가 아닙니다. 사람이 채팅으로 확인하고 Claude 가 반영한 변경도 `claude:…` 입니다. 확인 여부를 따로 남길지는 사람 확인 없이 해도 되는 일의 경계를 정하는 G4 에서 정합니다.
- 끝났거나 버린 프로젝트에는 열린 할 일이 있을 수 없습니다. 열린 할 일이 남은 프로젝트는 끝낼 수 없고, 끝난 프로젝트로 열린 할 일을 옮기거나 그 안의 할 일을 다시 열 수도 없습니다. 끝난 프로젝트 아래의 다음 행동은 프로젝트 점검에서 빠지기 때문입니다.
- 언젠가(someday)로 미룬 프로젝트의 할 일은 목록에서 빠집니다. 프로젝트를 미루면 그 행동도 미룬 것이기 때문입니다. `--project` 로 그 프로젝트를 고르거나 `--all` 이면 보입니다.
- 상황은 `@` 로 시작하게 맞춥니다(`phone` 과 `@phone` 은 같은 상황). 상황이 없는 할 일은 어디서나 할 수 있는 일로 보고, 상황으로 거를 때도 함께 보입니다. 실측에서 다음 행동 14개 중 13개가 상황이 없었습니다.
- 대기에서 벗어나면 기다리던 사람을 지웁니다(이력에는 남음). 나중에 다시 대기로 바꿀 때 예전 사람이 그대로 남지 않게 하려는 것입니다.
- 같은 통로의 같은 키는 한 번만 들어갑니다(유니크 인덱스). 업무 도구를 여러 번 훑어도 같은 항목이 두 번 들어가지 않습니다. 링크로도 중복을 가리는 일은 모으기를 옮기는 G4 에서 합니다.
- 장부를 열 때 `busy_timeout` 을 WAL 전환보다 먼저 겁니다. 반대 순서에서는 여러 프로세스가 동시에 열면 30번 중 1번꼴로 `database is locked` 가 났습니다. 마이그레이션은 immediate 트랜잭션 안에서 버전을 다시 읽어, 동시에 연 다른 프로세스가 같은 마이그레이션을 두 번 돌리지 않게 합니다. 고친 뒤 동시 받아 적기 150번이 모두 들어갔습니다.
- 개발 중 주의: `ui/` 개발 서버가 켜져 있으면, 코드가 바뀔 때 서버가 장부 모듈을 다시 불러오면서 새 마이그레이션을 실제 장부(`<홈>/nod.db`)에 바로 적용합니다. 커밋 전에 마이그레이션을 고쳐야 하면 서버를 끄고 고칩니다.

## 대화형 워커 실측 (2026-10-06, Claude Code 2.1.290, haiku)

**훅.** Stop 훅 입력에 `session_id`, `last_assistant_message`, `stop_hook_active` 가 옵니다. 그래서 결과를 파일이나 파이프로 따로 받지 않고 마지막 메시지의 보고 줄을 읽습니다. Stop 훅이 `{"decision":"block","reason":…}` 을 내면 같은 턴이 그 이유를 받아 이어집니다. 이렇게 이어진 턴의 마지막 메시지에는 보고 줄이 빠지는 일이 있어서, 이때(`stop_hook_active`)는 검증 결과로 판단합니다. 권한 확인 화면이 뜨면 Notification 훅이 `notification_type: permission_prompt` 로 옵니다.

**같은 세션에 이어 보내기.** 끝난 세션에 tmux 로 메시지를 넣으면 새 턴이 돌고, 첫 메시지에서 알려 준 단어를 기억했습니다. 세션을 강제로 닫은 뒤 `claude --resume <세션>` 으로 다시 열어도 앞에서 정한 언어("한국어")를 기억했습니다.

**폴더 신뢰.** 대화형 세션은 처음 보는 폴더에서 신뢰 확인 화면을 띄웁니다. 상위 폴더를 신뢰하면 하위 폴더에서는 묻지 않았습니다. 그래서 nod 는 처음 한 번 `<홈>/work` 를 신뢰합니다. 그 안에는 nod 가 만든 폴더와 사람이 지정한 레포의 worktree 만 생깁니다. 화면이 뜨자마자 보낸 키는 무시됐기 때문에, 선택된 항목을 화면에서 읽어 "Yes" 가 선택됐을 때만 Enter 를 누릅니다(측정 시 2초).

**worktree 의 신뢰.** worktree 는 `<홈>/work` 아래에 있어도 신뢰 확인 화면이 떴습니다. 화면에서 "Yes" 를 고르자 신뢰 목록에 worktree 가 아니라 원래 레포 경로가 기록됐습니다. Claude Code 는 worktree 를 원래 레포 기준으로 따지는 것입니다(M4 실측). 레포를 신뢰하면 그 레포에 들어 있는 Claude 설정과 훅이 워커에서 돌기 때문에, nod 는 이 화면을 자동으로 넘기지 않고 결정(trust)으로 올립니다. 레포 작업은 SessionStart 훅이 표시 파일을 만들 때까지 기다려서, 신뢰 화면에 걸렸는지 알아냅니다.

**권한 거절.** 권한 확인에서 Esc 는 "No" 이면서 그 턴을 끝내 버리고, 이때는 Stop 훅이 오지 않았습니다. 그래서 거절할 때는 Esc 뒤 화면에 "Interrupted" 가 뜨는 것을 확인하고, 그 턴을 닫은 다음 사람의 답을 새 턴으로 보냅니다.

**세션 닫기와 gc.** tmux 세션을 닫은 직후 Claude 세션 폴더를 지웠더니, 종료 중인 Claude 가 파일을 써서 폴더가 다시 생겼습니다. 그래서 세션을 닫을 때 프로세스가 끝날 때까지 기다립니다.

**끝까지 실행한 시나리오.** 4개를 동시에 띄웠습니다.

| 시나리오 | 결과 |
|---|---|
| 검증 있는 파일 작업 | 첫 턴에 통과 |
| 검증 실패 (`count.txt` 를 3으로 만들라 하고 4인지 검증) | 훅이 돌려보내자 같은 턴에서 4로 고치고 통과 |
| 질문 → 결정 → "한국어" | 같은 세션이 한국어 인사말 작성 |
| WebFetch → 권한 결정 → 거절 | 새 턴으로 거절 사유를 받고 건너뛰었다고 보고 |
| 끝난 작업에 `nod tell` | 같은 세션이 후속 지시 수행, 검증 통과 |
| 세션을 죽인 뒤 `nod tell` | 대화 기록에서 다시 열고 앞의 맥락으로 답함 |
| `nod drop` | cancelled, 세션 닫힘 |
| `nod gc --older-than 0` | 세션·작업 폴더·세션 폴더 모두 지움 |

## `claude -p` 시절 실측 (2026-10-05, Claude Code 2.1.289, MacBook 32GB·10코어)

M1~M3.5 의 워커는 `claude -p` 였습니다. 아래는 그때 잰 값이고, 권한·샌드박스 결과는 지금 워커에도 그대로 씁니다. 대화형 워커의 동시 실행 비용은 아직 재지 않았습니다.

**동시 실행.** 같은 작업(파일 하나 쓰기, haiku)을 한꺼번에 돌린 결과입니다. 워커 하나가 약 270MB 를 썼고, 32개에서 작업 평균이 15초로 느려졌습니다.

| 동시 수 | 전체 시간 | 작업 평균 | 최대 메모리 | 성공 |
|---|---|---|---|---|
| 8 | 11초 | 10초 | 2.3GB | 8/8 |
| 16 | 11초 | 11초 | 4.5GB | 16/16 |
| 32 | 17초 | 15초 | 8.5GB | 32/32 |

**worktree 동시 생성.** 한 레포에 `git worktree add` 를 32개 동시에 실행해도 실패가 없었습니다. 그래서 잠금을 두지 않았습니다.

**권한 모드.** `auto` 는 비대화 실행에서 파일 쓰기와 셸 명령을 모두 거부했고, `acceptEdits` 는 파일 쓰기만 통과시켰습니다. 그래서 `acceptEdits` 와 샌드박스를 함께 썼습니다. 워커는 사용자 설정(CLAUDE.md·훅·MCP)을 물려받습니다.

대화형 워커로 바꾼 뒤(2026-10-07) `auto` 로 바꿨습니다. 실제로 써 보니 샌드박스 안의 단순한 명령은 묻지 않고 지나갔지만, `cd … && git …`·`$변수`·반복문·따옴표 안 중괄호가 섞인 명령은 Claude Code 가 미리 검사하지 못한다며 확인창을 띄웠습니다. 리뷰 작업 세 개와 구현 작업 하나를 돌리는 동안 이런 결정이 17개 쌓였고, 모두 검사·조회·설치였습니다. `auto` 의 판단기는 이런 명령을 통과시키고, 판단하지 못하는 것만 확인창으로 남겨 결정이 됩니다. 워커 지시에도 셸 명령을 하나씩 단순하게 쓰라는 줄을 더했습니다. 대화형 세션에서 `auto` 가 실제로 이렇게 동작하는지는 아직 재지 않았습니다.

**셸 명령 정책: 허용 목록이 아니라 샌드박스.** 테스트 실행을 허용하는 순간 워커는 어떤 코드든 실행할 수 있으므로, 명령 목록은 경계가 되지 못합니다. 대신 OS 샌드박스로 어디에 쓸 수 있고 어디에 접속할 수 있는지를 막습니다.

- `sandbox.enabled` + `autoAllowBashIfSandboxed`: 샌드박스 안의 셸 명령은 묻지 않고 실행됩니다.
- 작업 폴더 밖 쓰기는 `operation not permitted` 로 막혔습니다.
- 네트워크는 기본으로 막히고, `network.allowedDomains` 에 넣은 곳만 통과했습니다. 기본 허용은 `registry.npmjs.org` 하나입니다.
- `allowUnsandboxedCommands: false` 로 샌드박스를 끄고 다시 시도하는 탈출구를 닫았습니다.
- worktree 에서의 `git commit` 은 성공했고, 전역 git 작성자 정보도 보였습니다.
- `git -c …` 처럼 설정을 덮어쓰는 명령은 권한 단계에서 거부됐습니다.
- WebFetch·WebSearch·MCP 도구는 승인을 받아야 하는 도구입니다. 비대화 실행에서는 거부됐고, 대화형 워커에서는 권한 결정으로 올라옵니다.

**결과 스키마.** zod 가 만든 JSON Schema 의 `$schema` 키를 Claude Code 가 거부했습니다. 지금은 구조화 출력 대신 보고 줄을 읽으므로 쓰지 않습니다.

## 계정

nod 는 실행한 셸의 Claude 로그인을 그대로 씁니다. 개인 일은 개인 계정으로 돌리려면 `CLAUDE_CONFIG_DIR=<개인 설정 폴더> nod add …` 처럼 실행합니다. tmux 서버는 처음 띄울 때의 환경을 기억하므로, nod 는 `PATH`·`NOD_HOME`·`CLAUDE_CONFIG_DIR` 를 워커 세션마다 직접 넘깁니다.
