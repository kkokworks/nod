# 결정 전하기

결정 알림이 오면 결정 번호(`d<번호>`), 작업(`n<번호>`), 질문을 그대로 사용자에게 전합니다. 아래 `<결정>` 은 그 `d<번호>` 입니다. 답은 사용자의 말로만 넘깁니다.

- `question`·`check_failed`: 사용자가 답하면 `nod <결정> '<답>'`. 사용자의 말을 그대로 넘깁니다. 답은 살아 있는 같은 세션에 들어갑니다. 워커가 `NOD: failed` 로 포기한 것도 `question` 으로 오고, 질문에 그 줄이 들어 있습니다. `check_failed` 는 검증 명령이나 독립 리뷰가 재시도를 다 쓰고도 실패한 것입니다. 질문에 리뷰어의 지적이 들어 있으면 그것도 함께 보여 줍니다. 질문이 `It has waited on background work` 로 시작하면 워커가 띄워 둔 서브 에이전트·셸을 차례 없이 모두 한 시간 넘게 기다린 것이니(기다림 사이에 돈 차례의 시간은 빼고) 그 점을 전합니다. 질문에 `nod passes on at most 4 between two tasks` 가 있으면 두 작업의 워커가 서로 말을 네 번 넘게 주고받으려 해 nod 가 그 보고의 메시지를 모두 멈춘 것입니다. 그 메시지들을 보여 주고, 사용자가 넘기라고 하면 `nod tell <받을 작업> '<메시지>'` 로 넘긴 뒤 결정에 답합니다.
- `permission`: 워커가 권한 확인 화면에서 기다리는 중입니다. 결정 내용에 화면이 들어 있으니 무엇을 하려는지 보여 줍니다. 사용자가 허락하면 `nod <결정> yes`, 아니면 사용자의 말을 그대로 `nod <결정> '<말>'` 로 넘깁니다(거절과 함께 그 말이 워커에게 갑니다).
- nod 가 스스로 허락한 권한 확인은 결정으로 오지 않고, nod 의 알림으로 `n<작업> 허락: <명령>` 한 줄이 옵니다. 답할 것이 없으니 사용자에게 한 줄로 전하기만 합니다. nod 가 허락하는 권한 확인은 그 작업의 폴더 안에서만 영향이 있고 다시 만들 수 있는 Bash 명령뿐입니다(그 밖에 사용자가 이미 믿은 레포의 신뢰 확인도 넘깁니다, 아래 `trust`). worktree 안에서 커밋하지 않은 일이 없는 경로를 지우는 `rm -rf`·`rm -fr` 과, 레지스트리 패키지를 설치·삭제하는 `bun`·`npm`·`pnpm`·`yarn` 명령입니다. 작업 폴더 밖 삭제·덮어쓰기, push·PR·댓글·메시지·MCP 쓰기 같은 바깥 쓰기, 운영 시스템·DB 접근, 비밀값, 권한 설정 변경, 판단이 애매한 것은 그대로 `permission` 결정으로 오고, 워커의 질문은 `question` 결정으로 옵니다. 이 범위를 넓히는 것은 nod 코드(`src/allow.ts`)를 고칠 일이라, 결정에 대신 yes 로 답해서 넓히지 않습니다.
- `trust`: 워커가 Claude Code 가 아직 신뢰하지 않는 레포에서 신뢰 확인을 기다립니다. 신뢰하면 그 레포에 들어 있는 Claude 설정·훅이 워커에서 실행된다는 점을 함께 전합니다. 사용자가 허락하면 `nod <결정> yes`, 아니면 사용자의 말을 그대로 넘깁니다(작업이 취소됩니다). 사용자가 앞 작업의 `trust` 결정에서 같은 레포를 이미 믿었으면(마지막 답이 yes) 계정이 바뀌어 다시 물어도 결정으로 오지 않고, `n<작업> 허락: trust <레포>, as the person did in decision d<결정> …` 한 줄이 위 허락처럼 옵니다.
- `rule`: 검증에 되돌려졌거나 실패한 작업을 회고 워커가 돌아보고, 앞으로 모든 워커가 받을 규칙 한 줄을 제안했습니다. 규칙과 회고 번호(`r<n>`), 그 계기가 된 작업을 보여 줍니다. 사용자가 받아들이면 `nod <결정> yes` 로 장부의 규칙에 들어가 그 회고와 이어지고, 아니면 사용자의 말을 넘겨 버립니다. 문구를 고치고 싶어 하면 받아들이지 말고 버린 뒤 `nod rule add '<문구>'` 로 새로 넣습니다. 이미 받아들인 규칙이면 `nod rule off <번호>` 로 끄고 새 문구를 `nod rule add` 로 넣습니다(문구 고치기는 없음). 나중에 빼고 싶어 하면 `nod rule off <번호>` 입니다(지우기는 없음). 규칙을 바꾸는 명령도 사용자가 말한 대로만 부릅니다.
- `interrupted`: 워커의 Claude Code 가 답하던 도중에 끝났습니다(계정 전환·충돌로 칸 안에서 다시 떴거나, 재부팅·tmux 종료로 칸이 사라짐). 또는 띄우자마자 거듭 끝나서 nod 가 다시 띄우기를 멈췄습니다(로그인이 없는 등, 질문에 마지막 화면이 들어 있음). 또는 메시지를 받기 전에 칸이 거듭 끝나서 nod 가 칸을 다시 열기를 멈췄습니다(칸 안의 `nod run` 이 뜨지 못하는 등). 그 차례의 일이 일부 됐을 수 있다는 점과 질문에 든 화면을 전합니다. 다만 메시지를 받기 전에 칸이 끝난 경우는 한 일이 없고, 받지 못한 메시지가 답보다 먼저 워커에게 간다고 전합니다. 사용자가 이어 가라고 하면 사용자의 말을 그대로 `nod <결정> '<말>'` 로 넘깁니다. 워커는 같은 대화에서 "차례가 끊겼으니 된 것부터 확인하라"는 말과 함께 받습니다. 화면에 로그인 문제가 보이면 먼저 고친 뒤 답하라고 안내합니다.
- `stuck`: nod 가 보낸 메시지가 워커에게 들어가지 않았습니다. 칸에 nod 가 모르는 창이 떠 있거나 무언가 막고 있습니다. 질문에 든 화면 줄과 메시지 앞부분을 보여 주고, 사용자가 `nod attach <작업>` 으로 칸을 보고 치운 뒤 `nod <결정> yes` 로 답하게 합니다. 아직 들어가지 않았으면 nod 가 메시지를 다시 보냅니다. 칸을 치우지 않고 답하면 화면이 그대로이므로 아무것도 치지 않고 다시 묻습니다. 다른 답은 메시지에 이어 워커에게 갑니다. 모르는 창의 선택지를 고르면 사용자의 Claude Code 설정이 바뀔 수 있으니 오케스트레이터가 칸에 키를 보내 풀지 않습니다. 메시지를 보낸 명령은 이때 `sent` 대신 `not in yet: …` 을 찍습니다. 열린 동안 `nod tell` 은 거절됩니다. 메시지가 저절로 들어가면 결정은 `(the message went in)` 로 닫힙니다.
- 사용자가 그 작업을 그만두라고 하면 `nod drop <결정>`. 세션도 닫힙니다. 열린 결정이 없는 작업(대기·도는 중)은 `nod cancel <작업> [--reason '<이유>']` 로 같게 끝냅니다. 이미 끝난 작업(succeeded·cancelled)에 남은 결정은 답하든 drop 하든 결정만 닫히고 작업은 그대로입니다.
- 사용자가 이 세션 밖에서 결정에 답하거나 닫으면 `decision <결정> <이유> answered by the person (task n<작업> …): <답>` 알림이 옵니다. 이미 닫힌 결정이니 사용자에게 한 줄로 전하기만 하고, 다시 답하지 않습니다(`nod <결정>`·`nod drop <결정>` 을 부르지 않음). 그 결정을 사용자에게 묻던 중이었으면 그 물음을 거둡니다.

## 자리를 비울 때 알림

사용자가 자리에 없을 때도 결정을 알고 싶어 하면 `~/.nod/notify` 실행 파일을 만들어 줍니다. nod 가 아래 일마다 JSON 한 줄을 stdin 으로 넘겨 부릅니다. 무엇으로 알릴지(macOS 알림, 개인 Slack 웹훅 등)는 사용자가 고릅니다.

- 결정이 열림(`decision`), 결정이 닫힘(`answered`, nod 가 스스로 닫은 것도)
- 작업이 성공함(`succeeded`), 오류로 끝나거나 시작에 실패함(`error`), 취소됨(`cancelled`)
- 착지: PR 을 엶(`pr_opened`), 머지함(`merged`), 기다리거나 실패한 까닭이 바뀜(`landing`)
- 할 일 감시가 통과함(`watch_passed`), 더는 돌 수 없음(`watch_failed`)
- 워커를 다시 띄울 차례인데 사람이 칸에 붙어 있어 기다림(`restart_held`)
